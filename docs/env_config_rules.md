# Env & Config Rules — окружение, секреты, настройки

> Два разных места для конфигурации: **окружение** (инфраструктура, секреты, задаётся при
> деплое) и **таблица настроек** (то, что меняют в UI без рестарта). Секреты не покидают
> окружение никогда.

## 1. Триада файлов окружения

| Файл | В git | Назначение |
|------|-------|-----------|
| `.env` | ❌ | рабочие значения текущей инсталляции |
| `.env.dist` | ✅ | шаблон: все ключи с пустыми/безопасными значениями |
| `.env.local` | ❌ | локальные переопределения и credentials для тестов |

**Новая переменная добавляется в оба файла сразу** — в `.env` (чтобы работало) и в
`.env.dist` (чтобы работало у остальных). Забыл `.dist` — следующий человек полдня ищет
`KeyError`.

`.env.local` не копия `.env`, а список отличий конкретной машины: загрузчик читает его
**поверх** `.env` и только переопределяет ключи. Ключа в нём нет — работает значение из
`.env`, нет самого файла — работает один `.env`. Поэтому в `.env.local` кладут ровно то,
что на этой машине расходится с инсталляцией, и ничего больше.

Загрузка `.env.local` идёт с override существующих переменных окружения — иначе она
бессмысленна: оркестратор отдаёт контейнеру `.env` уже настоящими переменными, а
обычный `load_dotenv` их не трогает и файл молча ни на что не влияет.

Хосты сервисов задаются в окружении **именами сервисов оркестратора**, а не `localhost`.
Отсюда следствие: приложение запускается только внутри своей композиции; попытка поднять
процесс «просто так» на хосте не разрешит имена и упадёт.

## 2. Секреты

1. **В документации, коммитах и истории shell секретов нет.** Ни разу, ни «для примера».
   Значение читается из файла окружения в момент вызова.
2. **Пароли не передаются аргументами командной строки** — аргументы видны в списке
   процессов. Только через переменную окружения процесса.
3. **Прод-окружение доставляется как единый секрет CI** и перезаписывает файл целиком.
   Отсюда главные грабли: **переменная, добавленная руками на сервере, исчезает при
   следующем деплое**. Новая прод-переменная добавляется в секрет CI, а не на сервере.
4. Ротация секрета — это правка секрета CI и деплой, а не `ssh` и `nano`.

## 3. Таблица настроек: то, что меняется без рестарта

Окружение — про инфраструктуру. Всё, что должен менять человек в UI, живёт в БД.

### Область действия (scope)

Настройка адресуется тройкой: **ключ + область**. Типичные области — глобальная, на узел
(инсталляцию/сервис), на пользователя. Разрешение значения — от узкого к широкому:
пользователь → узел → глобально.

### Ручной upsert обязателен

> ⚠️ **`UNIQUE INDEX` не ловит дубли, если часть ключа `NULL`.** SQL считает `NULL`
> не равным `NULL`, поэтому `(key, node_id=NULL, user_id=NULL)` вставится сколько угодно
> раз, и `INSERT ... ON DUPLICATE KEY UPDATE` не сработает.

Поэтому запись значения делается вручную:

```python
# UPDATE по ключу и области; если ничего не обновилось — INSERT
rowcount = await update(...)
if rowcount == 0:
    await insert(...)
```

Альтернатива — запретить `NULL` и хранить `0` как «нет области». Выбор один из двух, но
осознанный: молчаливые дубли настроек — очень дорогой в отладке баг.

### Служебные значения

Настройки, которые пишет код (счётчики, последний прогон, кэши, выбранные наборы данных),
помечаются флагом «динамическая» и **скрываются из UI**. Иначе список настроек
превращается в свалку, где человеку нечего править.

## 4. Конфиг для фронтенда

Фронтенду нужны некоторые значения окружения (внешние URL, флаги фич, лимиты). Для этого
делается один endpoint, отдающий **явно перечисленный белый список** ключей.

> ⚠️ **Секреты сюда не попадают.** Всё, что возвращает этот endpoint, видно в DevTools
> любому пользователю. Белый список — перечисление, а не фильтрация по маске.

На клиенте — один загрузчик с дедупликацией: параллельные вызовы должны отдать один и
тот же промис, иначе десять компонентов сделают десять запросов на старте страницы.

## 5. Чек-лист новой настройки

1. Решить, где ей место: **окружение** (инфраструктура/секрет, нужен рестарт) или
   **таблица настроек** (правит человек, применяется сразу).
2. Окружение → добавить в `.env` **и** `.env.dist`; для прода — в секрет CI.
3. Таблица → определить область действия и дефолт на случай отсутствия записи.
4. Нужна на фронтенде → добавить ключ в белый список конфиг-endpoint, **проверив, что это
   не секрет**.
5. Прочитать код чтения: есть ли осмысленное поведение, когда значения нет вообще.

## Грабли

1. **Забыт `.env.dist`** — падение у всех, кроме автора
2. **Прод-переменная добавлена на сервере** — стёрта следующим деплоем
3. **`UNIQUE` с `NULL`** — молчаливые дубли настроек, «настройка не применяется»
4. **Секрет в конфиг-endpoint** — утечка в браузер
5. **Нет дефолта** — приложение падает на свежей БД, где записи настройки ещё нет
6. **`localhost` вместо имени сервиса** — работает локально, не работает в композиции
