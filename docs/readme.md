# Docs Common — универсальные правила для всех проектов

> Здесь лежит документация **без привязки к конкретному проекту**: правила, которые
> действуют одинаково во всех репозиториях. Всё, что содержит имена таблиц, порты,
> контейнеры, роуты и прочие детали одной инсталляции, живёт в `.claude/docs/` самого
> проекта.
>
> **Единственный источник — `py_modules/docs/`.** Папка живёт в общем submodule и
> подключается в проект симлинком `.claude/docs-common -> ../py_modules/docs`. Правка
> делается здесь один раз и приезжает во все проекты обновлением submodule; копий,
> которые расходятся, больше нет.

## Как разделять `docs-common/` и `docs/`

| | `.claude/docs-common/` | `.claude/docs/` |
|--|------------------------|-----------------|
| Что описывает | правило, принцип, паттерн | как это реализовано здесь |
| Пример | «схема живёт в одном файле миграции» | «схема — `migrations/20260101000000_initial_schema.sql`» |
| Пример | «страница регистрируется в карте меню» | «допиши URL в `groupMap` в `base.html`» |
| Переносимость | копируется в новый проект как есть | не имеет смысла вне проекта |

Практический тест: **если файл нельзя скопировать в пустой новый проект без правок —
он не для `docs-common/`.** Конкретика заменяется на роль: не `migrations/20260101000000_initial_schema.sql`,
а «единственный DDL-файл»; не `uvicorn`, а «контейнер приложения».

## Как править

1. Правка делается **в `py_modules/docs/`** — это и есть источник.
2. Коммит идёт в репозиторий `py_modules`, а не в проект.
3. В проектах, где нужна свежая версия, двигается указатель submodule:
   `git submodule update --remote py_modules` и коммит нового указателя.

Так выглядит и обратное правило: **править файл через симлинк из проекта — значит править
общий репозиторий.** Изменения увидят все, поэтому проектная конкретика сюда не попадает
(тест переносимости выше).

⚠️ Копии этой папки в проектах заводить нельзя. Так уже было: до переноса `code_rules.md`
разошёлся между проектами на 67 строк — правку внесли в одном и не перенесли, и через
месяц это были два разных документа с одним именем.

## Зависимости

Библиотеки общих модулей объявлены рядом с ними, а не угадываются в проекте:

```bash
pip install -r py_modules/requirements.txt          # ядро: картинки и замеры (Pillow, numpy)
pip install -r py_modules/requirements-vision.txt   # + зрение через ai_vision (pydantic-ai)
pip install -r py_modules/requirements-doc.txt      # + документы: pdf_ и font_
```

В проектном requirements — одна строка `-r py_modules/requirements.txt`: тогда venv
ставится вместе с зависимостями общих модулей, а не добирает пакеты отдельной сессией;
нужную половину проект добирает своей строкой.

Ядро тощее сознательно, и половины отдельные по одной причине: `adb_` работает без
LLM-стека, а замер экрана не должен тянуть ни `pydantic-ai`, ни разбор PDF. Половины
подключают своё лениво, внутри функций, поэтому **импорт модуля не проверяет
зависимости** — падает вызов функции, а не `import`.

## Правила самой этой папки

1. **Один файл — одна тема.** Ориентир — до ~200 строк; больше — сигнал делить.
2. **Имена** — lowercase snake_case, суффикс `_rules` для файлов-правил.
3. **Никаких секретов и хостов.** Ни паролей, ни доменов, ни IP — даже в примерах.
4. **Примеры кода — обобщённые.** `<entity>`, `<domain>`, `<namespace>` вместо реальных имён.
5. **Правило добавляется, когда наступили на грабли дважды.** Умозрительные best practices
   без истории отладки в этой папке не нужны.
