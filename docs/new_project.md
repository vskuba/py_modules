# New Project — каркас нового проекта

> Проекты экосистемы устроены одинаково: FastAPI + SSR-страницы, MySQL с миграциями yoyo,
> сессионная авторизация, общий submodule библиотек, docker-compose с одинаковым набором
> сервисов. Новый проект **не придумывается с нуля** — берётся этот каркас, а своим в нём
> остаётся предметная часть.
>
> Документ собран сравнением трёх работающих проектов: то, что совпало у всех, и есть
> каркас; где они разошлись — сказано отдельно и с причиной.

## 1. Что копируется, а что пишется заново

| Слой | Откуда берётся |
|------|----------------|
| Общие библиотеки | submodule `py_modules` — подключается, не копируется (`py_modules.md`) |
| Универсальные правила | симлинк на `py_modules/docs` — не копируется (§7) |
| Каркас приложения | `main_uvicorn.py` соседнего проекта — правится под свои роутеры |
| Раскладка папок | §2, повторяется без изменений |
| Compose и Dockerfile | §4, меняются имена сервисов и порты |
| Авторизация, seed, backup | копируются как есть, меняется список ролей |
| **Предметная область** | **пишется заново — это и есть новый проект** |

Правило простое: **если код не про предметную область — он уже написан.** Ищи в
`py_modules` и у соседей, прежде чем писать.

## 2. Раскладка папок

```
<project>/
    CLAUDE.md                    точка входа для агента: что за проект, куда смотреть
    main_uvicorn.py              сборка приложения: middleware, роутеры, статика, миграции
    docker-compose.yml           сервисы
    docker-compose.override.yml  локальные отличия, в git не идёт
    docker-compose.override.yml.dist   образец override для нового разработчика
    pyproject.toml               зависимости и настройки pytest
    deploy.sh                    выкладка на прод

    .claude/
        docs/                    устройство этого проекта
        docs-common/             универсальные правила (копия, см. §7)

    src/
        auth/                    вход, сессии, роли, пароли
        mysql_/repository/       репозитории поверх AbstractRepository
        uvicorn/routers/         HTTP-точки, по файлу на подсистему
        <domain>/                предметная логика — своя у каждого проекта
        worker/                  фоновые обработчики (если нужны)

    data/
        uvicorn/template/        Jinja2-шаблоны SSR-страниц
        uvicorn/public/          статика: js, css, vendor
        seeds/                   SQL-снимки данных
        backups/                 дампы базы
        logs/                    журналы

    migrations/                  SQL-миграции yoyo, имя — метка времени
    scripts/                     разовые и служебные скрипты
    docker/uvicorn/              dockerfile и requirements.txt
    tests/                       интеграционная сюита
```

Папки `data/`, `logs/`, `backups/` держат **данные, а не код**: их пути задаются
переменными (`DATA_DIR`, `LOG_DIR`), чтобы в контейнере и на хосте они не расходились.

## 3. Каркас приложения

`main_uvicorn.py` собирается по одному шаблону — у двух соседних проектов он совпадает
почти построчно, включая имя функции middleware:

```python
middleware = [
    Middleware(SessionMiddleware, secret_key=config_get('SESSION_SECRET_KEY', '<project>-dev'),
               session_cookie='<project>_session'),
    Middleware(BaseHTTPMiddleware, dispatch=main_uvicorn_auth_middleware),
]
app = FastAPI(lifespan=lifespan, middleware=middleware)

app.mount('/static', StaticFiles(directory=...), name='static')
app.state.jinja2_template = Jinja2Templates(directory=...)
```

Обязательный минимум:

1. **Сессии** — `SessionMiddleware` с секретом из `.env`; своё имя cookie, иначе проекты
   на одном домене затирают сессии друг друга.
2. **Авторизация одним middleware** — `main_uvicorn_auth_middleware`: закрывает всё, кроме
   белого списка путей (логин, статика, health).
3. **Миграции при старте** — `mysql_migration_up()` в `lifespan`, до подъёма роутеров.
4. **Единый формат ошибок** — обработчик `RequestValidationError`, чтобы клиент получал
   один и тот же контракт (`api_rules.md`).
5. **Статика и шаблоны** — `StaticFiles` + `Jinja2Templates`, страницы рендерятся на
   сервере (`frontend_rules.md`).

⚠️ **Голый JSON в браузер не отдаём.** Ответ на неавторизованный запрос страницы — редирект
на вход, а не `{"detail": "Not authenticated"}`: человек видит белый экран с текстом и не
понимает, что делать.

## 4. Контейнеры

Минимальный набор сервисов, общий для всех проектов:

| Сервис | Зачем |
|--------|-------|
| `<prefix>_uvicorn` | само приложение |
| `<prefix>_mysql` | база |
| `<prefix>_phpmyadmin` | смотреть базу глазами |
| `<prefix>_redis` | очереди и кэш — если есть фоновая работа |
| `<prefix>_caddy` | HTTPS наружу — если проект смотрит в интернет сам |

**Имена сервисов с префиксом проекта.** На сервере проекты живут рядом, и `mysql` без
префикса — это столкновение имён и чужой контейнер под рукой. То же с томами.

База образа одна на все проекты — `python:3.11-slim`. Общее ядро зависимостей:

```
fastapi uvicorn jinja2 python-multipart python-dotenv
aiomysql pymysql yoyo-migrations
bcrypt cryptography itsdangerous
httpx python-json-logger
```

Порты наружу публикует **один** проект — тот, что стоит фронтом. Остальные ходят через
его reverse proxy: два Caddy на одном хосте подерутся за 80/443.

## 5. Настройки

Три слоя, порядок важен (`env_config_rules.md`):

| Файл | Что в нём | В git |
|------|-----------|-------|
| `.env` | рабочие значения установки | **нет** |
| `.env.local` | секреты и локальные отличия | **нет** |
| `.env.dist` | образец: все ключи, значения пустые | **да** |

Проверено во всех трёх проектах: в `.gitignore` стоят `.env`, `.env.local`, `.env.prod`, а
под версией только `.env.dist`. Отсюда правило: **завёл новую переменную — впиши её в
`.env.dist`**, иначе о ней узнает только тот, кто полезет читать код. Прод свой `.env`
получает не из репозитория (`deploy_rules.md`).

Переменные, которые есть у каждого проекта:

```bash
DATA_DIR=  LOG_DIR=      # где лежат данные и журналы
MYSQL_HOST= MYSQL_PORT= MYSQL_PORT_HOST= MYSQL_USER= MYSQL_PASSWORD= MYSQL_DATABASE=
PHPMYADMIN_PORT=
SESSION_SECRET_KEY=      # свой у каждого проекта
ADMIN_USERNAME= ADMIN_PASSWORD=
```

`MYSQL_PORT` — **контейнерный** (3306), `MYSQL_PORT_HOST` — тот, что виден с хоста. Путать
их — классика: приложение в контейнере ходит по внутреннему, скрипты с хоста по внешнему.

`APP_ENV` (`local` / `prod`) заводится, когда появляется первая ветка «только на проде» —
прод-заглушка, другой адрес, отключённый прогон. Пока таких нет, переменная не нужна: из
трёх проектов она есть у одного.

Проект, который пользуется соседним, добавляет его адрес и токен:

```bash
RHAPSODY_URL=            # адрес проекта-хаба
RHAPSODY_TOKEN=          # токен служебной учётки с узкими правами
```

**Служебная учётка узкая.** Не админ: сосед получает роль ровно под то, что вызывает
(`auth_rules.md`).

## 6. База и миграции

- Схема и данные — **только миграциями** yoyo (`database_rules.md`), применяются при
  старте приложения.
- Имя файла — метка времени с секундами: `date +%Y%m%d%H%M%S`, дальше короткое описание.
  Два файла на одну метку yoyo применит в неопределённом порядке.
  ⚠️ Порядковая нумерация (`0001.sql`, `0002.sql`) в одном из проектов осталась
  исторически и **для нового не годится**: над проектом работают параллельно, две ветки
  займут один номер, и конфликт вскроется только при слиянии. Метка времени расходится сама.
- Начальная схема — один файл `<метка>_initial_schema.sql`, дальше только правки поверх.
- Каждая миграция **идемпотентна**: `ADD COLUMN IF NOT EXISTS` MySQL не умеет, поэтому
  через `information_schema` + `PREPARE`, а `UPDATE` сторожит себя признаком «уже
  применено».
- Данные для разработки — `data/seeds/`, снимок отдельно от схемы (`backup_rules.md`).

## 7. Документация

```
.claude/docs-common ->   симлинк на ../py_modules/docs — общие правила, один источник
.claude/docs/            устройство этого проекта
CLAUDE.md                точка входа: что за проект, ключевые файлы, индекс документации
```

Общие правила **не копируются**, а подключаются вместе с submodule:

```bash
ln -s ../py_modules/docs .claude/docs-common
```

`CLAUDE.md` строится одинаково: обзор проекта → как запустить → ключевые файлы → индекс
`docs/` и `docs-common/`. Агент читает его первым, поэтому индекс — не украшение: без него
он ищет по grep и находит не то.

Так было не всегда, и причина переноса именно в этом: пока папку копировали, копии
расходились. Живьём `code_rules.md` разъехался между проектами на 67 строк — правку внесли
в одном и не перенесли. Теперь источник один, и правка приезжает обновлением submodule.

⚠️ **Правка через симлинк — правка общего репозитория.** Файл, открытый как
`.claude/docs-common/code_rules.md`, физически лежит в `py_modules`: коммит идёт туда, и
изменение увидят все проекты. Проектной конкретике здесь не место.

## 8. Деплой

Схема одна на все проекты: **архив → ssh → сборка образа → подъём → проверка**
(`deploy_rules.md`). В `deploy.sh` соседнего проекта она уже написана — берётся оттуда,
меняются имена и адреса.

Что важно не потерять при копировании:

- **`.env` не уезжает** в архиве: на проде свой, и перезапись сотрёт прод-секреты.
- Не тащить `.git`, `logs`, `backups`, `node_modules` — архив раздувается на порядок.
- Образ собирается **до** остановки контейнеров: сборка падает чаще, чем подъём, и
  падать она должна на работающем проекте.
- После подъёма — проверка живьём, а не «команда отработала»: код ответа страницы.

Проект под общим reverse proxy своих портов наружу не публикует — он получает имя на
домене соседа.

## 9. Чек-лист заведения

1. Создать репозиторий, подключить submodule: `git submodule add <url> py_modules`.
2. Подключить общие правила симлинком: `ln -s ../py_modules/docs .claude/docs-common`.
   Скопировать из соседнего проекта: `deploy.sh`,
   `docker/uvicorn/`, `docker-compose*.yml`, `main_uvicorn.py`, `src/auth/`,
   `src/mysql_/repository/`.
3. Разложить папки по §2; пустые `data/*` завести с `.gitkeep`.
4. Заменить во всём скопированном имя проекта: сервисы compose, cookie сессии,
   `SESSION_SECRET_KEY`, префиксы томов.
5. Написать `.env`, `.env.dist`; секреты — в `.env.local`, он в `.gitignore`.
6. Первая миграция — `<метка>_initial_schema.sql` со своей схемой.
7. Поднять: `docker compose up -d`, убедиться, что миграции применились и страница входа
   открывается.
8. Написать `CLAUDE.md` по образцу соседа: обзор, запуск, ключевые файлы, индекс доков.
9. Завести `.claude/docs/` — по файлу на подсистему, по мере появления.
10. Настроить тесты: `pyproject.toml` с `pythonpath = [".", "py_modules"]`, тестовая
    учётка (`testing_rules.md`).
11. Если проект ходит к соседу — завести там служебную учётку с узкой ролью и положить
    её токен в свой `.env.local`.

## Грабли

1. **Имена сервисов без префикса проекта** — на общем сервере столкнутся с чужими
2. **Общий секрет сессии или общее имя cookie** — проекты на одном домене выбивают друг
   друга из сессии
3. **Два reverse proxy на одном хосте** — драка за 80/443; наружу смотрит один
4. **`.env` уехал в деплое** — затёрты прод-секреты, и узнаётся это по отвалившимся
   интеграциям
5. **`MYSQL_PORT` перепутан с `MYSQL_PORT_HOST`** — приложение в контейнере не видит базу
   либо скрипты с хоста не видят её
6. **`docs-common` заведён копией, а не симлинком** — копии расходятся, проверено
7. **Копирование `py_modules` вместо submodule** — правки перестают доезжать до соседей
8. **Своя реализация того, что есть в `py_modules`** — вторая дорога, которая разойдётся
   с первой на первой же правке
