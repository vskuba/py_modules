# New Project — каркас нового проекта

> Проекты экосистемы устроены одинаково: FastAPI + SSR-страницы, MySQL с миграциями yoyo,
> сессионная авторизация, общий submodule библиотек, docker-compose с одинаковым набором
> сервисов. Новый проект **не придумывается с нуля** — берётся этот каркас, а своим в нём
> остаётся предметная часть.
>
> Документ собран сравнением трёх работающих проектов: то, что совпало у всех, и есть
> каркас; где они разошлись — сказано отдельно и с причиной.

## 1. Что копируется, а что пишется заново

| Слой | Откуда берётся |
|------|----------------|
| Общие библиотеки | submodule `py_modules` — подключается, не копируется (`py_modules.md`) |
| **Страницы панели целиком** | **submodule `dashboard` — подключается, не копируется** (§1.1) |
| Универсальные правила | симлинк на `py_modules/docs` — не копируется (§7) |
| Каркас приложения | `main_uvicorn.py` соседнего проекта — правится под свои роутеры |
| Раскладка папок | §2, повторяется без изменений |
| Compose и Dockerfile | §4, меняются имена сервисов и порты |
| Каталог прав и ролей | **пишется свой** — предметное знание (§1.1) |
| **Предметная область** | **пишется заново — это и есть новый проект** |

Правило простое: **если код не про предметную область — он уже написан.** Ищи в
`py_modules`, в `dashboard` и у соседей, прежде чем писать.

### 1.1 ⚠⚠ Вход, люди, настройки, seed и бэкапы писать НЕ надо

Их больше не копируют из соседа — они приезжают submodule-ом `dashboard` вместе
со своими страницами, ручками и хранилищем. Замерено на последней установке:
**подключение занимает ~40 строк в `main_uvicorn.py` и пять роутов** против
нескольких сотен строк, которые копировались раньше.

| Что даёт `dashboard` | Готовое |
|----------------------|---------|
| `panel_auth*` | вход сессией и токеном, зависимости роутов, три точки `/auth` |
| `panel_user*` | страница `/admin/user`, ручки `/api/users`, запреты домена |
| `panel_setting_api` | значения установки, часовой пояс панели |
| `panel_seed_api`, `panel_backup_api` | перенос таблиц и дамп базы со страницами |
| `panel_static`, `panel_template` | раздача и шаблоны «свой каталог первым» |
| `panel_access`, `panel_store` | **механизм** прав и хранения |

Проект пишет к ним ровно три вещи:

1. **каталог прав** — какие права бывают и что входит в роль (`PanelAccess`).
   ⚠⚠ В общий слой он не уезжает ни при каких условиях: `panel:work`,
   `install:manage` — имена чужой предметной области;
2. **`base.html` со своим меню** — общая страница делает `{% extends "base.html" %}`
   и берёт **его**, поэтому своё меню не мешает ей быть общей;
3. **то, что каркас просит, но не имеет** — см. §3.2. Это и есть главный
   источник тихих поломок на новой установке.

Своё хранилище людей (`PanelUserStore`) нужно, только если схема разошлась с
умолчанием «роль строкой в `user.role`».

⚠ Копировать `src/auth/` у соседа целиком не надо: там двери-переходники к
каркасу под его число вызовов. Новой установке хватит `auth_access.py`
(каталог) и тонкого `auth.py` (короткие имена) — см. §3.1.

## 3. Каркас приложения

`main_uvicorn.py` собирается по одному шаблону — у двух соседних проектов он совпадает
почти построчно, включая имя функции middleware:

```python
middleware = [
    Middleware(SessionMiddleware, secret_key=config_get('SESSION_SECRET_KEY', '<project>-dev'),
               session_cookie='<project>_session'),
    Middleware(BaseHTTPMiddleware, dispatch=main_uvicorn_auth_middleware),
]
app = FastAPI(lifespan=lifespan, middleware=middleware)
```

### 3.1 Подключение каркаса панели — это весь «готовый» слой

```python
# ⚠⚠ Шаблоны и статика ищутся в ДВУХ каталогах: свой первым, общий следом.
#    Без `shared` общая страница просто не находится.
app.state.jinja2_template = panel_template_env(
    os.path.join(DATA, 'template'), shared=os.path.join(ROOT, 'dashboard', 'template'))
app.mount('/static', panel_static_files(PUBLIC_DIR, shared=SHARED_DIR), name='static')
app.state.jinja2_template.env.globals['static_url'] = lambda path: panel_static_url(
    path, PUBLIC_DIR, shared=SHARED_DIR)

app.include_router(panel_auth_api_router())
app.include_router(panel_setting_api_router())
app.include_router(panel_user_api_router(extra_fields=('email',)))
app.include_router(panel_seed_api_router(runtime_tables=(...), title='<project>'))
app.include_router(panel_backup_api_router())
```

⚠⚠ **Пара каталогов `(PUBLIC_DIR, SHARED_DIR)` считается один раз и называется
именем.** Раздача статики и метка её версии обязаны смотреть в одни и те же
каталоги в одном порядке: разойдись они — метка считается по одному файлу, а
отдаётся другой, и ES-модуль из `dashboard` застревает в кэше вкладки навсегда
(`panel.md`, §11). Два одинаковых `os.path.join` в двух вызовах держат это на
внимательности правящего, а расходятся такие пары молча.

⚠ Роутеры каркаса отдаются **функцией**, а не переменной модуля: два приложения
в одном процессе (так живут тесты) получили бы один объект с уже навешенными
роутами.

⚠⚠ **Каталог прав и хранилище подключаются на импорте `src/auth/auth.py`, а не в
`lifespan`.** Зависимости вроде `auth_required` зовут и тесты, которые приложение
не поднимают: подключи договор на старте — в таких прогонах права останутся
незаведёнными, то есть **полными у всех**, и тест на отказ позеленеет, ничего не
проверив.

### 3.2 ⚠⚠ Чего каркас просит у проекта — и не получив, молчит

Самый дорогой класс ошибок новой установки: страница отдаёт `200`, рисуется
целиком и **не работает**. Ни отказа, ни записи в журнале.

| Страница | Чего ждёт | Не дали — что видно |
|----------|-----------|---------------------|
| `/admin/user` | ручку `GET /role/list` → `{'result':[{'id','name'}]}` | выбор роли **пуст**, роль не назначить |
| `/admin/user` | ключ `email` в ответе `/api/users` | в поле строка **`undefined`** |
| `/admin/seed` | `runtime_tables` доводом | рабочие таблицы отмечены к переносу |
| любая | `base.html` проекта с меню **и `groupMap`** | раздел в шапке не подсвечен |

⚠⚠ `email` **нельзя убрать своей копией шаблона**: `user.js` пишет в поле без
проверки на `null`, и удаление элемента роняет открытие карточки целиком. Проще
завести столбец — `extra_fields=('email',)` плюс своё хранилище.

⚠ Ручки, которых у установки нет (`/node/list`), страница спрашивает мягко и
отказ глотает. Это замысел, но он же и прячет забытую ручку: **проверяй кадром и
консолью, а не кодом ответа**.

Обязательный минимум:

1. **Сессии** — `SessionMiddleware` с секретом из `.env`; своё имя cookie, иначе проекты
   на одном домене затирают сессии друг друга.
2. **Авторизация одним middleware** — `main_uvicorn_auth_middleware`: закрывает всё, кроме
   белого списка путей (логин, статика, health).
3. **Миграции при старте** — `mysql_migration_up()` в `lifespan`, до подъёма роутеров.
4. **Единый формат ошибок** — обработчик `RequestValidationError`, чтобы клиент получал
   один и тот же контракт (`api_rules.md`).
5. **Статика и шаблоны** — `StaticFiles` + `Jinja2Templates`, страницы рендерятся на
   сервере (`frontend_rules.md`).

⚠️ **Голый JSON в браузер не отдаём.** Ответ на неавторизованный запрос страницы — редирект
на вход, а не `{"detail": "Not authenticated"}`: человек видит белый экран с текстом и не
понимает, что делать.

## 4. Контейнеры

Минимальный набор сервисов, общий для всех проектов:

| Сервис | Зачем |
|--------|-------|
| `<prefix>_uvicorn` | само приложение |
| `<prefix>_mysql` | база |
| `<prefix>_phpmyadmin` | смотреть базу глазами |
| `<prefix>_redis` | очереди и кэш — если есть фоновая работа |
| `<prefix>_caddy` | HTTPS наружу — если проект смотрит в интернет сам |

**Имена сервисов с префиксом проекта.** На сервере проекты живут рядом, и `mysql` без
префикса — это столкновение имён и чужой контейнер под рукой. То же с томами.

База образа одна на все проекты — `python:3.11-slim`. Общее ядро зависимостей:

```
fastapi uvicorn jinja2 python-multipart python-dotenv
aiomysql pymysql yoyo-migrations
bcrypt cryptography itsdangerous
httpx python-json-logger
```

Порты наружу публикует **один** проект — тот, что стоит фронтом. Остальные ходят через
его reverse proxy: два Caddy на одном хосте подерутся за 80/443.

## 5. Настройки

Три слоя, порядок важен (`env_config_rules.md`):

| Файл | Что в нём | В git |
|------|-----------|-------|
| `.env` | рабочие значения установки | **нет** |
| `.env.local` | секреты и локальные отличия | **нет** |
| `.env.dist` | образец: все ключи, значения пустые | **да** |

Проверено во всех трёх проектах: в `.gitignore` стоят `.env`, `.env.local`, `.env.prod`, а
под версией только `.env.dist`. Отсюда правило: **завёл новую переменную — впиши её в
`.env.dist`**, иначе о ней узнает только тот, кто полезет читать код. Прод свой `.env`
получает не из репозитория (`deploy_rules.md`).

Переменные, которые есть у каждого проекта:

```bash
DATA_DIR=  LOG_DIR=      # где лежат данные и журналы
MYSQL_HOST= MYSQL_PORT= MYSQL_PORT_HOST= MYSQL_USER= MYSQL_PASSWORD= MYSQL_DATABASE=
PHPMYADMIN_PORT=
SESSION_SECRET_KEY=      # свой у каждого проекта
ADMIN_USERNAME= ADMIN_PASSWORD=
```

`MYSQL_PORT` — **контейнерный** (3306), `MYSQL_PORT_HOST` — тот, что виден с хоста. Путать
их — классика: приложение в контейнере ходит по внутреннему, скрипты с хоста по внешнему.

`APP_ENV` (`local` / `prod`) заводится, когда появляется первая ветка «только на проде» —
прод-заглушка, другой адрес, отключённый прогон. Пока таких нет, переменная не нужна: из
трёх проектов она есть у одного.

Проект, который пользуется соседним, добавляет его адрес и токен:

```bash
RHAPSODY_URL=            # адрес проекта-хаба
RHAPSODY_TOKEN=          # токен служебной учётки с узкими правами
```

**Служебная учётка узкая.** Не админ: сосед получает роль ровно под то, что вызывает
(`auth_rules.md`).

## 6. База и миграции

- Схема и данные — **только миграциями** yoyo (`database_rules.md`), применяются при
  старте приложения.
- Имя файла — метка времени с секундами: `date +%Y%m%d%H%M%S`, дальше короткое описание.
  Два файла на одну метку yoyo применит в неопределённом порядке.
  ⚠️ Порядковая нумерация (`0001.sql`, `0002.sql`) в одном из проектов осталась
  исторически и **для нового не годится**: над проектом работают параллельно, две ветки
  займут один номер, и конфликт вскроется только при слиянии. Метка времени расходится сама.
- Начальная схема — один файл `<метка>_initial_schema.sql`, дальше только правки поверх.
- Каждая миграция **идемпотентна**: `ADD COLUMN IF NOT EXISTS` MySQL не умеет, поэтому
  через `information_schema` + `PREPARE`, а `UPDATE` сторожит себя признаком «уже
  применено».
- Данные для разработки — `data/seeds/`, снимок отдельно от схемы (`backup_rules.md`).

## 7. Документация

```
.claude/docs-common ->   симлинк на ../py_modules/docs — общие правила, один источник
.claude/docs/            устройство этого проекта
CLAUDE.md                точка входа: что за проект, ключевые файлы, индекс документации
```

Общие правила **не копируются**, а подключаются вместе с submodule:

```bash
ln -s ../py_modules/docs .claude/docs-common
```

`CLAUDE.md` строится одинаково: обзор проекта → как запустить → ключевые файлы → индекс
`docs/` и `docs-common/`. Агент читает его первым, поэтому индекс — не украшение: без него
он ищет по grep и находит не то.

Так было не всегда, и причина переноса именно в этом: пока папку копировали, копии
расходились. Живьём `code_rules.md` разъехался между проектами на 67 строк — правку внесли
в одном и не перенесли. Теперь источник один, и правка приезжает обновлением submodule.

⚠️ **Правка через симлинк — правка общего репозитория.** Файл, открытый как
`.claude/docs-common/code_rules.md`, физически лежит в `py_modules`: коммит идёт туда, и
изменение увидят все проекты. Проектной конкретике здесь не место.

## 8. Деплой

Схема одна на все проекты: **архив → ssh → сборка образа → подъём → проверка**
(`deploy_rules.md`). В `deploy.sh` соседнего проекта она уже написана — берётся оттуда,
меняются имена и адреса.

Что важно не потерять при копировании:

- **`.env` не уезжает** в архиве: на проде свой, и перезапись сотрёт прод-секреты.
- Не тащить `.git`, `logs`, `backups`, `node_modules` — архив раздувается на порядок.
- Образ собирается **до** остановки контейнеров: сборка падает чаще, чем подъём, и
  падать она должна на работающем проекте.
- После подъёма — проверка живьём, а не «команда отработала»: код ответа страницы.

Проект под общим reverse proxy своих портов наружу не публикует — он получает имя на
домене соседа.

## 9. Чек-лист заведения

Порядок проверен на живом заведении: от пустой папки до работающей панели со
страницами людей, настроек, seed и бэкапов — около часа.

1. Репозиторий и **два** submodule:
   ```bash
   git init -b master
   git submodule add <url>/py_modules py_modules
   git submodule add <url>/dashboard dashboard
   ln -s ../py_modules/docs .claude/docs-common
   ```
   ⚠ Симлинк, а не копия: копии расходятся, проверено.
2. Разложить папки по §2; пустые `data/*` завести с `.gitkeep`.
3. Скопировать из соседа и переименовать: `docker/uvicorn/`, `docker-compose*.yml`,
   `main_uvicorn.py`, `pyproject.toml`. **Заменить имя проекта везде**: сервисы
   compose, тома, cookie сессии, `SESSION_SECRET_KEY`.
4. Написать `.env` и `.env.dist`; пароли — в `.env.local` (он в `.gitignore`).
   ⚠⚠ **Порты — в `.env`, не в `.env.local`**: подстановку `${...}` делает docker,
   а `.env.local` он не читает вовсе. Свободные порты смотреть заранее:
   `ss -ltn | awk '{print $4}' | grep -oE '[0-9]+$' | sort -nu`.
5. Каталог прав: `src/auth/auth_access.py` (`PanelAccess`) и тонкий `auth.py`
   (§1.1, §3.1). Хранилище — только если схема разошлась с умолчанием.
6. Первая миграция `<метка>_initial_schema.sql`: `user`, `user_access_token`,
   `setting`. ⚠⚠ `token` — `VARCHAR(64)`: значение 43 знака, столбец уже режет
   **молча** (`panel.md`, §3).
7. Подключить каркас панели и свои роуты страниц (§3.1), не забыв §3.2.
8. Поднять и **войти глазами**: `docker compose up -d`, страница входа,
   учётка из посева, каждая страница каркаса.
9. **`.venv` на хосте** — без него не идут ни сюита, ни инструменты осмотра:
   ```bash
   python3 -m venv .venv
   .venv/bin/pip install -r docker/uvicorn/requirements.txt -r requirements-dev.txt
   ```
   ⚠ Системный питон закрыт для установки (PEP 668), и пакеты проекта ему не нужны.
10. Сюита: `pyproject.toml` с `pythonpath = [".", "py_modules"]`, `tests/conftest.py`
    на общей обвязке (`tests_panel.md`). ⚠⚠ Порядок строк в нём критичен — §10.
11. `CLAUDE.md` и `.claude/docs/`: обзор, запуск, ключевые файлы, индекс доков.
12. Если проект ходит к соседу — завести там служебную учётку с узкой ролью и
    положить её токен в свой `.env.local`.

## 10. ⚠⚠ `conftest.py`: три строки, порядок которых решает всё

Сюита ходит по HTTP в поднятую панель, и две вещи читаются **на уровне модуля**,
то есть при первом же импорте чего угодно:

```python
from config.config import config_get          # ← ПЕРВЫМ: он и читает `.env`

CONFTEST_DB_PORT = config_get('MYSQL_PORT_HOST', '')
CONFTEST_PORT = config_get('UVICORN_PORT', '')
if not CONFTEST_DB_PORT or not CONFTEST_PORT:
    raise RuntimeError('нет MYSQL_PORT_HOST/UVICORN_PORT: сюите нужен `.env`')

from tests_.tests_db import tests_db_reachable
tests_db_reachable(CONFTEST_DB_PORT)                                    # адрес базы
os.environ.setdefault('BASE_URL', f'http://localhost:{CONFTEST_PORT}')  # адрес панели
```

⚠⚠ **`config_get` импортируется первым, и это не вкусовщина.** Он на импорте
читает `.env`; без него `os.getenv('MYSQL_PORT_HOST')` на чистой оболочке
**пуст** — окружение сюите не даёт никто (контейнеру конфиг кладёт compose,
хосту нет). Поймано опытом: порт брался из запасного числа в коде и совпадал с
`.env` случайно, а поменяй его в `.env` — сюита молча шла по старому адресу.

⚠⚠ **`BASE_URL` обязателен.** Умолчание обвязки — `http://localhost:8000`, то
есть порт **внутри** контейнера, которого с хоста не видно.

⚠ **Запасных значений у портов быть не должно**: единственный их адрес — `.env`,
второе число в коде это «одно значение в двух местах». Пусто — падать словами.

⚠ Сторожу сети надо **разрешить свою панель**: умолчание `http_mock_guard` —
пустой список, то есть «никуда», и без разрешения он валит каждый тест на первом
же запросе.

## Грабли

1. **Имена сервисов без префикса проекта** — на общем сервере столкнутся с чужими
2. **Общий секрет сессии или общее имя cookie** — проекты на одном домене выбивают друг
   друга из сессии
3. **Два reverse proxy на одном хосте** — драка за 80/443; наружу смотрит один
4. **`.env` уехал в деплое** — затёрты прод-секреты, и узнаётся это по отвалившимся
   интеграциям
5. **`MYSQL_PORT` перепутан с `MYSQL_PORT_HOST`** — приложение в контейнере не видит базу
   либо скрипты с хоста не видят её
6. **`docs-common` заведён копией, а не симлинком** — копии расходятся, проверено
7. **Копирование `py_modules` вместо submodule** — правки перестают доезжать до соседей
8. **Своя реализация того, что есть в `py_modules`** — вторая дорога, которая разойдётся
   с первой на первой же правке
9. **Вход и люди написаны руками** — они готовы в `dashboard` (§1.1); сотни
   скопированных строк, которые с первой же правкой каркаса разойдутся
10. **`dashboard` положен в `PYTHONPATH`** — его `src/` сливается с `src/` проекта
    в один namespace-пакет, и файл с совпавшим именем молча перекрывает чужой.
    Импорт идёт **от корня проекта**: `from dashboard.src.panel… import …`
11. **Каркас подключён, а §3.2 забыт** — страница отдаёт `200`, рисуется и не
    работает: пустой выбор роли, `undefined` в поле. Ни ошибки, ни журнала
12. **`.main-wrapper` взят как обёртка обычной страницы** — в общем `common.css`
    это `display: flex; height: 95%`, контейнер двухпанельной страницы: заголовок
    и содержимое встают в ряд и растягиваются на весь экран
13. **Имя своего файла статики совпало с общим** — проект выигрывает, и общая
    страница молча получает чужой скрипт. Сверять до переноса:
    `ls dashboard/css/<имя>.css dashboard/js/<имя>.js`
14. **`.venv` не заведён** — инструменты осмотра падают `ModuleNotFoundError: httpx`,
    и это выглядит как поломка слоя, а не как незаведённое окружение
15. **Проверено кодом ответа, а не кадром** — `200 OK` ничего не говорит о том,
    что увидел человек; половина поломок страницы молчит и в консоли, и в журнале

### ⚠ `docker compose up` падает `all predefined address pools have been fully subnetted`

Не поломка проекта: на машине кончились адреса docker. Демон без `daemon.json`
раздаёт сети из `172.17.0.0/12` по /16 (пятнадцать штук) и из `192.168.0.0/16`
кусками — там, где рядом живут три десятка проектов, свободных не остаётся.

Расширять `default-address-pools` дёшево нельзя: пулы перечитываются **полным
рестартом демона**, то есть даунтаймом всех контейнеров машины, включая чужие.

Лечится адресом сети явно, и **в локальной накладке**, а не в прод-файле — это
свойство машины, а на проде пулы свободны:

```yaml
networks:
  <project>-net:
    ipam:
      config:
        - subnet: 10.51.0.0/24
```

⚠ Диапазон `10.x` берут не наугад: пулы docker его не трогают вовсе. Проверить,
что он свободен, — `ip route`; `192.168.1.0/24` часто настоящая сеть машины, и
захват её адресов оставит хост без интернета.
