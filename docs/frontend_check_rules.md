# Frontend Check Rules — приёмка вёрстки, написанной вслепую

> Тот, кто пишет разметку, её не видит: модель отдаёт HTML и CSS, не получив
> ни одного кадра обратно, и «выглядит правильно» у неё означает «синтаксис
> верный». Поэтому вёрстка не сделана, пока не снят кадр и не сосчитаны числа.
> Проверка идёт тремя кругами: **разметка встала** (rect'ы из DOM —
> `web_probe`), **геометрия сошлась** (арифметика по координатам, а не глаз),
> **кадр чист** (тон, границы, палитра — `web_shot` + `image_*`). Зрение
> модели — последний судья, а не первый.

Устройство страницы (шаблоны, роуты, меню, общие модули) — `frontend_rules.md`;
здесь только приёмка результата. Инструменты описаны в `web_shot.md`,
`image_tooling.md`, `image_scan.md`, `image_layout.md` — эта страница говорит,
**в каком порядке их звать и что считать доказательством**.

## 1. Почему «посмотрел код — правильно» проверкой не является

CSS ошибается не в синтаксисе, а в результате: правило валидно, а блок уехал.
Типовой набор дефектов сгенерированной страницы не виден в исходнике вообще —
он виден только в рендере:

| Дефект | Как выглядит в коде | Как выглядит на кадре |
|--------|---------------------|-----------------------|
| текст не влез в карточку | `overflow: hidden` — норма | обрезано на полуслове |
| колонки разъехались на 3 px | у соседей разный `padding` | ряд «дрожит» |
| отступы не из шкалы | `14px`, `18px`, `22px` вперемешку | ритма нет, а причины не видно |
| элемент вылез за вьюпорт | `width: 100%` + `padding` | горизонтальный скролл |
| блок под липкой шапкой | `position: sticky` без `padding-top` | первая карточка наполовину скрыта |
| палитра расползлась | 30 оттенков серого в файле | «грязный» вид без единой явной ошибки |

Отсюда два правила, нарушение которых обнуляет всю дальнейшую работу:

1. **Правка вёрстки без снятого кадра — гипотеза, а не работа.** Отдавать
   гипотезу как результат нельзя.
2. **Одна правка — один кадр.** Три правки подряд и один кадр в конце не
   говорят, какая из них помогла, а какая сломала соседний блок.

## 2. Базовый кадр снимается до первой правки

`web_shot` вызывается **до** правки и после неё, в одном и том же размере:

```bash
python -m web_.web_shot page.html --out /tmp/ui/before.png --size 390,844
# … правка …
python -m web_.web_shot page.html --out /tmp/ui/after.png  --size 390,844
python -m image_.image_ diff /tmp/ui/before.png /tmp/ui/after.png
python -m image_.image_pair diff-rows /tmp/ui/before.png /tmp/ui/after.png
```

`image_ diff` отвечает «где кадры разошлись зонами», `image_pair diff-rows` —
«какие строки тронуты»: правка одной карточки, задевшая футер, видна первой же
строкой. Без базового кадра фраза «стало лучше» ничем не подтверждается, а
сломанное рядом обнаруживает заказчик.

Кадры живут во временном каталоге (`/tmp/ui/…`), а не в репозитории: это
доказательство на время работы, а не артефакт проекта.

## 3. Круг первый — разметка встала: числа из DOM

Первым идёт зонд, а не снимок: `web_probe` отвечает, **куда страница поставила
элемент**, точными числами и без разглядывания пикселей.

```bash
python -m web_.web_probe page.html --size 520,844 --rect 'header' --rect '.card' --rect '#total'
# {'header': {'x': 0, 'y': 0, 'width': 520, 'height': 18}, '.card': …, '#total': None}
```

⚠️ **Ширину уже 500 px зонд не отдаёт.** `web_probe` (и `web_drive`) поднимают
окно браузера минимум до 500 и молча меряют его: запрошенные `390,844` дают
`innerWidth: 500` — числа придут правдоподобные и неверные (проверено:
360 → 500, 450 → 500, 520 → 520). Мобильная ширина проверяется **кадром**:
`web_shot` узкий вьюпорт кладёт честно (кадр 390 — это вёрстка на 390, а не
крой с 500). Числа — от 520 и выше.

Что читается в ответе:

- **`None` — элемент не отрисовался.** Не «скрыт», а не найден: селектор врёт
  или скрипт упал до вставки узла.
- **`width` или `height` = 0** — узел есть, содержимого нет: пустой контейнер
  на месте виджета глазами не отличить от «данные ещё грузятся».
- **`--rect` берёт первое совпадение** (`querySelector`), поэтому список
  карточек меряется телом зонда, а не десятью селекторами:

```bash
python -m web_.web_probe page.html --size 520,844 --probe-js "
  return [...document.querySelectorAll('.card')].map(e => {
    const r = e.getBoundingClientRect();
    return {x: r.x, y: r.y, w: r.width, h: r.height, text: e.textContent.trim().length};
  })"
```

Число элементов в ответе сверяется с числом записей в данных: страница,
нарисовавшая три карточки из пяти, на кадре выглядит безупречно.

## 4. Круг второй — геометрия: арифметика, а не глаз

Глаз ловит разъезд от ~4 px и не ловит систематический перекос. Считать надо
числами из § 3:

| Вопрос | Чем считается | Дефект |
|--------|---------------|--------|
| колонка выровнена | все `x` ряда равны | разный `padding`/`border` у соседей |
| ряд одной высоты | все `h` равны | карточка тянется по своему содержимому |
| отступы из шкалы | разности координат кратны шагу (4 или 8) | «на глаз подобранные» `14px`, `22px` |
| ничего не вылезло | `x + w <= ширина вьюпорта` | горизонтальный скролл страницы |
| блоки не наложились | rect'ы не пересекаются | элемент под липкой шапкой |

Два зонда, которые стоит гонять на каждой странице:

```bash
# 1. что вылезло за правый край вьюпорта
python -m web_.web_probe page.html --size 520,844 --probe-js "
  return {page: document.documentElement.scrollWidth - innerWidth,
          who: [...document.querySelectorAll('*')]
            .filter(e => e.getBoundingClientRect().right > innerWidth + 1)
            .map(e => e.tagName + (e.className ? '.' + e.className : ''))}"

# 2. где содержимое не поместилось в свой блок
python -m web_.web_probe page.html --size 520,844 --probe-js "
  return [...document.querySelectorAll('*')]
    .filter(e => e.scrollWidth > e.clientWidth + 1 || e.scrollHeight > e.clientHeight + 1)
    .map(e => ({el: e.tagName + '.' + e.className,
                clipped: getComputedStyle(e).overflow !== 'visible',
                w: [e.scrollWidth, e.clientWidth], h: [e.scrollHeight, e.clientHeight]}))"
# [{"el": "DIV.card clip", "clipped": true, "w": [317, 116], "h": [34, 34]}]
```

Второй зонд различает два разных дефекта: `clipped: true` — **текст обрезан**
(пользователь его не увидит), `clipped: false` — **контент вылез** наружу и
наедет на соседа. Первый уже виден в `page > 0` — горизонтальный скролл на
мобильной ширине не прощается ничем.

## 5. Круг третий — кадр: то, чего DOM не знает

DOM не знает, читается ли текст, есть ли шов и сколько в макете красок.
Это меряется по снимку:

| Вопрос | Команда | Почему так |
|--------|---------|------------|
| палитра не расползлась | `image_ literals page.css` | ведомость цветов CSS с яркостью и числом встреч: два почти одинаковых серых в списке — это два серых, а не «оттенок» |
| фон под текстом | `image_ measure shot.png --box 0.1,0.2,0.9,0.3` | мода окна (доли кадра), а не среднее: карточки и текст среднее утягивают |
| реальный габарит содержимого | `image_scan bbox shot.png` | пустой блок с фоном от блока с контентом отличает только это |
| граница блока на месте | `image_layout edge shot.png --band … --axis y` | граница ищется максимумом градиента, порог даёт фальшивый край на скруглении |
| шов, ступенька, лишняя линия | `image_ seam shot.png`, `image_ rect-seams shot.png` | 1 px светлее фона глазами не виден и остаётся в продакшене |
| рамка та, что обещали | `image_ stroke shot.png --rect x0,y0,x1,y1` | ширина ядра, цвет модой и радиус угла — против того, что написано в CSS |

⚠️ **Контраста по WCAG здесь нет** — ни функции, ни CLI. Яркости Rec.601 из
`image_ measure` и `image_ literals` ловят грубое («светло-серое по белому»),
формальный порог 4.5:1 считается отдельно и руками. Пробел назван, чтобы им
не подменяли проверку доступности.

Тексты интерфейса проверяются той же командой, что проза репозитория:

```bash
PYTHONPATH=. python -m tool_.tool_typo        # подмена буквы из другого алфавита в шаблоне
```

Латинская `c` в русском слове шаблона не видна никогда — ни на кадре, ни в
ревью, а поиск по странице с ней не работает.

## 6. Матрица: три ширины и данные, которые ломают вёрстку

Страница проверяется не один раз, а по комбинациям — цена комбинации одна
команда:

- **ширины**: узкая мобильная (`360,800`), планшет (`768,1024`), широкая
  (`1440,900`). Вёрстка, собранная на одной ширине, ломается на остальных
  двух — это не «редкий случай», это норма для сгенерированной сетки. Узкая
  проверяется **кадром и пиксельными замерами** (`image_scan`,
  `image_layout`): числа зонда там врут — см. потолок 500 px в § 3.
- **данные**: пусто, одна запись, много записей, очень длинная строка без
  пробелов, отсутствующая картинка, состояние ошибки и загрузки. Чем состояние
  подаётся — зависит от того, кто мерит: кадру (`web_shot`) — `--inject-js`,
  скрипт перед `</body>`: класс, атрибут, открытый попап; числам (`web_probe`) —
  `--seed-js`, посев `localStorage` в `<head>`, до скриптов страницы. Кадр
  состояния, которое страница читает на старте, снимается с seed-страницы
  (`pdf_seed_page(имя, storage)` — пишет хранилище и переходит на страницу) или
  прогоном `web_drive`. Два слота и их порядок — `web_shot.md`, § 3, § 5 и
  грабля 8.
- **тема**: если тёмная есть — отдельный прогон, а не «там те же отступы».

Кадры сводятся в один лист для человеческого взгляда:

```bash
python -m image_.image_frames grid /tmp/ui/w360.png /tmp/ui/w768.png /tmp/ui/w1440.png \
    --out /tmp/ui/sheet.png --cols 3 --scale 0.5
```

## 7. Живая страница: снимок не отвечает за динамику

Под `virtual-time-budget` асинхронные цепочки не наступают: `FileReader` и
`Image.onload` не стреляют никогда (`web_shot.md`, грабля 5). Поэтому:

| Что проверяется | Чем |
|-----------------|-----|
| разметка и геометрия в покое | `web_shot`, `web_probe` |
| поведение: клик, подача файла, асинхронная догрузка, консоль | `web_drive` (CDP, `--shot` даёт кадр после прогона) |
| логика инлайн-скрипта без браузера | `web_unit` (код возврата 1 — есть провалы) |
| страница за формой входа, долгая сессия | `browser_` — `browser_page.md` |
| страница панели, которой нет отдельным файлом | `uvicorn_mirror` — копия как исток для probe/shot |

Консоль читается всегда: `web_drive` собирает `console`, исключения и
`Log.entryAdded`. Красная ошибка в консоли при внешне целой странице означает,
что часть обработчиков не навесилась, — кадр этого не покажет.

## 8. Данные, а не только пиксели

Идеальный кадр рисует и страница, которая вместо данных показывает
захардкоженную заглушку. Ключи ответа ручки против ключей, которые читает JS:

```bash
PYTHONPATH=. python -m page_.page_contract --router routes.py --js static/page.js
```

Мёртвое поле (сервер отдаёт — никто не читает) и невзятый ключ (страница ждёт —
сервер не отдаёт) — оба немые: на кадре пусто там, где должно быть значение.

## 9. Зрение модели — последний судья

`ai.ai_vision describe` отвечает на то, что числами не ловится: «иерархия
сломана», «кнопка не выглядит кнопкой», «блоки не связаны в группы». И не
отвечает на «сколько пикселей» — в координатах и мелких деталях vision-модель
уверенно врёт (`vision_llm.md`). Порядок: сначала § 3–5, потом взгляд, и
каждое утверждение модели про размер или положение перепроверяется зондом.

## 10. Чек-лист перед «готово»

1. Кадр снят **после** последней правки, а не после предпоследней.
2. `before`/`after` сравнены — задетого соседнего блока нет.
3. `--rect` по ключевым узлам: ни одного `None`, ни одной нулевой ширины.
4. Число нарисованных элементов = числу записей в данных.
5. Зонд «вылезло за край»: `page` = 0, список пуст.
6. Зонд «не поместилось»: `clipped: true` — только там, где обрезка задумана.
7. Координаты ряда: `x` совпадают, `h` совпадают, отступы кратны шагу шкалы.
8. Три ширины сняты, лист собран, состояния «пусто» и «длинная строка» есть.
9. `image_ literals` — палитра не расползлась; `image_ seam` — швов нет.
10. Консоль чистая (`web_drive`), `tool_typo` молчит.

Пункт, который нечем закрыть, называется вслух: «контраст не проверял», а не
молча пропускается.

## Грабли

1. **«Проверил в голове»** — рендера никто не видел; самый частый способ сдать
   кривую страницу, и единственный, который не оставляет следов.
2. **Кадр только в конце** — непонятно, какая из правок сломала соседний блок;
   откат превращается в отдельное расследование.
3. **Одна ширина** — сетка, собранная на широкой, на мобильной даёт
   горизонтальный скролл; на кадре широкой это невидимо.
4. **Зонд на мобильной ширине** — `web_probe`/`web_drive` поднимают окно до
   500 px и отдают числа от него: запрошенные 390 приходят как 500, молча и
   правдоподобно. `web_shot` при этом кладёт честные 390 — кадр и зонд на узкой
   ширине расходятся, и прав кадр.
5. **Скроллбар и середина анимации** — вьюпорт «съезжает» на 15 px, а
   полупрозрачный слой врёт тоном 233 вместо 255: `--hide-scrollbars` встроен,
   `--budget` задаётся осознанно (`web_shot.md`, § 2 и § 4).
6. **`file://` без ассетов** — страница снята без картинок и шрифтов, метрики
   строк неверны; локальный HTML отдаётся раздачей, она встроена.
7. **Зонд вместо снимка и снимок вместо зонда** — DOM не знает про тон и швы,
   пиксели не знают про `scrollWidth`; нужны оба круга.
8. **Виртуальное время съело асинхронию** — пустой виджет на кадре означает не
   «сломано», а «`web_shot` не дождался»; проверять `web_drive`.
9. **Замер по среднему цвету** — фон меряется модой; среднее тянут карточки и
   текст (`image_tooling.md`, § 1).
10. **Vision-модель как измеритель** — «кнопка примерно по центру» от неё
   приходит уверенно и неверно; числа берутся зондом.
11. **Кадры остались в репозитории** — доказательство на час превращается в
    мусор навсегда; место кадрам во временном каталоге.
