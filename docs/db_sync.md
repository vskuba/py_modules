# Db sync — сверка баз, репетиция миграции, сборка SQL

> Правка едет из рабочей базы на прод через миграцию, и на этом пути четыре места, где
> тихо теряется смысл: автономера у баз свои, сличения разные, длинный текст рвётся при
> склейке, а «выкладка удалась» не значит «код на проде». Четыре модуля отвечают на эти
> вопросы поимённо; каждый вырос из поломки, а не из замысла.

## 1. Вопросы и кто на них отвечает

| Вопрос | Чем |
|--------|-----|
| чем рабочая база отличается от прода | `mysql_.mysql_snapshot` |
| переживёт ли миграция боевые данные и второй прогон | `mysql_.mysql_rehearse` |
| не упадёт ли запрос на разных сличениях | `mysql_.mysql_collate` |
| как положить длинный текст в SQL и ничего не слепить | `sql_.sql_build` |
| доехал ли коммит до прода | `deploy_.deploy_wait` |

## 2. ⚠⚠ Автономера: главная ловушка сверки

`id` у баз свои. Строки, одинаковые по смыслу, отличаются каждым числом — и наивное
сравнение показывает «различается всё». Хуже, когда номер лежит **внутри** значения:

    %qdrant_fact_search_676_result_str%     ← 676 это шаг ПРОДА
    "transitions_after": [{"step_id": "633"}]

Такая ссылка после переноса ведёт в пустоту, и это самая тихая из поломок: переменной
нет — секция промпта просто исчезает, ответ выглядит обычным.

`mysql_snapshot` сравнивает **по ключу** (`name`, `workflow_id,position`), а ссылки
приводит к тому же ключу — их описывают `--ref`. Замер на живой задаче: 23 «различия»
без него и 2 настоящих с ним.

⚠ Видов ссылок обычно несколько, и найти их можно только по остатку: прогнать без
`--ref`, посмотреть, чем отличаются строки, добавить по выражению на каждый вид.

## 3. ⚠ Репетиция: второй прогон обязателен

Миграции применяются повторно чаще, чем кажется — восстановление базы, второй контур,
случайный перезапуск. Неидемпотентная либо падает, либо тихо удваивает сделанное.

`mysql_rehearse` снимает срез прода, поднимает копию, применяет **дважды** и сравнивает
выводы. Совпадение — признак, а не доказательство (миграция может печатать одно, а делать
разное), но расхождение означает беду всегда.

⚠ Таблицы выводятся сами по внешним ключам: без родительских заливка падает на
`Cannot add or update a child row`, без справочников `*_type` — на вставке.

## 4. ⚠⚠ Сличения: ошибка, которая ждёт третьей базы

`utf8mb4_0900_ai_ci` на проде против `utf8mb4_general_ci` в рабочей — и запрос, годный
там, здесь падает:

    ERROR 1267: Illegal mix of collations

Три места, где это ломается: сравнение столбца с `CONCAT(…, @переменная)`, временная
таблица (берёт сличение **базы**, а не источника), `UNION` таблиц разного возраста.

⚠ **Чинить `COLLATE`-ом в миграции нельзя**: имя подойдёт ровно одной базе, а миграция
едет во все. Годные способы — сравнивать числом (у чисел сличения нет) или держать
переменную только для сборки строки, не для сравнения.

## 5. ⚠ Длинный текст в SQL

Подстановка `%s` не годится: миграция это **файл**, который выполнят потом. Значение
кладётся в текст, и там его ждут кавычки, слэши, переносы, `NULL` против пустой строки.

`sql_build` кладёт длинное через `FROM_BASE64` — в нём нет ни кавычек, ни переносов, — и
делает **по присваиванию на поле**. Цена вопроса измерена: самодельная склейка через
`CONCAT_WS('\x1e', …)` испортила девять записей разом, MySQL принял `\x1e` за текст
«x1e», и все поля слиплись в первое.

## 6. ⚠ «Выкладка удалась» ≠ «код на проде»

Между зелёной галочкой CI и перезапущенным процессом проходят секунды, иногда минуты. В
эти минуты всякая проверка отвечает про **старый** код, и рождается вывод «правка не
работает» — с последующей починкой уже починенного.

Различить по времени нельзя: метки прода в его поясе, твои часы в своём. Только по
коммиту. `deploy_wait_landed` спрашивает не CI, а сам сервер.

⚠ У `deploy_wait_run` довод `--workflow` почти обязателен: на толчок отвечают несколько
процессов, и «последний» — обычно короткое уведомление, которое кончается первым. Кусок
имени должен **различать**: `deploy` находит и «Deploy to Oracle Cloud», и «On Deploy
Status».
