# Порт как предмет: свободен ли и дождаться, пока займёт

> «Поднял сервис» и «сервис готов» — разные утверждения, и второе всегда
> про порт. Проверить порт глазами нельзя, а цикл `while ! nc -z` в каждом
> скрипте не пишется только по лени. Одна попыка TCP-соединения на половину
> секунды отвечает на вопрос точнее, чем `ss` без прав.

## 1. Сейчас

```python
from net_.net_port import net_port_free

net_port_free(8790)            # False — кто-то принимает
net_port_free(54321)           # True  — подключиться не к кому
```

## 2. Когда будет

```python
from net_.net_port import net_port_wait

net_port_wait(8080, timeout=30)          # дождаться занятия: True/False
net_port_wait(8080, up=False)            # дождаться освобождения (рестарт)
```

Возвращает **признак**, не исключение: не дождаться — обычный ответ сторожа.

```bash
PYTHONPATH=. python -m net_.net_port free 8790          # rc 0 — свободен, 1 — занят
PYTHONPATH=. python -m net_.net_port wait 8080 --timeout 60
PYTHONPATH=. python -m net_.net_port wait 8080 --down   # дождаться, что погас
```

## Грабли

1. **`up` значит «кто-то принимает TCP», а не «сервис здоров»**: процесс,
   висящий на полпути к готовности (прогрев модели, миграция БД), порт уже
   держит — за здоровьем идут по своему ручному признаку (`/health`).
2. **Свободен ≠ никому не доступен**: `net_port_free` смотрит с указанного
   `host` (петля по умолчанию). Порт, закрытый файрволом для внешних, с
   петли выглядит занятым чужим — смотреть надо с той стороны, откуда
   будут ходить.
3. **Висящий listener** (принимает, но не дописывает ответ) — попыка
   коннекта висит до таймаута и считается... коннектом: порт занят. Это
   правильно, но объясняет, почему `free` может тянуться целую секунду там,
   где ожидаешь мгновенного ответа.
4. **Занятый порт чужим процессом — тоже «свободен быть не может»**, но
   владельца модуль не называет нарочно: `ss -tlnp` требует прав и
   парсинга, а решение «порт занят, это кто» обычно принимает человек.
