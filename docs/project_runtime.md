# Project runtime — чем запускать код в проекте и чем спрашивать его базу

> Разовое действие в чужом проекте упирается не в код, а в окружение: где корень, каким
> интерпретатором, что в `PYTHONPATH`, по какому адресу база и где её пароль. Обычный ответ —
> длинная составная команда `cd … && .venv/bin/python - <<'EOF'` и `docker exec … mysql -p…`;
> она хрупкая, теряет код возврата и светит пароль. Модули `project_` и `mysql_` отвечают на
> эти вопросы один раз, и дальше разовый прогон — одна короткая команда.

## 1. Вопросы окружения и кто на них отвечает

| Вопрос | Отвечает | Чем плох ответ руками |
|--------|----------|----------------------|
| где корень проекта | `project_root()` | рабочий каталог процесса корнем не является: агент роли стартует в выкладке |
| где корень **основной** выкладки | `project_main_root()` | внешние системы помнят проект по каталогу, и из выкладки этот каталог другой |
| каким интерпретатором | `project_python()` | системный Python не видит зависимостей проекта, импорт падает |
| что в `PYTHONPATH` | `project_env()` | без общего слоя библиотек не импортируется ничего из него |
| как выполнить код | `project_run_python()` | heredoc ломается на кавычках, не имеет таймаута и глушит код возврата |
| какой адрес базы рабочий | `mysql_host_address()` | изнутри сети контейнеров и снаружи адрес разный |
| как спросить базу | `mysql_query_run()` | пароль в командной строке виден в списке процессов, вывод — псевдографика |

Зависимость между ними односторонняя: `mysql_` спрашивает каталог у `project_`, обратной
связи нет. Поэтому `project_` работает и там, где базы нет вовсе.

## 2. Проверка окружения — раньше, чем писать код

```bash
python <общий слой>/project_/project_.py root      # корень проекта
python <общий слой>/project_/project_.py python    # чем запускать
python <общий слой>/mysql_/mysql_query.py address  # адрес базы, имя базы, пользователь
```

Первые две команды не требуют ни зависимостей, ни настроек — только стандартную библиотеку;
они отвечают всегда, даже в пустом окружении. Третья уже читает настройки проекта и щупает
связь: она и есть проверка, что база вообще доступна отсюда.

Ответ `root` совпал с рабочим каталогом — обычная копия; отличается — выкладка (`worktree`),
и дальше важно, какой из двух корней спрашивать (см. § 4 и «Грабли» № 5).

## 3. Способы выполнить код — выбирать по задаче

| Задача | Чем | Почему |
|--------|-----|--------|
| выражение в одну-две строки | `project_run.py -c '…'` | без файла и без временных путей |
| то же, но с `await` | `project_run.py -a '…'` | обёртка `asyncio.run` дописывается сама |
| готовый файл | `project_run.py <файл> [аргументы]` | тот же интерпретатор и путь, что у проекта |
| модуль или тесты | `project_run.py -m <модуль> [аргументы]` | точка входа модуля в окружении проекта |
| длинный код | `project_run.py -` | текст со стандартного входа: кавычки оболочки не участвуют |
| прогон из своего кода | `project_run_python(...)` | возвращает код возврата, а не текст |

Таймаут стоит **по умолчанию**, а не по желанию: разовый прогон, который завис, иначе
держит вызывающего вечно. Снятый по таймауту процесс отдаёт код `124` — тот же, что у
системной утилиты `timeout`, чтобы вызывающему не пришлось запоминать особое число.

## 4. Инструменты этого репозитория

### `project_` — окружение (файл `project_/project_.py`)

| Функция | Контракт |
|---------|----------|
| `project_root() -> Path` | корень проекта; для выкладки — корень самой выкладки |
| `project_main_root() -> Path` | корень основной выкладки, один на проект и все его выкладки; вне git — то же, что `project_root()` |
| `project_python() -> Path` | интерпретатор: активное окружение, затем `.venv`/`venv` корня, затем `.venv` основной выкладки, затем текущий |
| `project_env(extra=None) -> dict` | копия окружения с `PYTHONPATH` из корня и общего слоя библиотек |

```bash
python <общий слой>/project_/project_.py {root|main-root|python|env}
```

Корень вычисляется **от положения самого файла**, а не от рабочего каталога и не от git:
модуль лежит в общем слое внутри проекта, и до корня от него всегда одинаковое число шагов.
Поэтому ответ не зависит от того, откуда процесс запущен, — а рабочий каталог у агента
почти никогда не совпадает с корнем.

Два корня различаются только в выкладке, и различие не косметическое: всё, что помнит
проект **по каталогу** (оркестратор контейнеров — в первую очередь), знает лишь основную.
Правило простое: своё — от `project_root()`, чужое — от `project_main_root()`.

### `project_run` — разовый прогон (файл `project_/project_run.py`)

| Функция | Контракт |
|---------|----------|
| `project_run_python(source='', path='', module='', argv=None, is_async=False, timeout=0) -> int` | ровно один источник из трёх; возвращает код возврата, `124` — снят по таймауту |

```bash
python <общий слой>/project_/project_run.py -c 'print(1)'
python <общий слой>/project_/project_run.py -a 'print(await coro())'
python <общий слой>/project_/project_run.py -m <модуль> -- --флаг-модулю
echo 'print(1)' | python <общий слой>/project_/project_run.py -
```

Вывод не перехватывается: дочерний процесс пишет прямо в тот же поток, поэтому длинный
прогон видно по мере выполнения, а не одной простынёй в конце.

### `mysql_host` — адрес базы (файл `mysql_/mysql_host.py`)

| Функция | Контракт |
|---------|----------|
| `mysql_host_address(timeout=2.0) -> tuple` | `(хост, порт)`: адрес из настроек, если отвечает, иначе петля и опубликованный наружу порт |
| `mysql_host_container() -> str` | имя контейнера базы этого проекта или пустая строка |

Контейнер ищется **по каталогу проекта** — по метке, которую оркестратор ставит сам, — а не
по имени. Имена у проектов свои, а баз на машине несколько: угадывание по имени рано или
поздно приводит в чужую базу, и заметно это будет уже после записи. Каталог берётся у
основной выкладки, поэтому из выкладки поиск тоже находит контейнер.

### `mysql_query` — запрос (файл `mysql_/mysql_query.py`)

| Функция | Контракт |
|---------|----------|
| `mysql_query_run(sql, params=(), limit=0) -> dict` | `{'columns': [...], 'rows': [{колонка: значение}], 'affected': N}` |
| `mysql_query_read_only(sql) -> bool` | меняет ли запрос данные — по первому слову |
| `mysql_query_format(result, style='table') -> str` | `table` человеку, `json` коду, `csv` в конвейер |

```bash
python <общий слой>/mysql_/mysql_query.py address
python <общий слой>/mysql_/mysql_query.py tables
python <общий слой>/mysql_/mysql_query.py columns <таблица>
python <общий слой>/mysql_/mysql_query.py sql 'select … limit 10' [--format json|csv] [--limit N]
python <общий слой>/mysql_/mysql_query.py sql '<запрос, меняющий данные>' --write
```

Учётные данные берутся из настроек проекта и уезжают в драйвер параметрами соединения —
в командной строке их нет, и в списке процессов они не видны. Запрос, меняющий данные,
без `--write` отвергается до соединения: разовый прогон по природе своей делается наспех,
и опечатка в нём стоит дороже лишнего слова в команде.

## 5. Чек-лист «сделать разовое действие в проекте»

1. `project_.py root` — тот ли проект, и не выкладка ли это.
2. Код — через `project_run.py`, а не составной командой с `cd` и heredoc.
3. Кода больше пяти строк — отдать через стандартный вход (`-`), а не в кавычках.
4. База — `mysql_query.py address`; не ответил — поднят ли оркестратор, вопрос не к модулю.
5. Читающий запрос — сразу с `limit`: разовый прогон легко вытаскивает миллион строк себе в вывод.
6. Меняющий запрос — сначала тем же условием в `select`, и только потом с `--write`.

## Грабли

1. **`ModuleNotFoundError` на первом же импорте, хотя файл запущен из корня проекта** —
   запуск файла модуля напрямую по пути кладёт в путь поиска **его каталог**, а не корень
   проекта, и общий слой библиотек становится невидимым. Запускать такие модули через
   `project_run.py -m <модуль>`: он и собирает `PYTHONPATH`. Точки входа, которые обязаны
   работать самостоятельно, чинят себе путь поиска сами, первыми строками.
2. **Ключ, написанный после цели, уходит не тому, кому предназначался** — у разбора
   аргументов позиционная цель забирает своё раньше остатка, поэтому `-m <модуль> --флаг`
   заканчивается жалобой самого запускателя на незнакомый ключ. Разделитель `--` отдаёт
   всё, что за ним, дочерней программе: `-m <модуль> -- --флаг`.
3. **Составная команда с `cd` и heredoc ломается на кавычках** — код с апострофами и
   `$` внутри одинарных кавычек оболочки не живёт, а экранирование множится с каждым
   уровнем. Стандартный вход (`-`) снимает вопрос целиком: оболочка текст не разбирает.
4. **Прогон «прошёл», хотя код упал** — составная команда возвращает статус последнего
   звена, и ошибка внутри теряется. `project_run_python()` возвращает код возврата
   дочернего процесса, а `124` отличает падение от снятия по таймауту.
5. **Из выкладки оркестратор отвечает «сервис не запущен», хотя контейнер работает** —
   проект он помнит по каталогу, где его подняли, и каталог выкладки для него чужой.
   Спрашивать `project_main_root()`; поиск контейнера по метке каталога так и сделан.
6. **Адрес базы из настроек не отвечает с машины разработчика** — это не поломка: настройки
   описывают базу так, как её видит приложение **внутри** сети контейнеров. Снаружи тот же
   порт опубликован другим номером; `mysql_host_address()` пробует оба по очереди.
7. **Пароль в командной строке** — виден всем в списке процессов и оседает в истории
   оболочки. Ходить в базу через модуль, а не через клиент оркестратора с ключом пароля.
8. **Вывод запроса не разобрать машинно** — псевдографика клиента для этого и не
   предназначена. `--format json` даёт разбираемый ответ, `--format csv` — конвейерный.
