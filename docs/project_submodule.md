# Указатель py_modules: state и bump без воровства чужой линии

> Два чекаута одного репозитория расходятся молча: gitlink указывает на старый
> кончик, правка уехала в другой каталог, панель крутится без свежей строки и
> молчит. `project_submodule_state()` называет gitlink, кончик чекаута, родство
> линий и список файлов между ними; `project_submodule_bump()` fetch'ит линию из
> второго чекаута, вливает неслитое через временную ветку и оставляет кончик на
> объединении. Инструмент — `py_modules/project_/project_submodule.py`,
> CLI: `python -m project_.project_submodule state|bump [--line] [--from]`.

## 1. Почему два чекаута — это две линии

`py_modules` живёт в двух каталогах как один репозиторий: самостоятельная
выкладка (там правят общий слой) и submodule `<корень>/проекта` (там его читает
панель). Коммит правки в одном чекауте не двигает указатель в другом; пока
человек не вспомнил про `git add py_modules`, панель крутится на старом
кончике. Симптом всегда один и тот же: «правка есть в файле, а панель её не
видит» — и это не баг панели, а расхождение линии с gitlink.

Отсюда два правила. Правку общего слоя коммитят в том чекауте, где правят, и
тут же доводят указатель проекта до нового кончика. Проверку «указатель ==
кончик» делают инструментом, а не глазом: у detached HEAD вопроса «чего не
хватает» не существует.

## 2. `project_submodule_state` — что и как расходится

```python
project_submodule_state() -> {'gitlink', 'checkout', 'synced', 'ancestor', 'files'}
```

`gitlink` — sha из дерева проекта (`ls-tree HEAD py_modules`); вне submodule-
контекста его нет, и это факт, а не ошибка. `ancestor` — gitlink предок
чекаута: линия проекта уже внутри общей. `files` — `diff --stat` между линиями:
что именно приедет в панель при bump. Ровно этот список человек и хочет
увидеть словами, а не списком объектов git.

## 3. `project_submodule_bump` — танец слияния, а не переезд

```python
project_submodule_bump(line='master', from_repo='/путь/второго/чекаута') ->
    {'sha', 'merged', 'files'}
```

Порядок, который модуль делает сам: цель из `--from` (та же ветка там, где
правка) забирается fetch'ем; если HEAD чекаута не предок цели, HEAD вливается
в `<line>` слиянием через временную ветку — объединение, а не переезд; кончик
остаётся на слиянии. `merged: true` — значит линия чекаута была неслитой и её
не украли; `files` — что это дало проекту. Коммит указателя (`git add
py_modules`, сообщение) — дело того, кто коммитит: модуль называет sha, не
коммитит.

Bump без слияния — это переезд: панель теряет всё, что было наведено во втором
чекауте, и теряет молча. Именно поэтому `state` до правки показывает `files`
между линиями, а `bump` сам делает merge.

### ⚠⚠ Голый `--line master` целится в **локальную** ветку, а она в подмодуле мёртвая

`master` без `--from` разрешается в чекауте подмодуля, а там локальные ветки
**устаревшие по природе**: подмодуль живёт отсоединённым (`HEAD` на sha, не на
ветке), и `master` в нём остаётся там, где его оставил `clone`. Никто его не
двигает, потому что никто им не пользуется.

Выглядит это как ложь инструмента, и распознаётся не сразу:

```bash
python -m project_.project_submodule bump --line master
{'sha': 'aabe1d5…', 'merged': true, 'files': []}     # ← тот же sha, что был
```

Ответ правдив целиком: цель (`master` = `f7bb61c`) оказалась **предком** текущего
кончика, слияние устаревшей линии честно вернуло кончик на место. Неверна была
цель, а не ответ. Измерено 06.10.2026 на claude-shell: пин стоял на 30 коммитов
позади, а `--line master` трижды подряд «успешно» не сдвинул ничего.

Цель называют одним из двух способов — оба показывают на живую линию:

```bash
git -C py_modules fetch origin                     # сперва освежить
python -m project_.project_submodule bump --line origin/master
python -m project_.project_submodule bump --line master --from ~/PycharmProjects/py_modules
```

⚠ Проверка на месте, одной строкой: если `sha` в ответе равен прежнему `checkout`
из `state`, bump не сдвинул ничего — независимо от того, что говорит `merged`.

## 3.1 ⚠⚠ Конфликт слияния разрешает человек — инструмент возвращает чекаут

Слить само можно только то, что не спорит. Две осмысленные правки одного места —
это выбор, и сделать его может лишь тот, кто знает, зачем они сделаны.

Поэтому `bump` на конфликте **отказывается словами** и возвращает чекаут ровно
туда, где человек стоял: прерванное слияние отменяется, HEAD встаёт обратно на
его линию, временная ветка убирается.

```
ошибка: линии разошлись содержанием, слить само не вышло — спорят: conf.txt.
        Чекаут возвращён на прежнюю линию, ничего не потеряно.
        Разрешать руками: cd <чекаут> && git merge master
```

⚠ **Прежде он бросал `CalledProcessError` посреди слияния.** Чекаут оставался с
конфликтом в дереве, на чужом коммите и с висящей `_psm-tmp`, а человек видел
`Command '[...]' returned non-zero exit status 128` — ни что случилось, ни где
теперь его линия. Хуже того, хвост ломал **следующий** заход: `branch` на
занятое имя падал, и причина выглядела совсем иной. Измерено на живом
расхождении DatingAi ↔ RhapsodyAi 01.10.2026; пострадавший чекаут PersonaAI
стоял на коммите чужого репозитория.

⚠ Перед работой инструмент снимает хвост прошлой неудачи сам — заход после
аварии больше не упирается в занятое имя ветки.

### `--from` принимает корень проекта, а не только путь к слою

«Возьми линию из DatingAi» — естественная формулировка, и держать в голове
`…/DatingAi/py_modules` человек не обязан. Инструмент сам спускается в подпапку
слоя, если она там есть; прямой путь к чекауту тоже работает.

⚠⚠ **Прежде корень проекта молча ломал весь танец.** `fetch` тянул линию
**самого проекта**, приезжала чужая история — и дальше:
`merge-base --is-ancestor` отвечал «не предок» даже у совпавших линий,
а слияние упиралось в `refusing to merge unrelated histories`. Снаружи это
выглядело как «линии разошлись» там, где они одинаковы, и чекаут при этом
уезжал на коммит чужого репозитория.

Признак, по которому это узнаётся в отказе: спорящих файлов **нет**. Конфликт
содержания всегда называет хотя бы один файл; пустой список значит, что
слияние не началось вовсе.

## Грабли

- **`git fetch <путь> <sha>` не берёт sha** — только имя ссылки. Модуль fetch'ит
  ту же ветку из чужого чекаута; sha-цель передают уже существующей меткой.
- **указатель правят в том же изменении, что и правку** — пережил один
  «потом добавлю»: «потом» не наступает, а панель между двумя линями не видит
  ни одной правки.
- **`ls-tree` отвечает и вне submodule-контекста** (обычная запись дерева) —
    поэтому пустой `gitlink` в standalone-чекауте отличают по признаку «проекта
    надо мной нет», а не по пустому выводу.
- **pre-push hook проекта** не пускает указатель, которого нет в origin общей
    линии: перед пушем проекта кончик должен быть запущен в origin, а не только
    лежать в локальном объекте.
