# Mobile device — как смотреть на телефон и что для этого нужно

> Телефон подключается по USB и смотрятся **два независимых глаза**: `scrcpy` — живая
> картинка человеку, `adb` + vision-модель — «что на экране» для кода. Модули `adb_` и
> `ai/ai_vision` лежат в этом репозитории; один вызов `adb_screen_describe()` возвращает
> текстовое описание текущего экрана.
>
> Здесь — только **смотреть**. Нажимать, вводить и запускать — `mobile_control.md`;
> там же карта экрана `adb_ui`, которая для кода почти всегда точнее зрения. Мелкое на
> целом снимке не читается — его ужимает уже читатель; вырезка в натуральную величину —
> `mobile_steps.md`, § 4.

## 1. Средства и их роли

| Средство | Роль | Кто им смотрит |
|----------|------|----------------|
| `adb` (android-tools) | единственная связь с устройством из кода: перечень, снимок экрана, Shell | код и модули |
| `scrcpy` | живое зеркало экрана с управлением клавиатурой и мышью, без рута и серверов на телефоне | человек |
| vision-модель | превращает кадр экрана в текст | код через `ai_vision` |

Нужное стоит один раз: `adb` и `scrcpy` ставятся в систему (`apt install adb scrcpy`
или эквивалент). Python-зависимости минимальны: `Pillow` — уже есть почти везде,
`pydantic-ai` — только там, где действительно обращаются к модели (см. § 4).

Устройство должно быть подключено с **разблокированным USB-отладчиком**; на первом
подключении телефон спрашивает разрешение — без согласия список устройств пустой,
и это не поломка кода.

## 2. Проверка связи — раньше, чем смотреть код

```bash
adb devices                        # список: серийник + состояние
python -m adb_.adb_ devices       # то же средствами модуля
scrcpy                            # живое окно на одно подключённое устройство
```

`adb devices` пустой — искать не в Python, а в физическом мире: кабель (некоторые
«только заряжают»), переключатель USB-отладки, не принято ли разрешение на экране
телефона. `unauthorized` в списке — то же разрешение, но отклонённое.

## 3. Способы посмотреть — выбирать по задаче

| Задача | Чем | Почему |
|--------|-----|--------|
| посмотреть и потыкать руками | `scrcpy` | интерактивно, без задержки на модель |
| отдать кадр в код (diff, сохранение, второй проход) | `adb_capture()` | байты JPEG без альфы, готовые к отправке |
| сохранить доказательство момента | `adb_capture_save(path)` | файл переживёт смену экрана |
| получить текстовое «что на экране» | `adb_screen_describe()` | снимок + модель одним вызовом |
| узнать, что на экране, **чтобы туда нажать** | `adb_ui_text()` (`mobile_control.md`) | надписи с точными координатами; модель координат не знает |

Последняя строка важнее, чем кажется: у зрения и карты разные ответы. Модель честно
опишет кнопку, но её место назовёт примерно — и нажатие уйдёт мимо. Зрение остаётся для
экранов, нарисованных одним полотном (Canvas, WebView): там текста в дереве нет.

Экран живёт своей жизнью: между снимком и ответом модели пользователь мог увести
телефон в другое приложение. Нужен воспроизводимый разбор — сохранить кадр
`adb_capture_save()` и описывать уже файл, а не живой экран.

## 4. Инструменты этого репозитория

### `adb_` — устройство (файл `adb_/adb_.py`)

| Функция | Контракт |
|---------|----------|
| `adb_devices() -> list[str]` | серийники подключённых устройств |
| `adb_capture(serial='', max_side=0) -> bytes` | кадр экрана сразу в JPEG без альфы; `max_side` — уменьшить длинную сторону |
| `adb_capture_save(path, serial='') -> str` | тот же кадр в файл, возвращает путь |
| `adb_screen_size(serial='') -> tuple[int, int]` | ширина и высота экрана в пикселях — от неё считаются доли в жестах |
| `adb_device_info(serial='') -> dict` | паспорт: модель, Android, SDK, разрешение, плотность — снимать живьём, не помнить (`mobile_hardware.md`) |
| `adb_screen_describe(prompt='', serial='', model_name='') -> str` | «увидеть экран»: снимок + `ai_vision_describe_wait` |

Соседние модули пакета (`adb_ui`, `adb_input`, `adb_app`, `adb_log`) отличаются командой,
а не способом её звать: общий запуск `adb` и разбор ошибок живут здесь. Что они делают —
`mobile_control.md`.

CLI для ручной проверки без обёрток:

```bash
python -m adb_.adb_ devices
python -m adb_.adb_ info
python -m adb_.adb_ capture --out /tmp/screen.jpg
python -m adb_.adb_ describe ["вопрос про экран"] [--serial ...] [--model ...]
```

Модуль ленив к LLM-стеку сознательно: снимок (`adb_capture`) работает в тощем
окружении, где нет `pydantic-ai`, — только `describe` подтягивает его при обращении
к модели. Пустой `prompt` описывает экран подробно, короткий вопрос — отвечать
коротко; формулировать вопрос дешевле, чем фильтровать простыню.

### `ai/ai_vision` — зрение (файл `ai/ai_vision.py`)

| Функция | Контракт |
|---------|----------|
| `ai_vision_normalize(image, max_side=1600) -> bytes` | любой читаемый Pillow картинку — в JPEG без альфы |
| `ai_vision_describe(image, ...) -> str` (async) | описание кадра моделью; адрес и ключ — из реестра провайдеров (`llm_rules.md`) |
| `ai_vision_describe_wait(...) -> str` | синхронная обёртка |

CLI — для картинки с диска, не с телефона (снимок из буфера, схема, чужой скриншот):

```bash
python -m ai.ai_vision describe [--model ...] [--tokens N] <файл> ["вопрос"]
python -m ai.ai_vision normalize <файл> --out <файл.jpg>
```

Ключи идут **до** пути, вопрос — последним: между позиционными аргументами разбор ключи не
принимает. `normalize` без обращения к модели полезен отдельно — им проверяют догадку
«сервер отверг картинку из-за формата», не тратя ход модели.

Как устроен сам запрос к модели со зрением — контракт `data:`-URI, цена кадра в
токенах и места, где модель уверенно врёт, — `vision_llm.md`.

Модель — из настройки `AI_VISION_MODEL_NAME` (или параметром `model_name=`) с
префиксом сервиса, адрес берётся у стратегии провайдера, не хардкодится.
`max_tokens=2500` по умолчанию — потолок **ответа в запросе**; контекст сервера
многократно больше, подробный разбор целого экрана в тесный потолок не влезает,
а конкретный вызов можно поднять параметром.

## 5. Чек-лист «посмотреть телефон»

1. `adb devices` — устройство в списке и без `unauthorized`.
2. Выбрать способ из таблицы § 3; для кода — `adb_screen_describe()`.
3. Ключ модели должен быть в окружении (настройка сервиса из `.env`); без него
   `describe` падает на пустом `Authorization` — это про окружение, не про модуль.
4. Ответ не похож на экран — сохранить кадр `adb_capture_save()` и проверить его
   вторым вызовом: отличие кадра от галлюцинации в том, что кадр не меняется.

## Грабли

1. **`400 Failed to load image or audio file` от локального mtmd-сервера** — картинка
   пришла с альфа-каналом или в WebP: сервер их декодировать не умеет. `screencap`
   отдаёт RGBA-PNG, а GUI-обёртки дорого перекладывают скриншоты в WebP. Все кадры
   идут через `ai_vision_normalize()` — он приводит к RGB-JPEG; сам снимок для этого
   и возвращается уже нормализованным.
2. **`400 Failed to tokenize prompt` на следующем ходе после безобидного запроса** —
   в историю conversation попал сырой дамп серверного устройства (вывод `/props`,
   чат-шаблон, сервисные токены вида `<имя>`), и при пересылке обратно токенизатор
   на нём ломается. Дампы внутренностей сервера не печатать в переписку целиком,
   вытаскивать отдельными полями; уже отравленный обмен — удалить из истории.
3. **Описание обрывается на середине** — потолок `max_tokens` в запросе (по умолчанию
   2500) меньше, чем экран; поднять параметром конкретного вызова. Это потолок ответа,
   не ограничение сервера: контекст сервера на порядки больше.
4. **Модуль падает на `ModuleNotFoundError: pydantic_ai` в тощем venv** — так и задумано
   для `describe`; но если падает сам `adb_capture`, значит ленивость импорта сломали
   и вернули тяжёлый импорт шапкой модуля.
5. **Кадры некоторых приложений — чёрный прямоугольник** — флаг защищённости окна;
   на это нет ни adb-обхода, ни модели. Так ведёт себя экран оплаты и часть банковских
   экранов; проверять связь на рабочем столе, а не на защищённом экране.
6. **Очень короткий ответ на вопрос про экран может схлопнуть детали** — при тесном
   потолке модель теряет часть кадровых деталей; для «перескажи экран» потолок не жалеть.
