# Мост страниц внутри Cordova: один ключ localStorage и сеттеры в `window`

> Страницы вебвью одного приложения делят данные через **один ключ**
> `localStorage` на пакет и через **сеттеры в `window`** (`X_SET`, `X_FILE`)
> для внешнего кода — нативного или соседней страницы. Дефолты материализуются
> в хранилище на первой загрузке, картинки проба размеров отсекает до записи,
> data-URL живёт в том же хранилище — с квотными последствиями.
> Образцы — `data/android/reserve` (`reserveData`, `EVOD_SET`) и
> `data/android/dia` (`diaData`, `DIA_SET_QR`, `DIA_QR_FILE`).

## 1. Один ключ на пакет, чтение — у кого угодно

`localStorage` общий на весь origin приложения: все страницы одного Cordova-
вебвью видят одно и то же значение без нативного кода. Ключ — константой на
странице (`var STORAGE_KEY = 'reserveData'`), набор полей — списком
(`FIELD_KEYS`), чтобы `collect`/`loadData` не разошлись по страницам; имена
полей совпадают между страницами пакета (секрет-меню пишет — карточка читает).
Читатель не должен уметь упасть на мусоре: `JSON.parse` в `try/catch` с
пустым объектом — повреждённое значение не роняет форму, а дефолты добирают
отсутствующее.

## 2. Дефолты материализуются сразу, а не «при чтении»

Дефолт, живущий только в коде страницы-источника, для остальных страниц не
существует, пока кто-то туда не зайдёт. Поэтому первая загрузка формы делает
`persist()` немедленно: хранилище заполнено дефолтами до первой правки, и
читатель получает одинаковые данные в любом порядке открытия страниц.
Пустая строка, сохранённая пользователем, — сохранённое значение: перезапись
дефолтом по `stored[key] != null`, а не по «правде ли», иначе намеренно
очищенное поле воскреснет при следующем открытии.

## 3. Внешний вход: `window.X_SET` / `window.X_FILE`

Нативный код (мост `ReservePdf` в `MainActivity.java`), консоль отладки и
соседняя страница заходят в страницу через именованные сеттеры на `window` —
не через поиск по DOM:

```js
window.DIA_SET_QR = function (url, note) { applyQr(url, note); };  // готовый data-URL
window.DIA_QR_FILE = function (f) { readQrFile(f, applyQr); };     // файл
window.EVOD_SET = function (json) { /* набор полей разом */ };
```

Сеттер проходит тем же путём, что пользовательский ввод (`applyQr` →
`persist`), — включая пробы и замечания: мост не может обойти проверку,
которую нельзя обойти с телефона. Ручной клик по файловому полю из автотеста
автотеста недоступен (нативный диалог не отдаёт файл в headless) — для
прогона тех же путей существует `web_drive` с DataTransfer-подачей файла.

## 4. Картинки: data-URL в общем хранилище и проба размеров

Картинка в `localStorage` — base64-dataURL: квота ~5 МБ на origin, PNG
706×706 — это уже ~1 МБ текста; в пакет с несколькими картинками квота
встаёт ребром — в reserve второй кадр едет как `reserveImages.qr_pdf` отдельным
вложенным объектом, и то только один. Перед записью — проба: dataURL в
`new Image()`, на `onload` сверка `naturalWidth === 706 && naturalHeight === 706`.
Размер не тот — записываем и показываем красное замечание (пользователь может
использовать и чужой кадр — отказывать нельзя), `onerror` («не картинка») —
не записываем вовсе. Тот же `naturalWidth`-пробер становится хуком и в
юнит-прогоне (`web_unit`: заглушка `Image` отвечает размерами на `__image_size(url)`).

## Грабли

1. **`localStorage` не наследуется между webview-процессами** — общий он
   только внутри origin одного приложения; отдельный `CustomTab`/`WebView`
   с другим scheme/хостом видит пустое хранилище.
2. **Квота — молча**: `setItem` переполнение отдаёт исключение, а он у
   образцов обёрнут в `try/catch`; без пробы на длину картинка исчезает из
   хранилища «в никуда» — отсюда проба и один кадр на пакет.
3. **`file://`-значения файловых input фиктивны** (`C:\fakepath`-наследие):
   в хранилище кладём data-URL, а не «путь», иначе читатель получит строку,
   которую нечем открыть.
4. **Дефолт перекрывает ручную очистку**, если сравнивать «пусто ли», а не
   «сохранено ли»: только `!= null` различает «не трогали» и «стёрли сами».
