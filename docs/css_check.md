# CSS check — доедет ли стиль до браузера целиком

> У CSS нет исключений. Сломанный файл не падает: парсер браузера выбрасывает то,
> чего не понял, и идёт дальше. Ни ошибки в консоли, ни записи в журнале, ни
> строчки в devtools — правило просто не применилось. Этот модуль ищет ровно те
> поломки, после которых правила теряются.

## 1. Зачем отдельный инструмент

Сосед — `js_check` (`js_check.md`): тот про браузерный разбор JS, этот про
браузерный разбор CSS. Нужда та же и по той же причине — **молчаливая потеря**.
Разница в том, что JS хотя бы умирает с `SyntaxError` в консоли, а CSS не
сообщает о себе ничем.

Измеренный случай, ради которого модуль написан. Текст комментария уехал за
пределы `/* … */` на одну строку:

```css
   правка в нём меняет все панели экосистемы. */
   ⚠ Потолка ширины нет: сетка городов добирает колонки по месту. */
.data-page { width: 100%; padding: 24px 20px; }
```

Парсер проглотил `.data-page` целиком. Страница встала уже экрана и без
прокрутки, `getComputedStyle` показывал `padding: 0px` при явно заданном
`24px 20px` — и неделю искали не там, в контейнере каркаса.

## 2. Что ищется

| Находка | Чем кончается в браузере |
|---------|--------------------------|
| комментарий не закрыт | съеден весь хвост файла |
| `*/` без начала | хвост комментария читается как код, следующее правило выброшено |
| `{` не закрыта | хвост файла считается телом блока |
| лишняя `}` | блок закрыт дважды, дальше разбор едет со сдвигом |

⚠ **Это не линтер.** Ни про неизвестные свойства, ни про порядок, ни про
вендорные префиксы здесь нет ни слова — для них есть stylelint, и он требует
node и конфига. Здесь одна забота, ноль зависимостей.

## 3. Как звать

```bash
PYTHONPATH=py_modules python3 -m css_.css_check <файл>.css
PYTHONPATH=py_modules python3 -m css_.css_check <каталог>            # обход дерева
PYTHONPATH=py_modules python3 -m css_.css_check <каталог> --pattern '*.css'
```

| Функция | Контракт |
|---------|----------|
| `css_check(path) -> dict` | `{'intact', 'what', 'where', 'chunk', 'rules'}`; у целого `what`/`where`/`chunk` пустые |
| `css_check_tree(root, pattern='*.css') -> list` | ответы **только по сломанным**; пусто — все целы |

⚠ `rules` — сколько блоков разобралось. Полезнее, чем кажется: файл бывает
«целым» и почти пустым, и если правил внезапно вдвое меньше, искать надо в том,
что его собирает, а не в нём самом.

## 4. ⚠⚠ Строки и комментарии разбираются одним проходом

Не по очереди: `content: "/*"` — валидная строка, а `/* "незакрытая кавычка */`
— валидный комментарий. Разбери их двумя проходами, и каждый соврёт на входе
другого. Те же грабли описаны у `sql_split` (`sql_split.md`) — там копия, не
умевшая комментариев, разошлась с умеющей на 136 файлах миграций из 232.

Отсюда же порядок проверок внутри прохода, и он не переставляется:
комментарий сильнее строки (`/* " */` — комментарий), строка сильнее скобок
(`content: "}"` скобку не закрывает).

## 5. Чего модуль намеренно не делает

**Незакрытая строка не считается поломкой файла.** Браузер дочитывает её до
конца строки и выбрасывает одно правило, а не всё остальное; объяви мы сломанным
весь хвост — одна забытая кавычка давала бы ложную тревогу на целом файле.
Поэтому `_css_string_end` выходит и по `\n` тоже.

## 6. Грабли

⚠ **Проверка не заменяет кадр.** Она отвечает на вопрос «доехал ли файл», а не
«то ли человек увидел». Целый CSS с неверной шириной остаётся целым CSS — это
ловится снимком страницы (`web_shot.md`, `uvicorn_mirror`) и замером
`getComputedStyle`, а не здесь.

⚠ Минифицированный CSS проверяется так же, но `chunk` у него бесполезен: вся
простыня лежит одной строкой, и вывод режется по `CSS_CHECK_CHUNK` знакам.
