# Видеоэкран телефона: `screenrecord` с действием посреди записи и разбор на кадры

> Скриншот ловит один миг; переходы между страницами и мелькающие всплески
> снимаются mp4: `adb_rec_record` пишет экран с shell-действием посреди записи,
> `adb_rec_frames` раскладывает готовый файл на PNG-кадры в указанное время,
> `adb_rec_sheet` показывает всю запись одной сеткой, `adb_rec_compare` сводит
> две записи плечом к плечу на одинаковых моментах.
> Инструмент — `py_modules/adb_` (модуль `adb_rec`), CLI: `python -m adb_.adb_rec`.

## 1. mp4 дописывается только в конце

`screenrecord` не отдаёт готовый контейнер, пока пишет: атомарность файла —
`moov`-заголовок дописывается при `SIGINT` или по исчерпании `--time-limit`.
Стянутый раньше файл — битый: ffmpeg его не откроет, и непонятно, запись ли
виновата или pull. Поэтому потолок времени задаётся всегда
(`ADB_REC_LIMIT` = 180 с — аппаратный максимум screenrecord), а `adb pull`
запускается только после того, как процесс adb завершился сам; временный файл
на устройстве удаляется в любом исходе.

## 2. Действие посреди записи и пауза перед ним

Запись стартует не мгновенно: adb-процесс поднимается ~секунду. Тап, отданный
в ту же секунду, что и запись, попадает в тишину до первой рамки — и
«проверенный» сценарий молча проверяет не то. Между стартом и действием —
выдержка `ADB_REC_START_DELAY`; само действие — одна shell-строка на устройстве
(`input tap 540 2200`, `am start -n …`, `input keyevent 24`):

```python
rec = adb_rec_record('/tmp/tap.mp4', during='input tap 540 2200', seconds=6, serial=SERIAL)
```

Проверка, что действие в кадре, не глазами, а пикселями: разница соседних
кадров до и после момента — десятки миллионов по каналу (у volume-UI всплеск
виден между t=0.8 и t=1.6).

## 3. Кадры: точный поиск, а не быстрый

`adb_rec_frames` зовёт ffmpeg с `-ss` **после** `-i`: у screenrecord ключевые
кадры раз в секунду, быстрый `-ss` до `-i` притягивает кадр к ближайшему
ключевому, и «момент тапа» приедет соседним, на котором ничего не произошло.
Имена кадров несут время (`f1.60.png`) — кадры сшиваются с событиями лога без
пересчёта на глаз. Частотный режим (`fps=`) годится для «в целом посмотреть»,
имена `f-0007.png` — порядковые.

## 4. Лист всей записи и сверка двух записей

Десяток одиночных кадров, открытых по очереди, теряет последовательность: к пятому
не помнится, что было «до». `adb_rec_sheet(mp4, out, fps=2, cols=5, width=270)`
отдаёт один png — сетку всех кадров, каждая клетка подписана плашкой со временем
(`t=0.5`): вся запись читается одним взглядом — где начался переход, что мелькнуло
между состояниями.

Не ffmpeg-овским `tile` — не каприз, а потерянный хвост: у фильтра нет сброса
неполного ряда (в рабочем билде опции просто нет — filtergraph не инициализируется),
то есть конец записи, обычно самый интересный, терялся бы молча. Модуль вытаскивает
кадры одним декодированием (`fps` + `scale`) и клеит ряды Pillow-ом: ряд ровно
столько, сколько есть, неполный последний доклеивается чёрным, подписи времени
рисуются там же. Кадры сверх `ADB_REC_SHEET_MAX_ROWS` рядов прореживают fps
автоматически — лист обязан оставаться обозримым.

`adb_rec_compare(mp4_a, mp4_b, times, out, labels=('A','B'), cell_width=270)` —
инструмент сверки «оригинал против клона»: берёт кадры из обоих файлов на одних и
тех же моментах (точным `-ss` через `adb_rec_frames`) и склеивает парами; колонки
подписаны плашками разных цветов — глаз собирает пары раньше, чем прочитается
текст. Список `times` — контрольные точки сценария: миг нажатия, середина
перехода, финальное состояние. Цвета меряют только записью с записью — § Грабли.

## CLI

```bash
python -m adb_.adb_rec record /tmp/rec.mp4 --serial SERIAL --seconds 6 --during "input keyevent 24"
python -m adb_.adb_rec frames /tmp/rec.mp4 --times 0.8,1.6,3.0
python -m adb_.adb_rec frames /tmp/rec.mp4 --fps 2 --out-dir /tmp/frames
python -m adb_.adb_rec sheet /tmp/rec.mp4 --out /tmp/sheet.png [--fps 2 --cols 5 --width 270]
python -m adb_.adb_rec compare /tmp/a.mp4 /tmp/b.mp4 --times 0.3,0.8,1.4 \
    --labels 'оригинал,клон' --out /tmp/cmp.png [--cell-width 270]
```

## Грабли

1. **Стянуть раньше конца записи — битый mp4**: `moov` дописывается на
   `SIGINT`/таймере; pull только после завершения процесса adb.
2. **Действие в первую секунду не попадает** — запись поднимается ~с; между
   стартом и `during` выдержка, иначе «проверено» значит «не снято».
3. **Потолок 180 с** — больше устройство не пишет; длинный сценарий — несколько
   записей, а не одна.
4. **`ffmpeg` — системный пакет** (как poppler в генераторе PDF): отсутствие —
   отдельная ошибка `FileNotFoundError`, а не тихий отказ; колесом в pip не
   ставится.
5. **Два устройства без `--serial`** — adb падает «more than one
   device/emulator»; сериал обязателен, когда подключён и эмулятор.
6. **Запись темнее экрана** — screenrecord пишет не те значения, что заданы в
   hex и что видит глаз: тонирование дисплея печатается поверх. Замеренный
   фон `#747f8a` (116,127,138) записывается примерно как (91,99,108), светлый
   глиф `#989898` — как (94,102,113). Поэтому цвет в проверках перехода —
   только «запись с записью», никогда «запись с hex»: разница между двумя
   записями одного экрана меньше системного сдвига и в лоб не сравнивается.
7. **`FLAG_SECURE` окна пишутся чёрным** — банки, менеджеры паролей, диалоги
   биометрии: screenrecord не имеет права снимать их пиксели. Чёрные кадры
   внутри записи — не порча файла и не ошибка разбора, а признак защищённого
   окна; «запись потемнела» посреди сценария проверяется по `adb_app_current`
   и карте экрана, а не повторной записью.
8. **Лаунчер показывает иконку до старта приложения** — MIUI/HyperOS до первой
   рамки приложения рисует системное стартовое окно с launcher-иконкой по
   центру: «чёрный квадрат на старте» лечится иконкой запуска (и её фоном),
   а не настройками splash — splash окно наступает позже. Стартовое окно
   видно на первых моментах `compare` и на `sheet` в самом верху листа.
