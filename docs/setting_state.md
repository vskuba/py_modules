# JSON-состояние поверх `setting_`: дефолты долиты, `dynamic=1` помнит

> Всё, что круг помнит между тиками (расписание: активна ли вещь, смены,
> последний прогон и почему он не состоялся), — одна строка `setting` с JSON.
> Голый `setting_get` про это молчит: значение — строка, дефолты каждый домен
> разводит руками, `dynamic=1` забывают — и состояние человека выползает на
> страницу настроек. `setting_state(key, defaults)` разбирает и доливает;
> `setting_state_patch(key, patch)` правит поверх состояния и пишет с `dynamic=1`;
> `setting_state_clear(key)` снимает. Инструмент — `py_modules/setting_/setting_state.py`,
> CLI: `python -m setting_.setting_state read|patch|clear <ключ>`.

## 1. Приём один раз, а не на каждый домен

Читать → разобрать JSON (словом сказать, если там не он) → долить дефолтами →
отдать dict; патч — поверх состояния, запись — с `dynamic=1`. Кругам остаётся
своя работа: что означает день и смена, что считать состоянием — это домен,
а не слой.

```python
state = await setting_state('photo.search.schedule', {'enabled': False})
state = await setting_state_patch('photo.search.schedule', {'enabled': True})
```

## 2. Чем состояние отличается от настройки

Настройку правит человек со страницы «Настройки → Значения»; состояние правит
код (счётчики, последний прогон, выбранные наборы), и человеку там править
нечего — поэтому строка пишется с `dynamic=1` и на странице не показывается.
Настройку чинят из UI, состояние — только правкой строки в базе, а это всегда
чужая страница.

## Грабли

- **нет строки — это не ошибка, а факт**: ответ один — дефолты целиком; круг
  без строки живёт по дефолтам, а не падает на `KeyError`.
- **в строке не JSON-объект** — ValueError с текстом: домен, разводящий
  состояние, обязан увидеть, что кто-то положил туда не объект, а молчание.
