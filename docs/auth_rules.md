# Auth Rules — аутентификация, роли, права

> Права проверяются **по возможностям, а не по имени роли**. Проверка вешается на
> endpoint декларативно. Роли — данные в БД, а не константы в коде.

## 1. Аутентификация

Сессия в БД (токен в cookie/заголовке), а не подпись в токене — потому что сессию нужно
уметь отзывать мгновенно и видеть список активных.

- пароли — только хеш с солью, никогда обратимое преобразование
- срок жизни сессии + продление при активности
- логаут удаляет запись, а не только cookie
- одна функция «получить текущего пользователя», используемая везде; ни один endpoint не
  парсит cookie сам

## 2. Роли — данные, а не код

Роли и наборы их прав хранятся в БД и добавляются без деплоя. В коде хардкодится максимум
одна роль — суперадминская, чтобы систему нельзя было запереть снаружи.

### Проверка права — декларативная

Права требуются на уровне endpoint через зависимость-класс:

```python
class AuthChecker:
    def __init__(self, required_permissions: list[str]):
        self.required_permissions = required_permissions

    async def __call__(self, request) -> Session:
        current_user = await auth_get_current_user(request)
        user_permissions = auth_role_permissions(current_user.role)
        for perm in self.required_permissions:
            if perm not in user_permissions:
                raise Forbidden("Недостаточно прав")
        return current_user
```

Применение — в объявлении роута, не внутри тела функции. Тогда список требований виден
при чтении сигнатуры, а не спрятан в двадцатой строке хендлера.

### ⚠️ Никогда не проверять роль по имени

```python
if user.role == 'admin':      # ❌ появилась вторая полноправная роль — сломалось молча
if auth_role_is_full(role):   # ✅ проверка возможности
```

Сравнение с литералом ломается при каждом добавлении роли, и ломается **тихо**: код не
падает, просто перестаёт кого-то пускать (или начинает пускать не тех). Любая проверка
роли должна быть предикатом-возможностью.

### Гранулярность прав

Права делятся по **действию**, а не по странице. Просмотр, изменение, удаление,
запуск/остановка, восстановление — разные права, если у них разные последствия.
Read-only роль должна получать ровно просмотр.

## 3. Полевые политики (field-level)

Роль может иметь право на сущность целиком, но не на отдельные поля. Политика — словарь
`сущность → роль → список полей` с обязательным fallback-ключом `'*'`:

```python
POLICY = {
    '<entity>': {
        'admin':   {'read': '*',                 'write': '*'},
        '<role>':  {'read': ['id', 'title'],     'write': ['title']},
        '*':       {'read': ['id', 'title'],     'write': []},
    },
}
```

Две функции: фильтр полей на чтение и фильтр полей на запись. **Фильтр на запись
обязателен** — иначе роль без права на поле пришлёт его в `PATCH` и изменит.

Fallback `'*'` нужен, чтобы новая роль по умолчанию получала минимум, а не всё.

## 4. Новая защищённая сущность: чек-лист

1. Объявить права на действия (`<entity>_view`, `<entity>_edit`, …) и раздать их ролям.
2. Навесить зависимость проверки на все роуты сущности.
3. Если поля неравноправны — добавить сущность в полевую политику **вместе с ключом `'*'`**.
4. Прогнать фильтр записи на входе в `UPDATE` (не только фильтр чтения на выходе).
5. Проверить под ограниченной ролью, а не только под админом.

## 5. Тестовая учётная запись

Для интеграционных тестов — **отдельная полноправная учётка, не админская**. Причина: её
сессии видно в логах отдельно, и «кто это сделал — человек или сюита» становится
отвечаемым вопросом. Пароль — в локальном файле окружения, никогда в коде тестов.

## Грабли

1. **`role == 'admin'`** — тихо ломается при добавлении роли
2. **Проверка права внутри хендлера, а не в объявлении роута** — легко забыть в новом методе
3. **Фильтр полей только на чтение** — запись остаётся дырой
4. **Нет ключа `'*'` в политике** — новая роль получает доступ ко всему
5. **Одно право на страницу вместо права на действие** — read-only роль может удалять
6. **Проверено только под админом** — 403 находит пользователь, не разработчик
