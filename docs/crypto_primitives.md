# crypto_ — примитивы вне цепочек: Ed25519, proof-of-work

## 1. Зачем namespace

DID-регистрации (Ed25519 + PoW-challenge), Solana/x402-обвязка, EdDSA-заголовки —
везде нужны те же два примитива, но ни одна цепочка их не «владеет»: `evm_` для
них неверный адрес. Отсюда отдельная папка: голые байты ключей/подписей и
подбор nonce, кодирование выбирает вызывающий.

## 2. Что здесь

| Модуль | Что делает |
|--------|-----------|
| `crypto_ed25519.py` | пара ключей (из seed или случайная), подпись/проверка сообщения |
| `crypto_pow.py` | `sha256(seed + nonce)` с ≥ N ведущими нулевыми битами; подбор и сверка |

## 3. Грабли

- **seed — ровно 32 байта.** Строку под seed сначала хешируют (sha256), иначе
  ключ зависит от кодировки текста и не воспроизводится на другой машине.
- **сообщение подписывается побайтово «как в challenge»** — ни strip, ни
  переносов из JSON; сервис сверяет подпись byte-for-byte.
- **кодирование у платформ разное**: MolTrust ждёт hex публички и base64url без
  padding для подписи; Solana — base58; угаданное кодирование даёт «signature
  does not verify» при верно подписанном сообщении.
- **PoWconcat — строками**: seed как дали + `str(i)`; hex-decode seed'а — другая
  задача. Ожидание ~2**bits попыток: bits=18 — доли секунды, bits>24 — таймаут
  в вызывающем.

## 4. Проверка правки

Одного импорта мало (crypto-пакеты ленивые): прогнать `crypto_ed25519` полный
круг пара→подпись→проверка и `python -m crypto_.crypto_pow SEED --bits 18` —
nonce и число нулей должны сойтись.
