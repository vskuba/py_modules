# dsh board — агенты DeepSeek Harness субагентами

> Оркестратор на той же машине, что и хост harness'а (Claude Code), раздаёт работу его
> агентам так же, как человек в браузере: заводит карточку под проект, ставит задачу и
> ждёт ответ. Задачи с ожиданием — и повторяющиеся, и разовые — ложатся на доску плагина
> `dsh-continuous-agent`: одна очередь-бокс, заходы идут по порядку бокса на моторах
> модели разом. `dsh_/dsh_session.py` — карточки и их журнал,
> `dsh_/dsh_board.py` — задачи, потолок, доска, `dsh_/dsh_board_cli.py` — команда.

Требования: хост `dsh --profile web` на этой машине (транспорт — `docs/dsh_api.md`) и
плагин `dsh-continuous-agent` из claude-shell (`plugins/`). Без плагина работают только
функции `dsh_session`.

## 1. Задача субагенту

```python
from dsh_.dsh_board import dsh_board_session_new, dsh_board_ask

session = dsh_board_session_new('~/PycharmProjects/BlogAi', 'разбор логов')
answer = dsh_board_ask(session, 'найди ошибки в logs/ и предложи фикс', wait=True)
```

Карточка заводится как кнопкой «＋ сессия» доски — preset и модель хоста по умолчанию.
С `wait` задача кладётся в бокс доски (`continuous_add` от имени самой карточки, заход
одноразовый) и видна там, пока ждёт мотора: её можно переставить, снять, поставить на её
место другую — §2 и §3. Без `wait` — промпт прямо в карточку: несколько вызовов подряд —
очередь промптов, агент разберёт их по одному; ответ потом — `dsh_session_answer_last`.

## 2. Много задач разом

```python
from dsh_.dsh_board import dsh_board_fanout

results = dsh_board_fanout([
    {'session': session, 'text': 'прогони тесты'},
    {'cwd': '~/PycharmProjects/CyberAi', 'title': 'ревью', 'text': '…', 'archive': True},
])
# [{'session': …, 'answer': …, 'error': ''}, …] — в порядке задач
```

`fanout` сначала кладёт, потом ждёт: задачи заводятся и ложатся в бокс последовательно,
по порядку списка, — что раньше в задачах, то раньше в боксе. Задач больше, чем моторов, —
лишние ждут своей очереди в боксе, а не в нитях: нити только читают журнал в ожидании
ответов, заход делает доска. Потому оборванный `fanout` не теряет работу: карточки
доработают на хосте, а `dsh-board collect` дождётся и допишет. Замерено: при одном моторе
две задачи шли строго друг за другом.

Сорвавшаяся задача остальных не роняет — у неё заполнен `error` (ловится любое
исключение: у каждой задачи строка результата). Её цель при этом остаётся на доске:
круг мог выжить, и его ответ доберёт человек (`dsh-board answer`); снятие цели — только
после полученного ответа. `archive: true` убирает в архив карточку,
которую `fanout` завёл сам, и только после ответа: сорвавшаяся могла оставить живой круг,
и его ответ ещё можно дочитать (`dsh_session_answer_last`). Чужую (`session`) не трогает
никогда.

## 3. Параллельность — бокс доски

Очередь одна — бокс доски: и цели человека из формы, и задачи `dsh_board_ask`/`fanout`.
У модели N цепочек (моторов), по умолчанию четыре: заходы из разных рядов идут разом, а
первый свободный мотор берёт раннюю по порядку бокса. Модели на llama.cpp (один поток)
ставят один мотор, иначе заходы встанут в её очередь:

```python
from dsh_.dsh_board import dsh_board_motors_set
dsh_board_motors_set('gx10-1', 'Qwen3.8-Flash-Next', 1)
```

Цель нашего клада одноразовая (`quotaRounds: 1`, без периода) и снимается с доски после
полученного ответа — закрытое не должно копиться и путать порядок; при ошибке и таймауте
цель не трогается. `ask` без `--wait` кладёт в бокс так же; ответ забирает `dsh-board wait`,
он же снимает закрытые цели карточки (`dsh_board_box_clear`). ⚠ Прямой промпт мимо бокса —
работа руками: мотор занимается **сверх** их числа (24.11 так встал пятый при четырёх), поэтому
мимо бокса идут только спящая карточка, неназванная модель и продолжение оборванного круга. Кто работает сейчас — `dsh_board_working()`: занятые моторы, у каждого `kind`
`run` (цель доски, `goal` — её название) или `hand` (работа руками), и подпись карточки.

Агентские карточки и промпты форма доски рисует с 🤖, чтобы отличать от заведённых
человеком. Карточку помечает этот слой: `dsh_board_session_new` шлёт `robot: true`
(доска заносит её в `robots`). Промпт помечает плагин: всё, что положено инструментом
(`continuous_add` — им пользуется и `dsh-board add`), получает `robot: true`, а
кирпичик любого промпта агентской карточки — 🤖 по её записи в `robots`.

## 4. Доска промптов

Правка целей — `dsh_board_tool(session, 'continuous_add' | 'continuous_edit' |
'continuous_drop', args)`: те же инструменты, что у модели, от имени живой карточки.
Снимок — `dsh_board_state()`: цели, цепочки, занятые машины (`machines`), настройки,
архивные карточки (`archived`).

## 5. Команда

```bash
# сессии и задачи
PYTHONPATH=. python -m dsh_.dsh_board sessions [--all]          # живые карточки (--all — и без агента)
PYTHONPATH=. python -m dsh_.dsh_board new ~/proj "логи" [--no-full-access] [--ask "…" --wait]
PYTHONPATH=. python -m dsh_.dsh_board ask <session> "прогони тесты" --wait [--timeout 1800]
PYTHONPATH=. python -m dsh_.dsh_board fanout tasks.json          # N задач разом
PYTHONPATH=. python -m dsh_.dsh_board answer <session>           # последний ответ
PYTHONPATH=. python -m dsh_.dsh_board history <session> -n 5     # промпты и ответы
PYTHONPATH=. python -m dsh_.dsh_board cancel <session>           # прервать круг
PYTHONPATH=. python -m dsh_.dsh_board archive <session>
PYTHONPATH=. python -m dsh_.dsh_board working [--line]           # кто работает сейчас
# доска
PYTHONPATH=. python -m dsh_.dsh_board board [--session <session>]
PYTHONPATH=. python -m dsh_.dsh_board add <session> "сверяй логи" --every 60
PYTHONPATH=. python -m dsh_.dsh_board edit <goal> [--text …] [--status paused] [--position 1]
PYTHONPATH=. python -m dsh_.dsh_board drop <goal>
PYTHONPATH=. python -m dsh_.dsh_board motors gx10-2/Qwen3.8-Flash-Next 4
PYTHONPATH=. python -m dsh_.dsh_board pause | resume              # рубильник доски
```

Текст промпта у `ask`, `add`, `edit --text`, `new --ask` и файл `fanout` можно дать `-` —
тогда он читается из stdin. `--json` (до или после подкоманды) — ответ JSON вместо текста,
`--base host:port` — другой хост. Потолок ожидания ответа по умолчанию — 1800 с, общий на
весь вызов.

Проект ставит её своей командой одной строкой — claude-shell: `dsh-board`
(`src/dsh/dsh_board.py` зовёт `dsh_board_cli_main`).

## 5а. Беречь контекст оркестратора: `--out`, «входящие»

Ответ субагента целиком в контексте оркестратора — это его токены, ради экономии
которых субагенты и заведены. Поэтому:

- `ask`/`new` с `--out ФАЙЛ`, `fanout` с `--out-dir КАТАЛОГ`: субагента просят начать
  ответ блоком «SUMMARY:» (старые ответы — «ИТОГ:») в 3–5 строк, полный ответ ложится в файл, в вывод — только итог и
  путь (`dsh_board_brief`; не послушал — первые строки, не длиннее 700 символов).
  Замерено: итог ~600 символов против 6 КБ ответа.
- **Язык — английский.** Задачи субагентам и все шаблоны слоя (шапка копии, тесты на копии,
  формат ответа, проверка, продолжение) — по-английски, ответ тоже по-английски; человеку
  оркестратор пересказывает по-русски. Замер 24.11 на токенизаторе Qwen3.8 (gx10-4): те же
  шаблоны — 347 токенов против 418 (−17%). Правило оркестратору приносят хуки
  `claude_hook_dsh_mode` (`DSH_MODE_ENGLISH`) и `claude_hook_dsh_prefix`.
- `dsh-board inbox` — агентские карточки с ответами, которых оркестратор ещё не забрал
  (его сессия могла закрыться, а ответ лёг в журнал карточки). `inbox --take` отмечает
  прочитанным; `ask --wait` и `answer` отмечают сами. Счёт — по числу кругов карточки
  (`sessionStats.turns`), не по журналу: служебные записи после ответа журнал сдвигают, а
  круг — нет; итог берётся из `turnOutline` без загрузки журнала. Отметки —
  `~/.dsh/dsh-board.inbox-turns.json`. `inbox --count` — число для статусной строки («📥 N»).

Хост на старте отвечает `gateway/service-unavailable` (`DshApiUnavailable`): вызов
точно не исполнен, и слой повторяет его до 120 с — и засечку, и промпт, и заведение
карточки. Таймаут (`DshApiUnreachable`) переспрашивается только у засечки: дошёл ли
промпт — неизвестно, повтор мог бы его задвоить.

## 5б. Оборванные круги, копии репозитория, статистика

**Перезапуск хоста** закрывает идущий круг записью `turn/end` с причиной `interrupted` —
промежуточная реплика («ищу…») тогда не ответ. `dsh_board_ask --wait` видит это
(`dsh_session_turn_reply` отдаёт причину) и сам шлёт «продолжай» — до двух раз.
Карточки, которых никто не ждёт, продолжает `dsh-board revive` (`--dry` — только
показать).

**Пишущий код субагент** — в своей копии репозитория: `dsh-board new <repo> "<имя>"
--worktree --ask …` заводит `git worktree` на ветке `dsh/<слаг>` в
`<repo>/.claude/worktrees/`; карточка — под общим техническим workspace (ниже).
Основная копия не трогается; что сделано —
`dsh-board diff <сессия> [--stat]` (и незакоммиченное, и новые файлы), сливает
оркестратор сам; копию убирает `dsh-board drop-worktree <сессия>` (ветка остаётся).
Принять работу — `dsh-board land <сессия> [--message …]`: незакоммиченное коммитится в
ветку субагента, ветка сливается в основную копию `merge --no-ff`, копия, ветка, карточка
и проект копии убираются; конфликт — слияние откатывается, всё остаётся для разбора.
В `fanout` задача с `"worktree": true` получает свою копию сама (в результате `worktree`
и `branch`) — N пишущих задач разом, каждая на своей ветке. Модуль — `dsh_/dsh_worktree.py`.

**Карточка копии — не отдельный проект на панели.** Harness не умеет задать сессии
рабочий каталог отдельно от workspace: `session/create` принимает `workspaceId` или `cwd`
(не оба), путь сессии берётся из пути workspace, а `WorkspaceEntity.attachSession`
отвергает карточку, чей `cwd` ему не равен. Поэтому все `--worktree`-карточки живут в одном
техническом workspace `~/.dsh/dsh-worktrees` (`dsh-worktrees` в панели, в нём только
`README.md`, репозитория там нет). Путь копии лежит в метаданных карточки
(`~/.dsh/dsh-board.worktrees.json`, `dsh_board_worktree_row`) и в шапке её промпта:
«Твоя копия репозитория: …; все команды — с `cd` в неё; основной репозиторий … не трогай».
По метаданным копию находят `diff`/`land`/`drop-worktree` и уборка; для старых карточек
(до метаданных) — по-прежнему по их `cwd` с приметой `.claude/worktrees/dsh-`. Технический
workspace уборка и `land` не снимают с панели — он общий дом карточек; одинокие
worktree-workspace старых карточек снимаются, как раньше.

**Занятость моторов** — `dsh-board working [--line]`: маршрут хоста `continuous-agent.working`
отдаёт занятые моторы и ёмкость (`capacity` — моторы включённых моделей); `--line` —
строка для статусной строки: `DSH 0/4` в простое, `DSH 1/4: [1] ревью …` в работе — перед
подписью значок мотора (`dsh_motor_badge`, цифра на плашке своего цвета; тот же значок
стоит в таблице сессий Claude напротив хозяина работы)
(`dsh_board_motors_busy`). С `--links КАТАЛОГ` каждая задача в строке — гиперссылка
OSC 8 на живой журнал карточки `<КАТАЛОГ>/<сессия>.md` (промпты и ответы, как `history`;
переписывается не чаще раза в 5 с, `dsh_working_log`). ⚠ На саму карточку в вебе хоста
сослаться нельзя: сессия в адрес страницы не попадает, вход — по токену `dsh web`.
⚠ Строку со ссылками не обрезать по байтам: обрезанная ссылка захватывает весь хвост.

**Статистика** — `dsh-board stats [--all]`: сумма `tokenUsage` агентских карточек
(входные, выходные, кэш) и самые затратные — работа, которую иначе делал бы оркестратор.

## 5г. Экономия в процентах тарифа — `saving`, «DSH 1/4 (-10%)»

`dsh-board saving` переводит работу субагентов в **проценты окон подписки Claude Code**
(`dsh_/dsh_saving.py`); статусная строка показывает экономию своей сессии зелёной меткой
`DSH 1/4 (-10%)` — доля 5-часового окна.

- **Цена процента калибруется**: взвешенные токены самого Claude за текущее окно (транскрипты
  `~/.claude/projects/**.jsonl`) делятся на `rate_limits.*.used_percentage`, который Claude
  Code отдаёт статусной строке; та кладёт снимок в `~/.cache/claude-rate/<session>.json`.
- **Веса — прайс API**: вход 1, выход 5, чтение кэша 0,1, запись 1,25 — и для Claude, и для
  `tokenUsage` субагента. Из работы вычитается цена делегирования: промпт (выход
  оркестратора) и выжимка на каждый круг (вход).
- **Чья карточка**: `new` пишет владельца — `CLAUDE_CODE_SESSION_ID` — в
  `~/.dsh/dsh-board.owners.json`; без него экономию по сессиям не разложить.

⚠ Оценка, не счёт Anthropic; ошибки в сторону **занижения**: расход аккаунта с других
машин в транскриптах не виден, а Claude на той же работе гонял бы свой больший контекст.
⚠ Сессии разных аккаунтов на одной машине: аккаунт узнаётся по `seven_day.resets_at`,
чужие транскрипты из калибровки выбрасываются. Общий файл снимка они перетирали.
⚠ Недельный сброс плывёт и **у того же аккаунта** (было `1795777200 → 1795780800`, на час):
аккаунт сопоставляется с допуском `DSH_SAVING_ACCOUNT_DRIFT` (сутки) — иначе свежее окно
теряло калибровку (метка «(-N%)» исчезала на часы), точка отсчёта сбрасывалась, а своя
сессия попадала в чужие.
⚠ Окно занято меньше 3% (после сброса) — калибровка прошлая: целый процент мерить нечем.

## 5в. Перекрёстная проверка и уборка

**Проверка ответа** — `dsh-board verify <сессия> [--out ФАЙЛ]`: второй субагент в той же
папке, без контекста первого, получает исходную задачу и ответ и сверяет каждое
утверждение с кодом или первоисточником — ✅ подтверждено / ❌ неверно / ❓ не проверить.
Оркестратору — итог; сам он смотрит только ❌ и ❓. Функция — `dsh_board_verify`.

**Уборка** — `dsh-board gc [--days 7] [--dry]`: агентские карточки, не идущие и не
обновлявшиеся дольше N дней, уходят в архив; их копии репозитория снимаются, если в них
нет незакоммиченных правок (ветка остаётся), проекты копий — с панели.

## 6. Префикс `d` — задача субагенту из чата

Сообщение человека Claude Code, начинающееся с `d ` (или `d:`), — задача субагенту, а
не самому агенту: хук `claude_/hook/claude_hook_dsh_prefix.py` (`UserPromptSubmit`,
прописан в `~/.claude/settings.json`) добавляет модели инструкцию — завести карточку
`dsh-board new <проект> "<имя>" --ask "<задача>"` в фоне, сказать человеку, что задача
отдана, а пришедший ответ проверить и пересказать с пометкой «ответ субагента».

```
d посмотри в интернете новости за 24 часа
```

## 7. Режим: `high` / `free` / `off`

Сколько отдавать субагентам, решает человек, а не модель заново на каждой задаче
(`dsh_/dsh_mode.py`):

| Режим | Что делает оркестратор |
|---|---|
| `high` (умолчание) | отдаёт всё: разведку, правки в `--worktree`, тесты, ревью, логи, поиск, проверку через `verify`; сам — только необратимое, решения, общение с человеком, приёмку и работу в одну-две команды |
| `free` | на своё усмотрение: объёмное — субагентам, остальное сам |
| `off` | субагентов не зовёт; префикс `d ` режим перекрывает |

Переключение — сообщением `/dsh high|free|off` (skill `~/.claude/skills/dsh`) или
`dsh-board mode <режим> [--session <id> | --default]`. Режим сессии лежит в
`~/.cache/dsh-mode/<сессия>`, общее умолчание — `~/.claude/dsh-mode`, нет обоих — `high`.

Хук `claude_/hook/claude_hook_dsh_mode.py` (`UserPromptSubmit`) кладёт правило режима
в контекст **каждого** хода: совет из CLAUDE.md модель вспоминала через раз. Сообщение
`/dsh <режим>` хук ловит сам и пишет файл сессии до того, как модель его прочтёт.
⚠ Сообщение должно быть ровно `/dsh <режим>`: с хвостом («/dsh high и сделай …») это
уже задача, а не переключатель. Режим виден в статусной строке: `DSH 1/4 high (-10%)`.

### Как режим следит за собой

Правило «разведку — субагентам» забывается ровно тогда, когда агент занят делом: он
читает файл за файлом сам. За следждением стоят два хука на `Read|Grep|Glob|Bash`,
считающие **серию чтений** — с последней из трёх засечек: вызова `dsh-board` (разведку
уже отдали), сообщения человека (новый ход) или строки `Сам:` в ответе агента (объяснил,
почему делает сам).

| Режим | Хук | Что делает |
|---|---|---|
| `high` | `claude_/hook/gate/claude_gate_dsh_delegate.py` (`PreToolUse`) | на **пятом** чтении подряд **отменяет вызов** и отдаёт готовую команду; повтор того же вызова проходит, следующая отмена — ещё через пять |
| `free` | `claude_/hook/claude_hook_dsh_nudge.py` (`PostToolUse`) | после восьми чтений — мягкое напоминание, одно на серию |
| `off` | — | молчат оба |

```
dsh-board new "<проект>" "<имя>" --ask "<что найти>" --wait --out <файл>
dsh-board fanout tasks.json --out-dir <каталог>        # независимые куски — разом
```

Пройти без делегирования можно честно: сказать человеку строку, начинающуюся с `Сам:`
(«Сам: ищу одну строку, описать задачу дороже») — с неё серия начинается заново.
⚠ Отказ заставы — **один на серию**: застава, отменяющая каждое чтение, была бы снята в
тот же день. Классификация «чтения» общая у обоих хуков
(`claude_hook_dsh_nudge_is_read`) и ловит чтение в **любом** куске составной команды —
`git fetch -q && ls`, `cat a.json | jq`, `cd X && Q() { …mysql_query… }; Q`.
Подробности — `docs/claude/hook/claude_gate_dsh_delegate.md`.

## Грабли

- ⚠⚠ **Ответ субагента не должен уходить в никуда.** Оркестратора будят только его фоновые
  процессы. Каждый промпт субагенту из сессии Claude ставит метку «ответ ждём»
  (`dsh_wait`); снимает её `ask --wait` или фоновый ждун `dsh-board wait --out-dir <каталог>`,
  который дожидается ответов по всем меткам своей сессии (обрыв — не ответ) и выходит —
  выход и будит. Застава `claude_hook_dsh_wait` на `Stop` не отпускает ход, пока метки есть,
  а живого ждуна нет. Так и было: задача без `--wait`, ход закрыт, ответ лежал, пока не спросили.

- ⚠ **Оборванные перезапуском хоста круги продолжаются сами** (`revive --auto` из статусной
  строки, раз в минуту): только агентские карточки, обновлявшиеся за полчаса, каждый обрыв —
  один раз (номер его `turn/end` в `dsh-board.revived.json`). Карточку, которую ждёт `ask`
  (пометка в `dsh-board.waiting.json` с pid), не трогает: тот продолжит её сам — иначе два промпта.

- ⚠⚠ **Тесты пишущей задачи — на коде её копии, а не на общем стенде.** :8011 крутит основную
  выкладку: правка субагента там не видна, и «зелёные» тесты ничего не доказывают. Пишущей
  задаче (`fanout … worktree: true`, `new --worktree --ask`) к промпту дописывается команда
  `project_worktree test`: свой одноразовый контейнер над копией (образ, сеть и `.env` — из
  compose-описания `uvicorn_task`), свободный порт, сюита с хоста, уборка. Параллельно можно.
  Подмодули (`py_modules`, `dashboard`) в копии пусты — подаются монтированием и временной
  папкой ссылок, копия не трогается; файлы, созданные контейнером (root), возвращаются хозяину.

- ⚠ **Оборванный `fanout` не теряет работу.** С `--out-dir` он ведёт `fanout.json`: карточка
  и копия — сразу при старте задачи, ответ в `N.md` — сразу по её концу. Убили `fanout` —
  карточки доработают на хосте, а `dsh-board collect <каталог>` дождётся их (лёгким
  `working`) и допишет недостающее.

- ⚠ **Уборка идёт сама** (`dsh_board_gc_auto` из статусной строки, раз в час на машину).
  Карточка копии репо, чья ветка уже слита или каталог удалён, убирается сразу вместе с
  проектом на панели; прочие агентские — через сутки тишины. Копию, удалённую руками
  (`git worktree remove`), уборка тоже заметит: проект без каталога снимается с панели.

- ⚠⚠ **`session/list` — самый дорогой вызов хоста.** Он несёт проекции всех карточек:
  346 карточек — 2,5 МБ и 43 с. Ожидание ответа звало его каждые 2 с ради одной засечки,
  трое ждущих держали хост в сборке мусора (6 ГБ кучи, load 69). Теперь засечку одной
  карточки называет `session/page` отказом `past cursor N` (0,2 с), журнал читается, только
  когда засечка сдвинулась, а сам список — общий кэш на диске на 60 с с одним читающим.

- ⚠ **Бокс доступен только живой карточке.** Маршрут `continuous-agent.tool` живёт при
  живом агенте (400 «is not live») — уснувшую после рестарта хоста карточку целью не
  покормишь. `ask`/`fanout` в этом случае ставят задачу прямым промптом; цели на доске
  тогда нет, и снимать после ответа нечего. Так же — когда модель карточки нечем назвать
  (несколько моделей на доске, у свежей карточки `sessionModel` ещё нет).

- ⚠⚠ **Карточка без полного доступа встаёт молча.** Субагент в копии репо (`--worktree`)
  доходит до `git commit`, каталог `.git` лежит вне песочницы — и круг ждёт «Allow once»
  человека, а `fanout` ждёт круг. Поэтому `dsh_board_session_new` и `fanout` по умолчанию
  дают полный доступ, как галочка окна доски; отказ — явный `--no-full-access`.

1. **Ответ — на свой промпт, а не на первый конец круга.** Перед отправкой берётся
   засечка журнала; после — ищется свой `user/message` (новее засечки, тот же текст),
   затем `turn/end` после него, и ответ — последнее сообщение агента между ними. Первый
   `turn/end` после засечки бывает чужим: карточка занята работой руками, заходом доски
   или соседней задачей того же `fanout` — и прежде такой чужой ответ выдавался за наш
   (нашёл субагент DeepSeek на ревью). Опрос `running` вместо журнала пропускает
   короткий круг, если хост в эти секунды занят. ⚠ Два одинаковых текста подряд в одну
   карточку по тексту неразличимы.
2. **Журнал без вебсокета.** Хвост журнала хост отдаёт первым кадром потока
   `session/follow`, но тот же хвост даёт обычный `session/page` — ему нужна засечка
   `throughSeq` не дальше текущей (иначе `bad-request … past cursor`). Её приносит
   `session/list`: `projections.asOfSeq` карточки.
3. **Архивная карточка остаётся в `session/list`.** Архив виден только реестром
   проектов (поток `workspace/follow`); доска отдаёт его полем `archived` в `state`.
4. **Промпт человека — `user/message` с `source.kind == "user"`.** Тем же типом идут
   служебные вставки хоста (инструкции проекта, снимок песочницы) со своим `kind`.
5. **Без модели цель доски «неположена»** и не идёт нигде — кладите её на цепочку
   модели своей карточки (`sessionModel` из `state`), как делает форма; наш слой так и
   делает (`dsh_board_model_of`), а назвать нечем — уходит прямым промптом.
