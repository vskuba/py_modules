# Code Rules — именование, размещение, дробление, докстринг

> Обязательные правила для всего кода: имя публичной функции начинается с namespace
> своего файла, приватные функции стоят в конце файла, файлы дробятся по ответственности.
> Применяются и к новым файлам, и к правкам существующих.
>
> Подход к разбиению — **GRASP + DDD**: границы режут по предмету, обязанность кладут
> туда, где лежат данные для неё, одинаковое живёт одним паттерном, а механика не торчит
> наружу (§4).

## Основные правила архитектуры кода

- Не размазывать код, не допускать один и тот же функционал по сути в разных файлах.
  Функционал, отвечающий за конкретную логику, должен быть инкапсулирован.
- Основные принципы при написании кода:
    - DDD (domain-driver design)
    - SOLID
    - GRASP (General Responsibility Assignment Software Patterns)

## Прежде всего — поискать готовое

**Перед тем как писать функцию, файл или namespace — спроси словами, нет ли такого в
общем слое.** Всё, что ниже, — про то, как назвать и разместить новый код; этот шаг
решает, появится ли он вообще.

```bash
PYTHONPATH=. python -m tool_.tool_find "снять экран телефона"    # из py_modules
PYTHONPATH=py_modules python -m tool_.tool_find "разобрать json" # из проекта: слой лежит submodule-ом
```

Полторы секунды: опись собирается обходом дерева, индекса на диске нет — устаревать
нечему. Ответ двух видов: 🔧 функция говорит «чем это делают», 📄 тема документации —
«как устроено и обо что уже спотыкались». Искать идут обычно за вторым, а зовут первое.

Поиск **лексический**, и это диктует, как спрашивать: одно короткое намерение словом из
описи («коммит-сообщение», а не «проверить коммит-сообщение») — два шумных слова уже
размазывают ранжирование. Слова не дали ничего — `--map` покажет карту namespace-ов и
тем, дальше по ней. Подробности — `tool_find.md`.

Второй вариант уже существующей функции пишется обычно не от лени, а оттого, что первую
**не нашли**: функций в слое под пять сотен, реестра и точки входа у него нет.

## 0. Перед созданием нового файла — посмотри на соседей

**Всегда открой целевую папку и повтори её шаблон именования.** Готового не нашлось —
это первое действие, до написания кода.

```
<domain>/
    task_agent.py
    task_claim.py
    task_pipeline.py
    task_state.py
```

Шаблоны читаются из того, что уже есть:

- `task_<domain>_<action>.py` → функции `task_<domain>_<action>_...`
- `task_<domain>.py` → функции `task_<domain>_...`

Типичная ошибка — обратный порядок слов, ломающий шаблон модуля:

- `bug_task_create.py` ❌ — не продолжает существующий `task_*` шаблон
- `task_bug_create.py` ✅ — продолжает

```bash
ls <dir>/*.py                                              # какие файлы уже есть
grep -oP '^async def \K[a-z_0-9]+' <dir>/*.py | sort -u    # какие префиксы уже в ходу
```

### 0.1 До шаблона соседей — папка: namespace называют по предмету

Прежде чем смотреть шаблоны соседей, ответь одной строкой, **о чём** этот модуль, —
папку называют по этому предмету. «Я зову его руками из CLI» — не предмет: от этого
признака всё вокруг выглядит инструментом, и так можно свалить что куда попало.
В `tool_` живут инструменты, которые говорят о самом слое: опись `tool_find`,
вычитка `tool_typo`, порядок `tool_order`. Проверка целости файла говорит о файле —
значит `file_/file_check.py`, а не `tool_/tool_intact.py`.

Признак ошибки: папку выбрали по тому, кто зовёт, а не по тому, что функция
возвращает (`{'intact', 'bytes'}` со словами про файл — значит предмет «файл»).

## 1. Префикс публичной функции = namespace файла

Namespace — путь «папка + имя файла». Все публичные функции файла начинаются с него.

```
<root>/tool/fact/fact_collection_.py  ->  fact_collection_add()
                                          fact_collection_remove_by()

<root>/ai/ai_llm.py                   ->  ai_llm_node_get()
                                          ai_llm_image_generate()
```

**Хвостовое подчёркивание в имени файла в префикс не входит** — оно ставится только
чтобы не конфликтовать с именем пакета или встроенного модуля:

| Файл | Префикс |
|------|---------|
| `fact_collection_.py` | `fact_collection_` |
| `mysql_.py` | `mysql_` → `mysql_find_by()` |
| `queue_.py` | `queue_` → `queue_get()` |

**Одна функция, названная именем файла, — уже соблюдает правило.** Модуль ради
единственного действия называют этим действием, и функция повторяет имя файла без
суффикса:

| Файл | Функция | Почему допустимо |
|------|---------|------------------|
| `web_screenshot.py` | `web_screenshot()` | модуль ровно об этом действии |
| `mysql_seed_up.py` | `mysql_seed_up()` | то же |
| `task_bug_create.py` | `task_bug_create()` | то же |

Смысл правила — чтобы по имени функции было видно, из какого она модуля. Здесь видно
полностью, и добавлять глагол (`web_screenshot_capture`) значит удлинять имя, ничего им
не сообщая. Условие ровно одно: **публичная функция в файле одна**. Появилась вторая —
префикс обязателен обеим, включая первую.

Отдельно про инструменты (`<root>/tool/**`): там имя функции ещё и ключ в реестре
инструментов, по нему их зовут шаги workflow. Переименование такой функции меняет
контракт и требует пересинхронизации реестра на всех установках, включая прод, —
причина не трогать их без нужды, а не только вопрос стиля.

Второе исключение — **точки входа планировщика**: скрипт, запускаемый как процесс,
называет свою функцию `main()`. Логика при этом всё равно живёт в доменном модуле и
подчиняется правилу полностью.

### 1.1 Четвёртое слово в префиксе — пора заводить подпапку

**Префикс дорос до четырёх слов — это не длинное имя, это неназванная папка.**

Признак механический и потому надёжный: имена файлов в папке начинают повторять
друг друга всё более длинным началом, а префикс функций тянется следом.

```
src/dating/dating_favorite.py            ->  dating_favorite_pick()
src/dating/dating_favorite_mail.py       ->  dating_favorite_mail_quiet()
src/dating/dating_favorite_mail_round.py ->  dating_favorite_mail_round_run()   ← четыре
```

Слово `dating` здесь не сообщает ничего: **вся папка** про dating, и оно повторено
в имени каждого её файла. Значит его место — в пути, а не в имени:

```
src/dating/favorite/favorite.py            ->  favorite_pick()
src/dating/favorite/favorite_mail.py       ->  favorite_mail_quiet()
src/dating/favorite/favorite_mail_round.py ->  favorite_mail_round_run()        ← три
```

Namespace при этом **не потерян, а переехал**: правило §1 читает его как «путь папка
+ имя файла», и `favorite/favorite_mail_round.py` даёт тот же смысл, что давало
`dating_favorite_mail_round.py`. Изменилось одно — общая часть названа один раз.

**Правило работает на любом уровне.** Дорос до четырёх префикс уже внутри подпапки —
заводится следующая:

```
src/dating/favorite/favorite_mail_round_retry.py   ← четыре внутри favorite/
->  src/dating/favorite/mail/mail_round_retry.py   ->  mail_round_retry_run()
```

#### Почему четыре, а не «когда покажется длинным»

Три слова читаются как «что — о чём — действие» (`favorite_mail_round`), и это
предел, на котором имя ещё произносят целиком. С четвёртого начинается перечисление:
имена соседних файлов различаются последним словом, и глаз ищет различие в хвосте,
прочитав одинаковое начало по третьему разу.

Порог назван числом намеренно. «Когда станет длинным» — не признак: длинным оно
кажется автору на пятом слове, читателю на третьем, а в code review не кажется
никому, потому что обсуждают правку, а не папку.

#### Что это стоит и когда платить

Переезд меняет имена публичных функций, то есть **ломает вызывающих**. В общей
библиотеке это правка всех проектов сразу (см. «Правки здесь — правки всех»), в
проекте — импортов по всему коду.

Отсюда порядок:

- **новая группа файлов** — сразу подпапкой, если уже видно, что их будет больше
  двух и общее начало у них длиннее одного слова;
- **существующая группа** — переезжает, когда её и так правят, а не отдельным
  заходом «привести в порядок»: переименование ради стиля стоит конфликтов в чужих
  ветках дороже, чем сообщает.

⚠ **Один файл с четырёхсловным префиксом папки не требует.** Признак — именно
**группа**: три и больше файлов с общим началом. Одинокий `task_bug_create_retry.py`
переезжать некуда, и подпапка из одного файла ничего не называет.

### 1.2 Имена — только латиницей и английскими словами

**Кириллицы нет ни в одном имени — нигде и ни в одном проекте.** Имя пишется
латинскими буквами и английскими словами, других вариантов нет:

| Где | Примеры имён, на которые правило распространяется |
|-----|---------------------------------------------------|
| Python | переменные, функции, классы, методы, атрибуты, имена файлов и папок, имена тестов |
| MySQL | таблицы, колонки, алиасы, индексы, имена в миграциях, значения-состояния (`status = 'new'`) |
| Данные | ключи словарей и JSON, поля API, параметры запроса, ключи `.env` и настроек, имена артефактов на диске |

**Исключение одно: объяснения, адресованные человеку.** Docstring, комментарии и
текст сообщений (лог, ошибка, вывод CLI) — по-русски, как и вся документация здесь.
Правило про имена, а не про язык объяснений: `raise ValueError("Данные пусты")` — норма,
`данные_пусты = True` — нет.

Python кириллицу в именах допускает, поэтому запрет держится не на синтаксисе, а на
том, что имя приходится набирать руками:

- `pytest -k "приватные"` требует переключения раскладки посреди команды, а привычный
  отбор по латинской подстроке такое имя не найдёт вовсе;
- `grep`, `git log -S` и поиск в редакторе перестают работать с одной раскладки;
- в трейсбеках и выводе CI смешанные алфавиты читаются хуже, а похожие начертания
  (`с`/`c`, `р`/`p`, `о`/`o`) дают имена, различимые только байтами.

#### Запрос к базе — тот же код

**MySQL-запрос правилу подчиняется целиком**: схема, запрос и значения, по которым
код ветвится.

```sql
-- ❌ имя требует кавычек всегда, а `статус = 'новый'` приезжает в код сравнением с кириллицей
SELECT `имя`, `статус` FROM `заказы` WHERE `статус` = 'новый';

-- ✅
SELECT name, status FROM orders WHERE status = 'new';
```

Причины те же, что у Python-имён, плюс две свои:

- **колонка — это ключ в коде**: строка запроса возвращает `row["статус"]`, и
  кириллица из схемы расползается по коду проекта, куда её никто не писал;
- **обратные кавычки перестают быть необязательными**: имя без них ломается в дампе,
  в `mysql_query`, в миграции и в любом стороннем клиенте — а забывают их регулярно.

⚠ **Содержимое строк правило не трогает.** Имя пользователя, текст объявления,
комментарий в данных — на любом языке: это данные, а не имена. Запрет — на схему,
запрос и служебные значения, по которым есть `if`.

Транслитерация запрет не обходит: `test_nezakrytuyu_schit_ne_derzhit` не читается ни
как русское, ни как английское. **Имя переводится словами**, а префикс берётся от
проверяемого модуля — по нему же работает отбор:

```
test_подзадача_в_планировании_меняет_тип  ->  test_task_state_type_to_plan_covers_subtask
test_ответ_не_режется                     ->  test_task_log_shell_answer_kept_whole
test_всегда_думающей_ставим_минимум       ->  test_llm_reasoning_disable_falls_back_to_minimal
```

Правило появилось не на пустом месте: за два дня в тестах набралось 111 кириллических
имён, и три файла оказались смешанными — в одном файле оба стиля разом.

## 2. Константы: UPPER_CASE с префиксом namespace

Namespace для константы — путь от корня кода до файла, разделители `/` → `_`.

```python
# ❌ — без префикса, может конфликтовать при импорте из другого модуля
MAX_ATTEMPTS = 3
BUG_SCAN_ENABLED = True

# ✅ — с префиксом namespace
PROJECT_TASK_BUG_SCAN_ENABLED = True   # из <root>/project/task/task_pipeline.py
AI_LLM_TIMEOUT = 120.0                 # из <root>/ai/ai_llm.py
```

Разбор имени: `<NAMESPACE>_<SUBSYSTEM>_<TYPE>` — namespace модуля, затем подсистема,
затем тип переключателя (`ENABLED`, `LIMIT`, `TIMEOUT`, `MAX`).

Константы, живущие только внутри одного файла, допускаются без префикса. **При
сомнениях префикс добавляется:** избыточное имя дешевле конфликта имён.

## 3. Приватные функции: имя по смыслу, место — в конце файла

На приватные функции (`_prefix`) правило префикса **не распространяется** — их называют
по смыслу:

```python
def _where_build(table_name: str, criteria: dict) -> tuple:
    ...

def _row_json_safe(row: dict) -> dict:
    ...
```

Префикс в приватной функции не ошибка, но и не требование.

**Место строго фиксировано: все приватные — ниже всех публичных, в конце файла.**

```python
# ── публичный API модуля ──

async def task_state_get(task_id: int) -> dict:
    ...

async def task_state_plan_save(task_id: int, plan_json: str) -> None:
    ...


# ── детали реализации ──

def _where_build(table_name: str, criteria: dict) -> tuple:
    ...
```

Причина — порядок чтения: файл открывают, чтобы понять, **что** модуль умеет, а не как
он это делает. Правило распространяется и на правки: увидел приватную выше публичной —
перенеси вниз, даже если менял в файле что-то другое.

### Хук `__main__` — самая последняя строка файла

```python
if __name__ == "__main__":
    main()
```

Кликнувший по CLI читает файл уже собранным целиком, и хук обязан стоять **под
приватными функциями, в конце**: поставленный в середину (сразу за `main`, до
приватной части) он даёт модуль, который импортируется, и тесты в том же процессе
проходят, а вызов через CLI падает на `NameError` — на момент запуска `main()`
определений нижних приватных ещё нет.

Проверяет и это, и порядок определений — `function_.function_order`:

```bash
PYTHONPATH=py_modules python -m function_.function_order src/
```

⚠ Он видит то, чего не видит `grep`-рецепт из §«Быстрые проверки»: классы, методы
внутри класса и хук не на месте. Последнее как раз и стоит `NameError` при
запуске через CLI — а тесты при этом зелёные, потому что модуль импортируется.

⚠ Приватная **константа** в шапке нарушением не считается: она объявляется до
того, кто её читает, и место ей там. Приватную часть открывает только
определение — `def` или `class`. Без этой оговорки проверка дала на общем слое 43
файла, почти все ложно.

## 4. Одна ответственность: дробить файлы, не размазывать знание

Один файл — одна ответственность. Вместо толстого модуля — директория-namespace с
несколькими небольшими файлами.

Ориентир — **до ~150–200 строк**. Превышение само по себе не криминал, но это сигнал
проверить, не совмещает ли файл несколько ответственностей.

### Признак, что пора делить

Файл делает несколько разных вещей. Типичный разбор одного модуля на ~370 строк:

| Файл | Ответственность |
|------|-----------------|
| `<domain>_pipeline.py` | машина состояний |
| `<domain>_claim.py` | захват работы, реклейм блокировок |
| `<domain>_state.py` | запись состояний и истории в БД |
| `<domain>_plan.py` | формат данных (сериализация) |
| `<domain>_agent.py` | роли исполнителей |

Каждый файл после деления получает **свой префикс функций** по правилу 1. То же и для
HTTP-роутеров: CRUD сущности — в одном файле, конвейер/операции — в отдельном.

### 4.1 Подход — GRASP + DDD

Дробление не самоцель, иначе вместо одного толстого файла получаются пять тонких с тем
же перепутанным знанием. **Режут по предмету (DDD), а обязанность кладут туда, где уже
лежат данные для неё (GRASP).** Что это значит в правках здесь:

| Принцип | Как выглядит в этом коде |
|---------|--------------------------|
| DDD: модуль называется предметом | папку называют по тому, о чём она, а не по тому, кто её зовёт (§0.1) |
| DDD: один язык | слово в имени функции — то же, которым предмет называют в докстринге и в разговоре |
| DDD: граница контекста | знание проекта (таблицы, роли, состояния) не переезжает в общий слой — `tool_rules.md`, §1 |
| GRASP: Information Expert | решает тот, у кого данные; тянуть чужие внутренности, чтобы решить, — признак, что обязанность лежит не там |
| GRASP: High Cohesion | файл делает одно — §4 выше |
| GRASP: Low Coupling | наружу торчит действие, устройство не торчит — §4.3 |
| GRASP: Polymorphism / Indirection | семейство случаев — реестр «имя → класс», а не ветка `if` (`llm_rules.md`, §1) |
| GRASP: Protected Variations | чужой формат, протокол, драйвер закрыты своей функцией: меняются они — правится одно место |

Имена принципов нужны не для красоты, а как общий словарь в споре о правке:
«здесь нарушен Information Expert» короче, чем «функция ходит в три чужих модуля, чтобы
посчитать то, что целиком знает один».

### 4.2 Одинаковое делается один раз — паттерном

**Три места делают одно и то же — это не три функции, а один паттерн с точкой различия.**
Размазанный по копиям код не «слегка дублируется»: правку вносят в одну копию из трёх, и
дальше это три разных поведения под одним смыслом. Расходятся копии молча — тем и опасны.

```python
# ❌ — три почти одинаковых функции, отличаются одной строкой
async def report_daily_send(chat_id: int) -> dict: ...     # собрать → отрисовать → отправить
async def report_weekly_send(chat_id: int) -> dict: ...    # то же
async def report_monthly_send(chat_id: int) -> dict: ...   # то же

# ✅ — один скелет, различие параметром
async def report_send(chat_id: int, period: str = "daily") -> dict: ...
```

Порог — **правило трёх**: два похожих места ещё совпадение, третье — уже паттерн. Число
названо по той же причине, что «четвёртое слово» в §1.1: «когда станет похоже» не признак —
автору похоже на пятой копии, читателю на второй, а в обсуждении правки — никому.

Грабля, на которую уже наступили: запрет размышлений у LLM жил веткой `if` в общей
функции. Ветка знала два сервиса из трёх, и до моделей за OpenRouter настройка не
доезжала. Лечится это не четвёртой веткой, а реестром «префикс → класс», где новый
сервис = файл + строка реестра (`llm_rules.md`, §1).

⚠ **Похожее по форме — не всегда одно по смыслу.** Признак ложного объединения: внутри
общей функции заводится `if mode == ...`, и ветки не делят ни строки. Значит склеены две
разные обязанности, и теперь каждая правка одной задевает вторую. Ложное обобщение хуже
дубля: дубль виден глазами, а склейка притворяется паттерном.

⚠ **Осознанный дубль объясняется прямо в докстринге** — иначе следующий читатель сведёт
его «в порядок» и получит связность там, где её не было. Так сделано у `_image_stats`
в `font_/font_.py`: копия статистики из `pdf_` оставлена намеренно, чтобы два модуля не
знали друг о друге, и причина записана рядом с кодом.

⚠ Цена сведения **здесь** — правка всех проектов сразу: удалить одну из трёх публичных
функций значит сломать того, кто звал именно её. Порядок тот же, что в §1.1 — новое
пишется паттерном сразу, существующее сводится, когда его и так правят; расширить
параметром с умолчанием безопасно, убрать публичное имя — нет.

### 4.3 Ячейка прячет свою механику

Модуль предлагает наружу **действия**, а не устройство. Остальное — приватное в конце
файла (§3), и это не вопрос порядка строк: каждое торчащее наружу имя кто-нибудь
импортирует, и оно перестаёт быть деталью, которую можно поменять.

| Наружу не отдают | Почему |
|------------------|--------|
| соединение, курсор, сессию, сырой ответ драйвера | вызывающий начинает их закрывать, переоткрывать и чинить — механика расползлась по коду |
| порядок шагов («сначала X, потом Y») | порядок — знание модуля; отданный наружу, он повторится в каждом вызывающем по-своему |
| формат чужого API или файла | меняется он — правится N мест вместо одного |
| словарь внутреннего состояния | правка поля ломает читателей, о которых модуль не знает |

```python
# ❌ — последовательность знает каждый вызывающий, и каждый по-своему
conn = <domain>_connect(); <domain>_auth(conn)
rows = <domain>_fetch(conn, query); <domain>_close(conn)

# ✅ — последовательность внутри, наружу — действие
rows = <domain>_fetch(query)
```

Проверка одной фразой: **вызывающему должно хватать первой строки докстринга** (§7.1).
Пришлось читать тело — значит наружу торчит механика, а не действие.

### 4.4 Признаки размазанного знания

| Симптом | Что он означает |
|---------|-----------------|
| одно изменение требует правки в трёх файлах | у знания нет владельца, оно размазано |
| функция тянет данные из трёх чужих модулей, чтобы решить | обязанность лежит не там, где данные (Information Expert) |
| `if` по имени сервиса, типа, режима в общей функции | вместо ветки — реестр или стратегия (§4.2) |
| копипаста с заменой двух слов | пропущенный параметр |
| вызывающие повторяют одну и ту же цепочку вызовов | порядок должен жить внутри (§4.3) |
| у модуля десяток публичных имён, а действий три | наружу вынесены детали |

Механическая часть этого ловится проверкой «функции с совпадающим телом» в разделе
«Автопроверка».

## 5. Три ветки размещения кода

Положить файл не в ту ветку — не стилистическая погрешность, а **функциональная
ошибка**: у ветки инструментов и ветки планировщика особое поведение.

| Ветка | Назначение | Особое поведение |
|-------|-----------|------------------|
| `<root>/**` | бизнес-логика по namespace | нет |
| `<root>/tool/**` | инструменты движка workflow | автообнаружение, попадают в БД и предлагаются LLM |
| `<root>/cronjob/**` | точки входа планировщика | запускаются как процесс, нужен `__main__` |

- **Обычную бизнес-логику в ветку инструментов не класть** — она автоматически станет
  инструментом. Подробности — `tool_rules.md`.
- **Файл в ветке планировщика — тонкий:** разбор аргумента, вызов доменной функции,
  печать результата, закрытие пула в `finally`. Признак нарушения — файл без `__main__`.
- **Asyncio-раннеры, живущие в процессе приложения** (запуск из lifespan), — не
  кронджобы. Их место в доменной папке.

## 6. Приведение существующего кода

Правишь файл, где имена не совпадают с namespace, — приводи к правилу заодно. Это
ожидаемая часть работы, а не выход за рамки задачи.

При переименовании проверить, что имя нигде не используется как строка:

```bash
grep -rn "старое_имя" <code_dirs> <template_dirs> tests/
```

Если переименованное/перемещённое — инструмент, после правки нужна пересинхронизация
реестра инструментов: пути хранятся в БД.

## 7. Докстринг публичной функции

Докстринг здесь — **единственный индекс на четыре с лишним сотни публичных функций**:
общего реестра и точки входа нет, соседний namespace не виден, пока в него не заглянешь.
Второй вариант уже существующей функции пишется не от лени, а оттого, что первую не нашли
по описанию.

**У публичной функции докстринг обязателен**; приватная обходится комментарием, когда
неочевидна.

### 7.1 Первая строка — зачем звать, а не что внутри

Она читается вместо кода и попадает в каталог функций, поэтому в ней стоят слова,
которыми функцию **ищут**, — намерение, а не пересказ сигнатуры.

```python
# ❌ — по таким словам не ищут
"""Возвращает соединение Redis."""

# ✅ — намерение и отличие от соседнего
"""Подключиться к Redis — один клиент на процесс, адрес из настроек."""
"""Один запрос без браузера — весь ответ как есть."""
```

Одно предложение, без «Данная функция» и «Возвращает объект типа». У `main` первая строка
описывает CLI: `"""CLI: python -m image_.image_tone rows|band …"""`.

### 7.2 Объём — по сложности, а не по единому шаблону

| Функция | Достаточно |
|---------|-----------|
| тривиальная обёртка | одной первой строки |
| с неочевидными параметрами | + `Args:` |
| инструмент с режимами и форматами | + `Returns:`, единицы измерения, умолчания |

Обязательный `Args:` на функции без аргументов даёт воду, а вода в индексе хуже пустоты:
она совпадает с любым запросом.

### 7.3 Блок `⚠` обязателен, когда грабли есть

Грабли записываются там, где на них наступают, — в докстринге функции, а не только в
`docs/`:

| Грабля | Что сказать |
|--------|-------------|
| модульный синглтон | состояние делится на весь процесс и переживает вызов |
| привязка к event loop | объект не переживает смену loop |
| ленивый импорт тяжёлого | `ModuleNotFoundError` прилетит из вызова, а не из импорта |
| историческое имя вне §1 | переименование сломает соседние проекты |

```python
async def mysql_pool_get() -> Pool:
    """Общий пул соединений с базой — один на процесс, заводится при первом обращении.

    Returns:
        Пул aiomysql: 5–10 соединений, autocommit, DictCursor.

    ⚠ Пул лежит в модульной переменной и привязан к event loop, в котором создан.
    Импорт длинной формой (`py_modules.mysql_.mysql_`) загрузит модуль второй раз —
    и пулов станет два.
    """
```

Модуль целиком описывается не докстрингом, а страницей в `docs/` — `docs_rules.md`, §7.

## Автопроверка

Функции, нарушающие правило префикса, в конкретной директории:

```bash
for f in <dir>/*.py; do
  base=$(basename "$f" .py); base=${base%_}   # снять хвостовое подчёркивание
  pub=$(grep -oP '^(async )?def \K[a-z_0-9]+' "$f" | grep -v "^_" || true)
  # Одна публичная функция, названная именем файла, — исключение из правила:
  # по имени и так видно модуль, добавлять глагол нечего.
  [ "$(echo "$pub" | grep -c .)" = "1" ] && [ "$pub" = "$base" ] && continue
  bad=$(echo "$pub" | grep -v "^${base}_" || true)
  [ -n "$bad" ] && echo "$f: $(echo $bad)"
done
```

Единственное допустимое совпадение в выводе — `main` в точке входа планировщика.

Группы файлов, доросшие до подпапки (§1.1) — три и больше соседей с общим началом,
у которых префикс тянет на четыре слова:

```bash
for d in $(find <code_dirs> -type d -not -path '*/__pycache__/*'); do
  ls "$d"/*.py 2>/dev/null | xargs -rn1 basename | sed 's/\.py$//' \
    | awk -F_ 'NF>=2 {print $1"_"$2"\t"NF}' \
    | awk -F'\t' -v d="$d" '{n[$1]++; if ($2+0 >= 4) deep[$1]=1}
        END {for (k in n) if (n[k] >= 3 && deep[k])
               print d": "k"_* — "n[k]" файла, есть префикс на 4 слова"}'
done
```

⚠ Считаются **все** файлы группы, а глубина — по самому длинному из них. Считай мы
только четырёхсловные, группа `dating_favorite` (`_favorite`, `_favorite_mail`,
`_favorite_round`, `_favorite_mail_round`) не нашлась бы вовсе: длинный там один,
а переезжать им всем вместе.

⚠ **Это подсказка, а не запрет.** Вывод здесь не обязан быть пустым: переезд ломает
вызывающих, и группу переносят, когда её и так правят (см. §1.1). Строка в выводе
означает «посмотри сюда», а не «сломано».

Имена функций и ключи словарей на кириллице — по всему коду разом. Вывод обязан
быть пустым. Смотрит инструмент — он разбирает `*.py` деревом и потому не гадает
по раскладке, ловит и смешанные имена (`test_metadata_строкой_из_mysql`):

```bash
PYTHONPATH=. python -m tool_.tool_typo --cyrillic
```

⚠ Дереву не видно классы — их ловит шаблон (`\w*` — чтобы смешанные имена не
уходили):

```bash
grep -rnP '^\s*class\s+\w*[а-яА-ЯёЁ]' --include=*.py . | grep -v "\.venv\|__pycache__"
```

Переменные — по присваиванию. Строки и комментарии шаблон не ловит: имя обязано
стоять первым словом в строке, а комментарий начинается с `#`:

```bash
grep -rnP '^\s*\w*[а-яА-ЯёЁ][\w]*\s*=[^=]' --include=*.py . \
  | grep -v "\.venv\|__pycache__"
```

Имена в SQL — в коде и в миграциях разом. `\b` перед ключевым словом обязателен:
без него `probe_table обязателен` из текста ошибки считается таблицей:

```bash
grep -rnP '\b(FROM|JOIN|INTO|UPDATE|TABLE|SELECT|WHERE|GROUP BY|ORDER BY)\s+`?\w*[а-яА-ЯёЁ]' \
  --include=*.py --include=*.sql . | grep -v "\.venv\|__pycache__"
```

Файлы, где приватная функция стоит выше публичной. ⚠ Рецепт грубый и оставлен
как запасной: классов, методов и хука `__main__` он не видит — для проверки есть
`function_.function_order` (§3).

```bash
find <code_dirs> -name '*.py' -not -path '*/__pycache__/*' | while read -r f; do
  last_pub=$(grep -nP '^(async )?def [a-z]' "$f" | tail -1 | cut -d: -f1)
  first_priv=$(grep -nP '^(async )?def _' "$f" | head -1 | cut -d: -f1)
  [ -n "$last_pub" ] && [ -n "$first_priv" ] && [ "$first_priv" -lt "$last_pub" ] && echo "$f"
done
```

Файлы в ветке планировщика, которые не являются точками входа:

```bash
find <root>/cronjob -name '*.py' -not -path '*__pycache__*' \
  | while read -r f; do grep -q "__main__" "$f" || echo "не точка входа: $f"; done
```

Файлы, где хук `__main__` стоит не в конце (проверка: `if` ровно за предпоследней
строкой, файл кончается переводом строки):

```bash
for f in $(git ls-files '*.py'); do
  ln=$(grep -n '^if __name__ == "__main__":' "$f" | cut -d: -f1)
  [ -n "$ln" ] && [ "$ln" -ne $(( $(wc -l < "$f") - 1 )) ] && echo "$f"
done
```

Следы неудачной правки в прозе — подмена буквы из другого алфавита, слипшиеся слова,
повтор. Идёт перед коммитом вместе с остальными проверками (`docs_rules.md`, §6.0):

```bash
PYTHONPATH=. python -m tool_.tool_typo
```

⚠ Орфографию это не проверяет и не может: словаря нет. Чистый вывод означает «механических
следов нет» — границы и вычитка моделью описаны в `tool_typo.md`.

Публичные функции без докстринга (§7). Текстовым шаблоном докстринг надёжно не увидеть —
проверка разбирает синтаксическое дерево:

```bash
python - <<'PY'
import ast, pathlib
for p in sorted(pathlib.Path('.').rglob('*.py')):
    if '.venv' in p.parts or '__pycache__' in p.parts: continue
    try: tree = ast.parse(p.read_text(encoding='utf-8'))
    except SyntaxError: continue
    for n in tree.body:
        if isinstance(n, (ast.FunctionDef, ast.AsyncFunctionDef)) \
                and not n.name.startswith('_') and not ast.get_docstring(n):
            print(f'{p}:{n.lineno} {n.name}')
PY
```

Проверяются функции **уровня модуля** — те, что видны импортом и подчиняются правилу
префикса §1. Методы классов сюда не попадают намеренно: их описывает класс.

Кандидаты на дробление:

```bash
find <code_dirs> -name '*.py' -exec wc -l {} + | sort -rn | head -20
```

Функции с совпадающим телом — кандидаты в один паттерн (§4.2). Сравниваются деревья,
а не текст, поэтому отступы и докстринг не мешают:

```bash
python - <<'PY'
import ast, pathlib, collections
seen = collections.defaultdict(list)
for p in sorted(pathlib.Path('.').rglob('*.py')):
    if '.venv' in p.parts or '__pycache__' in p.parts: continue
    try: tree = ast.parse(p.read_text(encoding='utf-8'))
    except SyntaxError: continue
    for n in ast.walk(tree):
        if not isinstance(n, (ast.FunctionDef, ast.AsyncFunctionDef)): continue
        body = n.body[1:] if ast.get_docstring(n) else n.body
        if len(body) < 5: continue          # короткие совпадения — шум, а не копия
        seen[ast.dump(ast.Module(body=body, type_ignores=[]))].append(f'{p}:{n.lineno} {n.name}')
for places in seen.values():
    if len(places) > 1: print(' == '.join(places))
PY
```

⚠ **Это подсказка, а не запрет** — как и проверка групп в §1.1. Сегодня она даёт одну
строку: `font_/font_.py:_image_stats == pdf_/pdf_.py:_stats` — дубль осознанный и
объяснённый в докстринге (§4.2), сводить его не надо.

⚠ Ловится только буквальная копия: тела с заменёнными именами переменных деревья
различают, и «похожее с двумя другими словами» проверка пропустит. Признаки такого —
глазами, по таблице §4.4.

**Вывод проверок должен быть пустым** — кроме двух помеченных подсказками: групп файлов
под подпапку (§1.1) и функций с совпадающим телом (§4.2); там строка означает «посмотри
сюда». Найденное чинится по мере правок этих файлов (правило 6) — **списка «согласованных
исключений» не существует.**
