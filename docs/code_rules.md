# Code Rules — именование, размещение, дробление

> Обязательные правила для всего кода: имя публичной функции начинается с namespace
> своего файла, приватные функции стоят в конце файла, файлы дробятся по ответственности.
> Применяются и к новым файлам, и к правкам существующих.

## 0. Перед созданием нового файла — посмотри на соседей

**Всегда открой целевую папку и повтори её шаблон именования.** Это первое действие,
до написания кода.

```
<domain>/
    task_agent.py
    task_claim.py
    task_pipeline.py
    task_state.py
```

Шаблоны читаются из того, что уже есть:

- `task_<domain>_<action>.py` → функции `task_<domain>_<action>_...`
- `task_<domain>.py` → функции `task_<domain>_...`

Типичная ошибка — обратный порядок слов, ломающий шаблон модуля:

- `bug_task_create.py` ❌ — не продолжает существующий `task_*` шаблон
- `task_bug_create.py` ✅ — продолжает

```bash
ls <dir>/*.py                                              # какие файлы уже есть
grep -oP '^async def \K[a-z_0-9]+' <dir>/*.py | sort -u    # какие префиксы уже в ходу
```

## 1. Префикс публичной функции = namespace файла

Namespace — путь «папка + имя файла». Все публичные функции файла начинаются с него.

```
<root>/tool/fact/fact_collection_.py  ->  fact_collection_add()
                                          fact_collection_remove_by()

<root>/ai/ai_llm.py                   ->  ai_llm_node_get()
                                          ai_llm_image_generate()
```

**Хвостовое подчёркивание в имени файла в префикс не входит** — оно ставится только
чтобы не конфликтовать с именем пакета или встроенного модуля:

| Файл | Префикс |
|------|---------|
| `fact_collection_.py` | `fact_collection_` |
| `mysql_.py` | `mysql_` → `mysql_find_by()` |
| `queue_.py` | `queue_` → `queue_get()` |

**Одна функция, названная именем файла, — уже соблюдает правило.** Модуль ради
единственного действия называют этим действием, и функция повторяет имя файла без
суффикса:

| Файл | Функция | Почему допустимо |
|------|---------|------------------|
| `web_screenshot.py` | `web_screenshot()` | модуль ровно об этом действии |
| `mysql_seed_up.py` | `mysql_seed_up()` | то же |
| `task_bug_create.py` | `task_bug_create()` | то же |

Смысл правила — чтобы по имени функции было видно, из какого она модуля. Здесь видно
полностью, и добавлять глагол (`web_screenshot_capture`) значит удлинять имя, ничего им
не сообщая. Условие ровно одно: **публичная функция в файле одна**. Появилась вторая —
префикс обязателен обеим, включая первую.

Отдельно про инструменты (`<root>/tool/**`): там имя функции ещё и ключ в реестре
инструментов, по нему их зовут шаги workflow. Переименование такой функции меняет
контракт и требует пересинхронизации реестра на всех установках, включая прод, —
причина не трогать их без нужды, а не только вопрос стиля.

Второе исключение — **точки входа планировщика**: скрипт, запускаемый как процесс,
называет свою функцию `main()`. Логика при этом всё равно живёт в доменном модуле и
подчиняется правилу полностью.

### Имена — только латиницей

**Кириллицы в именах нет нигде: ни в функциях, ни в классах, ни в переменных, ни в
тестах.** Docstring, комментарии и текст сообщений — по-прежнему по-русски: правило
про идентификаторы, а не про язык объяснений.

Python кириллицу в именах допускает, поэтому запрет держится не на синтаксисе, а на
том, что имя приходится набирать руками:

- `pytest -k "приватные"` требует переключения раскладки посреди команды, а привычный
  отбор по латинской подстроке такое имя не найдёт вовсе;
- `grep`, `git log -S` и поиск в редакторе перестают работать с одной раскладки;
- в трейсбеках и выводе CI смешанные алфавиты читаются хуже, а похожие начертания
  (`с`/`c`, `р`/`p`, `о`/`o`) дают имена, различимые только байтами.

Транслитерация запрет не обходит: `test_nezakrytuyu_schit_ne_derzhit` не читается ни
как русское, ни как английское. **Имя переводится словами**, а префикс берётся от
проверяемого модуля — по нему же работает отбор:

```
test_подзадача_в_планировании_меняет_тип  ->  test_task_state_type_to_plan_covers_subtask
test_ответ_не_режется                     ->  test_task_log_shell_answer_kept_whole
test_всегда_думающей_ставим_минимум       ->  test_llm_reasoning_disable_falls_back_to_minimal
```

Правило появилось не на пустом месте: за два дня в тестах набралось 111 кириллических
имён, и три файла оказались смешанными — в одном файле оба стиля разом.

## 2. Константы: UPPER_CASE с префиксом namespace

Namespace для константы — путь от корня кода до файла, разделители `/` → `_`.

```python
# ❌ — без префикса, может конфликтовать при импорте из другого модуля
MAX_ATTEMPTS = 3
BUG_SCAN_ENABLED = True

# ✅ — с префиксом namespace
PROJECT_TASK_BUG_SCAN_ENABLED = True   # из <root>/project/task/task_pipeline.py
AI_LLM_TIMEOUT = 120.0                 # из <root>/ai/ai_llm.py
```

Разбор имени: `<NAMESPACE>_<SUBSYSTEM>_<TYPE>` — namespace модуля, затем подсистема,
затем тип переключателя (`ENABLED`, `LIMIT`, `TIMEOUT`, `MAX`).

Константы, живущие только внутри одного файла, допускаются без префикса. **При
сомнениях префикс добавляется:** избыточное имя дешевле конфликта имён.

## 3. Приватные функции: имя по смыслу, место — в конце файла

На приватные функции (`_prefix`) правило префикса **не распространяется** — их называют
по смыслу:

```python
def _where_build(table_name: str, criteria: dict) -> tuple:
    ...

def _row_json_safe(row: dict) -> dict:
    ...
```

Префикс в приватной функции не ошибка, но и не требование.

**Место строго фиксировано: все приватные — ниже всех публичных, в конце файла.**

```python
# ── публичный API модуля ──

async def task_state_get(task_id: int) -> dict:
    ...

async def task_state_plan_save(task_id: int, plan_json: str) -> None:
    ...


# ── детали реализации ──

def _where_build(table_name: str, criteria: dict) -> tuple:
    ...
```

Причина — порядок чтения: файл открывают, чтобы понять, **что** модуль умеет, а не как
он это делает. Правило распространяется и на правки: увидел приватную выше публичной —
перенеси вниз, даже если менял в файле что-то другое.

## 4. Файлы дробить по ответственности

Один файл — одна ответственность. Вместо толстого модуля — директория-namespace с
несколькими небольшими файлами.

Ориентир — **до ~150–200 строк**. Превышение само по себе не криминал, но это сигнал
проверить, не совмещает ли файл несколько ответственностей.

### Признак, что пора делить

Файл делает несколько разных вещей. Типичный разбор одного модуля на ~370 строк:

| Файл | Ответственность |
|------|-----------------|
| `<domain>_pipeline.py` | машина состояний |
| `<domain>_claim.py` | захват работы, реклейм блокировок |
| `<domain>_state.py` | запись состояний и истории в БД |
| `<domain>_plan.py` | формат данных (сериализация) |
| `<domain>_agent.py` | роли исполнителей |

Каждый файл после деления получает **свой префикс функций** по правилу 1. То же и для
HTTP-роутеров: CRUD сущности — в одном файле, конвейер/операции — в отдельном.

## 5. Три ветки размещения кода

Положить файл не в ту ветку — не стилистическая погрешность, а **функциональная
ошибка**: у ветки инструментов и ветки планировщика особое поведение.

| Ветка | Назначение | Особое поведение |
|-------|-----------|------------------|
| `<root>/**` | бизнес-логика по namespace | нет |
| `<root>/tool/**` | инструменты движка workflow | автообнаружение, попадают в БД и предлагаются LLM |
| `<root>/cronjob/**` | точки входа планировщика | запускаются как процесс, нужен `__main__` |

- **Обычную бизнес-логику в ветку инструментов не класть** — она автоматически станет
  инструментом. Подробности — `tool_rules.md`.
- **Файл в ветке планировщика — тонкий:** разбор аргумента, вызов доменной функции,
  печать результата, закрытие пула в `finally`. Признак нарушения — файл без `__main__`.
- **Asyncio-раннеры, живущие в процессе приложения** (запуск из lifespan), — не
  кронджобы. Их место в доменной папке.

## 6. Приведение существующего кода

Правишь файл, где имена не совпадают с namespace, — приводи к правилу заодно. Это
ожидаемая часть работы, а не выход за рамки задачи.

При переименовании проверить, что имя нигде не используется как строка:

```bash
grep -rn "старое_имя" <code_dirs> <template_dirs> tests/
```

Если переименованное/перемещённое — инструмент, после правки нужна пересинхронизация
реестра инструментов: пути хранятся в БД.

## Автопроверка

Функции, нарушающие правило префикса, в конкретной директории:

```bash
for f in <dir>/*.py; do
  base=$(basename "$f" .py); base=${base%_}   # снять хвостовое подчёркивание
  pub=$(grep -oP '^(async )?def \K[a-z_0-9]+' "$f" | grep -v "^_" || true)
  # Одна публичная функция, названная именем файла, — исключение из правила:
  # по имени и так видно модуль, добавлять глагол нечего.
  [ "$(echo "$pub" | grep -c .)" = "1" ] && [ "$pub" = "$base" ] && continue
  bad=$(echo "$pub" | grep -v "^${base}_" || true)
  [ -n "$bad" ] && echo "$f: $(echo $bad)"
done
```

Единственное допустимое совпадение в выводе — `main` в точке входа планировщика.

Имена с кириллицей — по всему коду разом. Вывод обязан быть пустым:

```bash
grep -rnP "^\s*(async\s+)?def\s+\w*[а-яА-ЯёЁ]|^\s*class\s+\w*[а-яА-ЯёЁ]" \
  --include=*.py . | grep -v "\.venv\|__pycache__"
```

Шаблон намеренно ищет `\w*[а-яА-ЯёЁ]`, а не имя целиком из кириллицы: имена
`test_metadata_строкой_из_mysql` начинаются латиницей и по более узкому шаблону не
находились бы.

Файлы, где приватная функция стоит выше публичной:

```bash
find <code_dirs> -name '*.py' -not -path '*/__pycache__/*' | while read -r f; do
  last_pub=$(grep -nP '^(async )?def [a-z]' "$f" | tail -1 | cut -d: -f1)
  first_priv=$(grep -nP '^(async )?def _' "$f" | head -1 | cut -d: -f1)
  [ -n "$last_pub" ] && [ -n "$first_priv" ] && [ "$first_priv" -lt "$last_pub" ] && echo "$f"
done
```

Файлы в ветке планировщика, которые не являются точками входа:

```bash
find <root>/cronjob -name '*.py' -not -path '*__pycache__*' \
  | while read -r f; do grep -q "__main__" "$f" || echo "не точка входа: $f"; done
```

Кандидаты на дробление:

```bash
find <code_dirs> -name '*.py' -exec wc -l {} + | sort -rn | head -20
```

**Вывод всех проверок должен быть пустым.** Найденное чинится по мере правок этих файлов
(правило 6) — **списка «согласованных исключений» не существует.**
