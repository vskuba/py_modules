# Deploy Rules — Blue-Green деплой

> Два одинаковых слота, трафик переключается только после того, как новый слот ответил
> на healthcheck. Источник истины о текущем слоте — **конфиг прокси**, а не рантайм.

## 1. Схема

| Элемент | Роль |
|---------|------|
| прокси | принимает внешний трафик, проксирует в активный слот |
| слот A | один экземпляр приложения на своём внутреннем порту |
| слот B | второй экземпляр, порт отличается |
| конфиг прокси | файл, в котором записан адрес активного слота |

Слоты полностью равноправны: в них разворачивается один и тот же образ, различаются только
имя и порт. Никакого «основного» и «резервного» — есть только «активный сейчас».

## 2. Источник истины

> ⚠️ **Определять активный слот по рантайму (кто запущен, кто отвечает) — ошибка.**
> В момент деплоя запущены оба, а во время сбоя может не отвечать ни один. Тогда скрипт
> «угадывает» и разворачивается поверх работающего слота.

Правильно: активный слот записан в **конфиге прокси** (или в отдельном файле-маркере,
который пишется вместе с ним). Он читается перед деплоем и меняется одной операцией
после успешного healthcheck.

## 3. Последовательность

1. **Прочитать активный слот** из конфига → целевой слот = другой.
2. **Собрать образ** новой версии.
3. **Поднять целевой слот** на его порту. Активный продолжает обслуживать трафик.
4. **Healthcheck целевого слота** — опрос до успеха с таймаутом.
5. **Миграции/подготовка данных** — по правилам `database_rules.md` (адресно, вручную,
   не полным DDL-файлом).
6. **Переключить конфиг прокси** на целевой слот и перезагрузить прокси **без разрыва
   соединений** (graceful reload, не restart).
7. **Остановить прежний слот** — но не удалять его образ: он нужен для отката.

Провал на шагах 2–5 — деплой прерывается, трафик всё ещё на старом слоте, откат не нужен.
Провал после шага 6 — нужен откат.

## 4. Healthcheck

- отдельный endpoint, который проверяет **готовность обслуживать**, а не просто «процесс
  жив»: соединение с БД, применённые миграции, загруженная конфигурация
- опрос с интервалом и общим таймаутом (десятки секунд — приложение стартует не мгновенно)
- **пустой код ответа / ошибка соединения ≠ провал**: на старте это нормально, значит
  «ещё поднимается». Провал — истёкший таймаут или устойчивый 5xx
- healthcheck идёт **напрямую в порт слота**, минуя прокси: иначе проверяется старый слот

## 5. Откат

Откат — это тот же шаг 6 в обратную сторону: переключить конфиг прокси на предыдущий слот
и перезагрузить прокси. Он **быстрый ровно до тех пор, пока предыдущий слот не удалён** —
поэтому его контейнер и образ не чистятся сразу после деплоя.

Откат оставляется **ручным**. Автоматический откат по первому же 5xx звучит хорошо, но
скрывает причину и порождает флаппинг между версиями.

**Что откат не отменяет:** применённые изменения схемы и данных. Отсюда правило —
изменения схемы должны быть совместимы с предыдущей версией кода (добавление колонки, а не
переименование; новое поле nullable или с дефолтом). Иначе откат кода ломает базу.

## 6. Чек-лист деплоя

1. Новые переменные окружения — в секрете CI (см. `env_config_rules.md`), не на сервере.
2. Изменения схемы обратно совместимы с текущей рабочей версией кода.
3. Healthcheck проверяет реальную готовность, а не только процесс.
4. Предыдущий слот сохранён для отката.
5. Известно, как откатиться, **до** переключения трафика, а не после.

## Грабли

1. **Активный слот определён по рантайму** — деплой поверх работающего слота
2. **`restart` прокси вместо graceful reload** — обрыв активных соединений
3. **Healthcheck через прокси** — проверяется старая версия
4. **Ошибка соединения принята за провал** — деплой прерывается на нормальном старте
5. **Ломающая миграция** — откат кода невозможен, база уже новая
6. **Прежний слот удалён сразу** — откат превращается в новый деплой
7. **Прод-переменная добавлена руками** — стёрта этим же деплоем
