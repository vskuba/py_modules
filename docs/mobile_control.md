# Mobile control — управлять телефоном из кода

> Смотреть на устройство — `mobile_device.md`. Здесь второе: **действовать**. Нажать,
> ввести, прокрутить, запустить приложение, прочитать журнал. Ключ ко всему — карта
> экрана `adb_ui`: она даёт точные координаты элементов, а без координат нажимать
> некуда.
>
> Третье — **убедиться, что действие сработало**: `mobile_steps.md`. Там слой поверх
> этого: шаг, который сам ждёт покоя и сам сравнивает экраны до и после. Сценарий
> длиннее пары нажатий пишется на нём, а не на голом `adb_input`.

## 1. Круг работы: карта → действие → проверка

Управление устройством — это цикл из трёх шагов, и пропуск любого превращает работу
в угадывание:

```
adb_ui_text()        что на экране и где именно (координаты)
adb_input_tap_on()   действие по надписи, а не по пикселю
adb_ui_wait()        дождаться нового экрана, потом следующий шаг
```

Почему не «снимок и зрение» на каждом шаге: **модель не знает координат.** Она честно
опишет кнопку, но её место на экране назовёт примерно — и нажатие уйдёт в соседний
элемент. Промах при этом внешне неотличим от попадания: экран поменялся, значит
«сработало». Дамп `uiautomator` знает границы каждого элемента точно, стоит одной
команды и не тратит ход модели.

Зрение остаётся ровно для тех экранов, где дерева нет (§ 2, «куда карта не достаёт»).

## 2. Карта экрана — `adb_/adb_ui.py`

| Функция | Контракт |
|---------|----------|
| `adb_ui_text(serial='', nodes=None) -> str` | человекочитаемая карта: строка на цель, координата нажатия, пометки |
| `adb_ui_nodes(serial='', xml='') -> list[dict]` | элементы списком словарей — для кода, а не для чтения |
| `adb_ui_find(query, serial='', nodes=None, exact=False) -> dict` | найти элемент по надписи; `{}` — не найден |
| `adb_ui_wait(query, serial='', timeout=15, exact=False) -> dict` | то же, но ждать появления; не дождался — `TimeoutError` |
| `adb_ui_dump(serial='', tries=3) -> str` | сырой XML, когда нужно разобрать самому |

Карта выглядит так — координата, надпись, пометки:

```
com.example.app
[ 169, 175] Меню
[ 540, 413] Профиль                                  нажать
[ 540, 690] Уведомления                              нажать
[ 540,1500] Выход                                    нажать
[ 126,2115] Главная                                  нажать
[ 953,2159] Ещё
```

Живой экран из 66 узлов дерева сворачивается в полтора десятка строк: это и есть цель
модуля — **отдать модели то, по чему можно принять решение**, а не дерево, в котором
надо разбираться.

Три вещи, которые стоит знать про элементы:

- **Нажимать нужно по `tap`, а не по середине `bounds`.** Надпись и иконка обычно лежат
  внутри кликабельной обёртки, у которой ни текста, ни описания нет. `tap` — это точка,
  где нажатие принимают: ближайший кликабельный предок, а не центр самой надписи.
- **Элемент с границами `[0,0][0,0]` — не мусор.** Так выглядят, к примеру, подписи
  нижних вкладок: сама надпись без размера, а размер — у обёртки. Выбросить их значит
  потерять имена вкладок; координата у них берётся от предка.
- **Совпадение ищется по надписи, описанию и id, без учёта регистра.** При нескольких
  попаданиях выигрывает точное совпадение, а среди равных — элемент меньшей площади:
  это ближе к цели, чем контейнер, внутри которого она лежит.

**Куда карта не достаёт:** экраны, нарисованные одним полотном, — Canvas, WebView и
часть кросс-платформенных фреймворков. Дерево у них есть, а текста в нём нет. Признак
однозначный: карта из двух строк на богатом экране. Вот там и остаётся зрение
(`adb_screen_describe`). Обратное тоже верно: **элемент нашёлся в дампе — модель
спрашивать незачем.** Для WebView есть и третий путь — CDP (§ 8), когда страницу
надо не описать, а вычислить или куда-то повести.

## 3. Действия — `adb_/adb_input.py`

| Функция | Контракт |
|---------|----------|
| `adb_input_tap_on(query, serial='', exact=False, timeout=15) -> dict` | главный вход: найти по надписи, дождаться, нажать; возвращает нажатый элемент |
| `adb_input_tap(x, y, serial='')` | нажатие по координате |
| `adb_input_swipe(x1, y1, x2, y2, ms=400, serial='')` | жест из точки в точку; больше секунды — перетаскивание |
| `adb_input_scroll(direction='down', serial='', part=0.5, ms=400)` | прокрутка на долю экрана: `down`, `up`, `left`, `right` |
| `adb_input_text(value, serial='')` | ввод в поле, которое **уже** в фокусе; только ASCII |
| `adb_input_key(name, serial='')` | клавиша: `BACK`, `HOME`, `ENTER`, `DEL`, `APP_SWITCH` — префикс `KEYCODE_` необязателен |
| `adb_input_wake(serial='')` | разбудить экран; замок не снимает |
| `adb_input_wake_full(unlock=True, home=True, stayon=True, tries=5, serial='') -> dict` | полный ритуал: экран → замок → шторка → домой, с перечиткой `mCurrentFocus`; вернёт `{'awake','focus','shade'}`, `shade=True` — шторка удержала фокус, трогать экран рано |
| `adb_input_stayon(on=True, serial='')` | `svc power stayon`: не гасить экран на зарядке; по окончании работы **вернуть `on=False`** |

На HyperOS/MIUI `adb_input_wake` будит только экран и на этом сдаётся, а до
рабочего состояния руками приходится проходить три каприза системы: с AOD
(`Dozing`) однократный сигнал не срабатывает — жмём `POWER` циклом до
`mWakefulness=Awake` (уснувший `WAKEUP` не будит вовсе); окно `AOD` или
шторка держат `mCurrentFocus` даже когда `mFocusedApp` уже лаунчер — тапы
уходят в систему, при этом `cmd statusbar collapse` помогает не всегда, а
`HOME` с AOD не снимает вообще: `wake_full` повторяет `collapse` с паузой и
добавляет свайп вверх (тем самым жестом, которым живой человек сбрасывает
AOD); сон между действиями съедает половину серии — на
её время `svc power stayon true`, обратно самому (иначе телефон греется и
разряжается, а замеры врываются).

Возврат `adb_input_tap_on` — не формальность: по нему видно, **во что попали на самом
деле**. Надпись «Сохранить» может найтись и в заголовке, и на кнопке.

Доли экрана вместо пикселей — не стиль, а переносимость: зашитая координата означает
жест не туда на первом же другом устройстве. Оттого прокрутка считает точки от
`adb_screen_size()` и отступает от краёв: жест вплотную к краю забирает себе система
(«назад» снизу, шторка сверху), и до приложения он не доходит вовсе.

## 4. Приложения — `adb_/adb_app.py`

| Функция | Контракт |
|---------|----------|
| `adb_app_current(serial='') -> dict` | что на переднем плане: `{'package', 'activity'}`; `{}` — фокуса нет (экран погашен, замок) |
| `adb_app_list(serial='', query='', system=False) -> list[str]` | установленные пакеты; по умолчанию без системных |
| `adb_app_start(package, serial='', activity='')` | запустить (или вынести вперёд); без `activity` — стартовый экран приложения |
| `adb_app_wait(package, serial='', timeout=20) -> dict` | дождаться приложения на переднем плане |
| `adb_app_stop(package, serial='')` | `force-stop`: данные на месте, теряется несохранённое |
| `adb_app_version(package, serial='') -> dict` | версия и даты установки/обновления |
| `adb_app_install(apk, serial='', downgrade=False, timeout=120) -> str` | поставить APK; провал расшифрован в подсказку (понижение — `downgrade=True`, чужая подпись — снять пакет, отмена — ставьте без пальца пользователя рядом) |
| `adb_app_pull_apk(package, out_dir='/tmp/apk', serial='') -> list` | стянуть APK приложения на машину: `pm path` + pull base и split-ов (base первым); пакета нет — `RuntimeError` |

`adb_app_current()` отвечает на вопрос «нужный экран вообще открылся?» без снимка и без
модели. Ни зрение, ни карта на него не отвечают: они видят, что нарисовано, но не
отличат чужое приложение поверх нашего от нашего же.

Имя пакета — **единственное надёжное имя приложения**: заголовок на экране переводится,
меняется от версии и повторяется у разных программ.

`adb_app_pull_apk` — мостик к разбору чужого APK на машине: устанавливаемое
приложение часто есть только на устройстве (Play-маркет руками не распаковываешь),
а смотреть содержимое удобнее не на телефоне. Ставится на то, что у приложения
бывают **split-пакеты** (`config.arm64_v8a.apk` и подобные): ресурсы и код лежат
не только в `base.apk`, поэтому `pm path` отдают список целиком и тянут все
файлы, а голый `base.apk` с половины приложений даёт неполную картину. Дальше —
`apk_inspect.md`: бинарный XML и таблицы ресурсов читаются с машины.

## 5. Журнал — `adb_/adb_log.py`

| Функция | Контракт |
|---------|----------|
| `adb_log_read(serial='', package='', lines=200, level='', tag='') -> str` | хвост журнала с фильтрами |
| `adb_log_crash(serial='', lines=200) -> str` | буфер падений: пусто — приложение не падало |
| `adb_log_clear(serial='')` | очистить буферы **перед** проверяемым действием |
| `adb_log_pid(package, serial='') -> int` | номер процесса приложения |

Экран говорит, что приложение «не работает», журнал — почему. Порядок разбора такой:
`adb_log_clear()` → действие → `adb_log_read(package=…, level='E')`. Без очистки причина
ищется среди тысяч посторонних строк.

## 6. Сценарий целиком

```python
from adb_.adb_app import adb_app_start, adb_app_wait
from adb_.adb_input import adb_input_tap_on, adb_input_text
from adb_.adb_log import adb_log_clear, adb_log_crash
from adb_.adb_ui import adb_ui_text, adb_ui_wait

adb_log_clear()
adb_app_start('<package>')
adb_app_wait('<package>')                      # экран рисуется секунды

print(adb_ui_text())                           # посмотреть, что предлагают
adb_input_tap_on('Войти')
adb_ui_wait('Пароль')                          # дождаться следующего экрана

adb_input_tap_on('Пароль')                     # поставить курсор в поле
adb_input_text('<value>')
adb_input_tap_on('Продолжить')

try:
    adb_ui_wait('Готово', timeout=30)
except TimeoutError:
    print(adb_ui_text())                       # что вместо ожидаемого экрана
    print(adb_log_crash())                     # и не упало ли приложение вовсе
```

Ожидание здесь не украшение: `adb_app_start` и любое нажатие возвращаются мгновенно, а
экран рисуется секунды. Ожидание не дождалось — это `TimeoutError`, а не `False`:
молча пройти мимо неоткрывшегося экрана нельзя, следующее нажатие уйдёт в чужой.

CLI тех же модулей — для ручной проверки, без обёрток:

```bash
python -m adb_.adb_ui map                      # карта текущего экрана
python -m adb_.adb_ui find <надпись>
python -m adb_.adb_input tap-on <надпись>
python -m adb_.adb_input scroll down
python -m adb_.adb_app current
python -m adb_.adb_app list --query <часть имени>
python -m adb_.adb_app pull-apk <пакет> --out /tmp/apk   # base и сплиты на машину
python -m adb_.adb_log crash
```

## 7. Чек-лист «сделать что-то на телефоне»

1. `adb devices` — устройство на месте (`mobile_device.md`, § 2).
2. `adb_ui_text()` — карта экрана: цель на ней есть?
3. Цели нет → она ниже (`adb_input_scroll`), в другом приложении (`adb_app_current`)
   или экран нарисован полотном (§ 2) — тогда зрение.
4. Действие — `adb_input_tap_on` по надписи, не по координате.
5. Проверка — `adb_ui_wait` следующего экрана, а не «нажали, значит сработало».
   Экран заранее не известен — `adb_step_tap` вместо шагов 4–5: он сравнит сам
   (`mobile_steps.md`).
6. Не сработало — `adb_log_crash()`, потом `adb_log_read(package=…, level='E')`.

## 8. WebView — третий канал: CDP — `adb_/adb_cdp.py`

`uiautomator` видит WebView одним узлом: ни текста, ни кнопок страницы в дереве
нет; зрение описать такое может, но не может ни вычислить, ни нажать, и второй
раз ответит иначе. DevTools внутри WebView точен: DOM, `eval` с возвратом
значения, навигация — воспроизводимо, без модели. Условие одно: debuggable-сборка
(debug APK), иначе сокет `webview_devtools_remote_<pid>` не поднимается.

| Функция | Контракт |
|---------|----------|
| `adb_cdp_connect('package', serial='') -> dict` | pid → forward → список страниц; forward переповешивает на свежий pid при каждом вызове |
| `adb_cdp_pages() -> list` | открытые страницы: `{title, url, ws}` |
| `adb_cdp_eval('js', url_part='') -> значение` | вычислить и вернуть значение; `returnByValue` — только данные, DOM-объекты так не вернуть |
| `adb_cdp_navigate('url', url_part='', waitfor='') -> str` | открыть и дождаться загрузки, вернуть итоговый адрес; игла `url_part` сверяется с итоговым href, точное `href == url` — успех всегда; `waitfor` — JS-условие, которого дождаться после смены адреса |
| `adb_cdp_waitfor('js', url_part='', timeout=10, poll=0.3) -> значение` | опрашивать выражение до истинности и вернуть значение; навигацию страницы (eval бросает) пережидает, провал — TimeoutError с последним значением |
| `adb_cdp_capture_all('package', urls, 'out', serial='') -> list` | пачка: открыть каждый адрес, дождаться дорисовки, снять экран PNG в каталог (имя — из адреса); сбой одного адреса не гонит пачку |
| `adb_cdp_element_at(x, y, url_part='') -> dict` | элемент под экранными координатами снимка: `{tag, id, cls, text, href, rect, chain}`; деление на `devicePixelRatio` — внутри |
| `adb_cdp_element_rect('селектор', url_part='', serial='') -> dict` | обратный ход: прямоугольники всех элементов по CSS-селектору — `{count, dpr, origin, items: [{tag, cls, text, css, screen}]}`; `screen` — уже пиксели снимка, с поправкой на начало WebView на экране |
| `adb_cdp_element_shot('селектор', 'out', url_part='', serial='') -> dict` | выкройка элемента: `Page.captureScreenshot` с clip по первому совпадению — `{file, rect}`; `out` с `/` на конце — имя из селектора; кадр в физических пикселях (`captureBeyondViewport` домножает на dpr, `scale` держат 1) |
| `adb_cdp_target_pick('substr', port=9222) -> dict` | целевая страница по части адреса: `{title, url, ws}`; не найдено или неоднозначно — ошибка со списком всех страниц |
| `adb_cdp_viewport(url_part='', serial='') -> dict` | геометрия страницы на экране: `{x0, y0, dpr, css_w, css_h}`; начало координат — из окна WebView в дампе uiautomator |
| `adb_cdp_tap(selector, url_part='', serial='') -> tuple` | тап по центру элемента, возвращает экранные пиксели; доставка через CDP Input, см. ниже |
| `adb_cdp_storage(items, url_part='', reload=False) -> dict` | залить `{ключ: значение}` в localStorage страницы и прочитать обратно: `{seeded, values}`; значения кладутся как `JSON.stringify` (контракт шины — читают `JSON.parse`), `reload` перезагружает страницу после записи; строка-значения, похожая на готовый JSON, отклоняется `ValueError` до страницы — иначе закодировалась бы дважды |

CLI: `python -m adb_.adb_cdp connect com.example.app | pages | target reserve | eval 'location.href' |
waitfor 'window.ready' | navigate https://localhost/menu.html --waitfor 'document.title' |
capture com.example.app shots/ <url...> | element 540 300 | element-rect .tab |
element-shot .tab shots/ | viewport | tap <селектор> | storage diaData='{"name":"СКУБА"}' --reload`.
Флаги: `--url-part` (цель), `--timeout`
(navigate/waitfor), `--json` — вывести значение как JSON (`true`/`null`, а не Python-`True`/`None`:
вывод едят `jq` и скрипты, без флага идёт читаемый repr).
Транспорт — `adb_ws` (WebSocket на stdlib): фрагментация длинных ответов и
ping/pong уже учтены в нём.

`element_rect` нужна, когда элементом надо померить картинку: «где на снимке
лежит эта крышка/кнопка/поле», чтобы загнать координаты в `image_seam` или
`image_measure` (`image_tooling.md`, §4–5) — без ручной арифметики vw→px.
WebView начинается не с верха снимка, а ниже статус-бара, и DOM его высоту не
знаёт: функция берёт её из списка окон системы (`dumpsys`, на Android 16 это
строка `ty=STATUS_BAR`), сырой сдвиг лежит в `origin`. Значение
устройство-зависимое: на эмуляторе 66 px, на телефоне 91 px — промах на эту
высоту означает «меряю не там». Приложение, рисующее во весь экран включая
область статуса, поправку сломает: в нём доверять следует только `css`.

Страницы ассетов открываются схемой `https://localhost/<страница>`: на `file://`
обработчик схемы не реагирует, а `chrome://`-переходы WebView блокирует.
Навигация асинхронна — `Page.navigate` отвечает до смены страницы, — поэтому
ходят через `adb_cdp_navigate`, иначе следующий шаг отработает по старой странице
и примет её за новую.

**Завершение навигации — по ИТОГОВОМУ адресу, и адрес ещё не готовность.**
Игла `url_part` сверяется с итоговым href после редиректов: игла от страницы-
источника (`auth` при редиректе на `reserve.html`) не сработает никогда, и
`TimeoutError` в сообщении об этом скажет. Точное совпадение `href == url`
засчитывается независимо от иглы: возврат на текущую страницу — успех (иначе
«навигация не работает» оказывалось ложной паузой в 15 с). Когда мало самого
адреса — данные страница раскладывает после смены href — просят `waitfor`:
`navigate(..., waitfor='document.readyState === "complete"')` или отдельно
`adb_cdp_waitfor`. Слепой `sleep` вместо ожидания — источник плавающих
тестов: либо ждёт лишнего, либо не дожидается.

`element_shot` бережёт от ручного кроя: вместо «снять полный экран и вычесть
статус-бар» она отдаёт кадр ровно по элементу — его меряют `image_seam`,
`image_rect_seams` и `image_audit` (`image_tooling.md`, §5–6). Chrome берёт
целые пиксели с округлением вниз, поэтому `rect` в ответе описывает записанный
кадр (IHDR png), а не теоретический `css×dpr` — мерить надо по нему.

**Состояние страницы — писать прямо в шину, а не тапать по редактору.**
Приложения держат персональные данные и режимы в localStorage (у dia — ключ
`diaData`), и настроить их тапами через секрет-редактор дольше и менее
воспроизводимо, чем написать в то же место, откуда приложение читает.
`adb_cdp_storage` кладёт значения как `JSON.stringify` — класть надо dict, а
не готовую строку: ручное экранирование кавычек и кириллицы в JS-выражении —
типовое место поломки. Строковое значение, начинающееся с `{` или `[`, —
готовый JSON-текст; функция сериализует сама, такое значение закодировалось
бы дважды, страница прочитала строку вместо объекта и приложение молча уехало
на дефолты шины (ошибка тоньше пустого экрана). Хитрость в том, что двойное
кодирование не падает, а live, поэтому функция отклоняет его `ValueError`
до всякого обращения к странице — передавайте объект или распарсенное
`json.loads` значение. Обратное чтение возвращает сырые строки до всякой
перезагрузки: `reload` асинхронен и читал бы гонку. После `reload` приложение
перечитывает шину на старте — следующий шаг (снимок, diff) должен дать
странице дорисоваться.

**Цель выбирается адресом, а не порядком.** После цикла печати в приложении живёт
второй, оффскрин WebView (у Reserve — `evod_pdf.html`), и он тоже виден `pages()`;
«первая страница со ws» оказывается им, навигация в него упирается в
`chrome-error://chromewebdata/` и повторами не лечится — только `adb_app_stop`.
Отсюда правило: в многоцелевых приложениях любой вызов с `url_part`, а слепой
пустой — только когда `pages()` честно отвечает одной страницей. Холодный старт
тоже гонка: стартовая страница приложения через пару секунд сама уходит на основную,
навигация в этот момент сталкивается с ней — цель берут из списка страниц,
сам переход повторяют.

**Тап — событием в страницу, не системным `input tap`.** SurfaceFlinger отдаёт
системное касание окну только после отрисованного им кадра: холодный, загруженный
WebView держит клик в очереди 3–5 секунд, и «нажал — не открылось» выглядит как
мёртвый слушатель, хотя слушатель жив. `adb_cdp_tap` шлёт
`Input.dispatchTouchEvent` прямо в рендерер — в ту же очередь, что и `eval`, —
и доставка становится такой же предсказуемой, как вычисление. Возвращает тап
экранные пиксели (через `adb_cdp_viewport`) — сверить со снимком.

**Начало координат страницы — измерением, не формулой.** Сдвиг содержимого
WebView к центру экрана (`x0`, `y0`) не выводится из `screen_h − dpr·css_h`:
эта формула предполагает, что всё несъеденное место — сверху, а на телефоне
сверху статус-бар, снизу панель навигации, и остаток делится между ними.
`adb_cdp_viewport` берёт прямоугольник крупнейшего WebView-узла из дампа
uiautomator; на эмуляторе Reserve это (0, 66) — статус-бар, на телефоне со
своими панелями — свои числа, и угадывать их незачем.

## 9. Диалог сохранения документа — `adb_/adb_doc.py`

| Функция | Контракт |
|---------|----------|
| `adb_doc_save(save_dir='Download', serial='', timeout=40) -> str` | дождаться системного диалога сохранения, нажать «Зберегти», дождаться файла; вернуть путь на устройстве |

Приложение отдаёт файл не само: оно поднимает `CREATE_DOCUMENT` — и экран
перехватывает `com.google.android.documentsui`, чужое окно со своими надписями
(по-украински — «Зберегти») и своей разметкой. Порядок, который `adb_doc_save` проверяет на каждом
шаге: фокус перехватил documentsui (не наш ли экран вообще?), кнопка сохранения
нашлась среди узлов, файл появился и дописался. Жать «где-то справа внизу»
нельзя: **тап мимо кнопок диалога — отмена**, он закрывается молча и без
следа, а повторного `CREATE_DOCUMENT` приложение может не послать.

Файл в `Download` показывается нулевой длиной раньше, чем дописывается:
`MediaStore` регистрирует строку до готовности байтов. Оседание — по двум
подряд совпавшим замерам `(size, mtime)` при ненулевом размере; одинарный
`size > 0` ловит пустой файл. Если такой файл уже был — documentsui спрашивает
о замене, и «замінити» тоже нажимается здесь.

CLI: `python -m adb_.adb_doc save --dir Download`.

## Грабли

1. **`logcat` без `-d` не завершается никогда** — команда висит до таймаута, а вызывающий
   ждёт. В модуле `-d` стоит в каждой команде; своя команда мимо модуля — ставить самому.
2. **`input text` не умеет кириллицу и эмодзи** — он шлёт нажатия текущей раскладки, а
   в ней их нет: на устройство уедут пропуски или мусор. Модуль отказывается вслух, а не
   печатает испорченное. Ввод не-ASCII делают отдельной клавиатурой-приёмником (IME),
   которую ставят на устройство и назначают на время работы.
3. **Аргументы `adb shell` разбирает оболочка на устройстве, а не Python** — adb склеивает
   их в одну строку. Пробел в тексте рвёт аргумент надвое, `$` подставляет переменную
   телефона, кавычка ломает команду. Всё, что идёт в `adb shell`, экранируется по правилам
   `sh`.
4. **Дамп `uiautomator` срывается на анимации** («could not get idle state») — переход
   между экранами короче секунды, и попытка приходится ровно на него. Лечится не числом
   попыток, а паузой между ними; в модуле это уже сделано.
5. **К дампу приписан хвост `UI hierchary dumped to: …`** (да, с вендорской опечаткой) —
   в XML он не входит и разбор ломает. Вырезается разбором от `<?xml` до последнего
   `</hierarchy>`.
6. **`am start` и `monkey` сообщают о провале нулевым кодом возврата** — «Error:» и
   «No activities found to run» лежат в обычном выводе. Проверять код возврата
   недостаточно, нужно смотреть текст.
7. **`force-stop` чужого приложения гасит экран, на который смотрит человек** — на общем
   устройстве это заметно. Останавливать имеет смысл то, что сам и запустил.
8. **Фильтр журнала по приложению требует запущенного приложения** — logcat отбирает
   строки по номеру процесса, а у незапущенного его нет. Упавшее приложение фильтруется
   не по пакету, а через `adb_log_crash()`.
9. **Обёртка открывает несуществующую страницу системным диалогом ошибки** — адрес,
   который есть на сайте, но не в ассетах приложения, поднимает из обёртки окно
   «Application Error». Диалог — отдельное окно: он перехватывает касания и виден
   на снимках, а «навигация» за ним будто работает. Перед переходом проверяют, что
   страница в приложении есть.
10. **Системный `input tap` доходит до окна только после отрисованного кадра** —
    холодный или загруженный WebView держит касание в очереди SurfaceFlinger 3–5
    секунд: слушатель жив, нажатие обработано, но «не сразу», и проверка
    «тапнул — открылось» превращается в несводимую гонку. В WebView тап доставляют
    CDP-событием (`adb_cdp_tap`), нативный остаётся для экранов без отладки.
11. **Тап в середине анимации бьёт по соседу** — шторка Reserve едет 0.28 с, и
    центр кнопки в это время стоит там, где ещё лежит затемняющая подложка: тап
    по ней закрывает шторку. Ждущий тест сверяет прямоугольник цели дважды и
    трогается, когда замеры совпали.
12. **Сокет DevTools рождается позже активности** — `adb_app_wait` возвращается,
    как только появилась активность, а `webview_devtools_remote_<pid>` безмолвствует
    или обрывает соединение ещё секунду-другую. Прямой вызов `adb_cdp_connect`
    сразу после старта — гонка, которой нет внутри модуля; повторяй подключение.
13. **Осевший после отменённого сохранения пикер держит экран** — documentsui
    поверх WebView ломает загрузку фоновой страницы (та же уезжает в
    `chrome-error`) и не даёт `adb_app_start` вывести приложение на передний план.
    Перед сценарием — `adb_app_stop('com.google.android.documentsui')`.
14. **Погасший экран эмулятора — тапы в темноту** — без «розетки» дисплей гаснет
    за минуту, невидимый WebView валит загрузку в `chrome-error`, и все проверки
    после этого врут. `svc power stayon true` на эмуляторе — один раз, навсегда.
15. **Прямые вызовы CDP без `url_part` берут первую страницу из списка** — а после
    цикла печати это оффскрин-страница printing-WebView; `eval` на ней отрабатывает
    по чужому DOM («null.classList» там, где элемент есть). Многостраничное
    приложение — всегда с адресной оговоркой.
