# Tool Rules — автообнаруживаемые инструменты для LLM

> Инструмент — обычная функция в специальной ветке кода. Её **докстринг — это контракт для
> LLM**, а не комментарий для человека. Ошибки возвращаются, а не выбрасываются.
>
> Слоёв переиспользуемого кода два: инструменты знают проект и видны LLM, общие библиотеки
> переносимы и не видны. **Универсальное пишется в библиотеку, а не в ветку инструментов**
> (§1) — иначе соседний проект напишет то же самое заново.

## 1. Куда писать: два слоя переиспользуемого кода

Прежде чем писать функцию, реши, в какой слой она идёт. Слоя два, и в разговоре
инструментами называют оба — но устроены они по-разному, и ошибка слоя обходится дорого.

| | Инструменты | Общие библиотеки |
|---|---|---|
| Где | ветка инструментов (`<root>/tool/**`) | общий модуль проектов (здесь — `py_modules/`) |
| Привязка к проекту | **да**: знают его таблицы, роли, логику | **нет**: про проект не знают ничего |
| Видит ли LLM | **да**, выбирает по докстрингу | **нет**, это обычный импорт |
| Реестр в БД | заводится автоматически | не заводится |
| Кто вызывает | движок сценариев и агенты | код проекта, в том числе инструменты |
| Git | часть репозитория проекта | обычно отдельный репозиторий (submodule) |

Ниже по тексту «инструмент» означает первое — то, что видит LLM: остальные разделы про
контракт, докстринг и реестр относятся только к нему. Что уже лежит в общем слое и как с
ним обращаться — `py_modules.md`.

**Прежде чем писать в любой из слоёв — перечисли существующее.** `ls` по пакетам общей
библиотеки и докстринги кандидатов дешевле самописного аналога: половина кода, который
пишут руками (обход устройств, снимки, пробуждение экрана, поиск по дампу), уже лежит
в библиотеке, работает и имеет CLI.

**Зависимость односторонняя: инструменты пользуются библиотеками, наоборот — никогда.**
Обычным импортом, без обёрток:

```python
from mysql_.mysql_ import mysql_get_db_async     # общая библиотека
from logging_.logging_ import logger_info


async def fact_collection_add(name: str) -> dict:
    """Инструмент проекта — знает его таблицы, пользуется общим доступом к базе."""
    async with mysql_get_db_async() as db:
        ...
```

### Универсальное — в общую библиотеку

**Правило: написал код, который пригодится другому проекту, — ему место в общей
библиотеке, а не в ветке инструментов.** Признаки такого кода:

- не упоминает таблицы, роли, состояния и понятия конкретного проекта;
- решает задачу целиком своими силами: разбор формата, работа с хранилищем, время,
  очередь, обёртка над внешним API;
- объясним без контекста проекта — «клиент Redis», а не «очередь задач конвейера».

Смешанный случай разделяется: общая часть уходит в библиотеку, проектная остаётся
инструментом и её импортирует. Инструмент при этом худеет до своего смысла — что именно
он делает **в этом** проекте.

Обратное правило жёстче: **в общей библиотеке не должно быть знания о проекте.** Она
уезжает во все проекты, которые её подключают, и одна проектная подробность делает её
непереносимой для всех остальных.

### Чего слои не умеют

- **Функция в общей библиотеке инструментом не станет.** Автообнаружение сканирует только
  ветку инструментов; положенная в библиотеку функция в реестр не попадёт и LLM её не
  увидит, сколько бы правильный докстринг ей ни написали.
- **Правка библиотеки — правка чужого репозитория.** Она приедет во все проекты сразу, а
  их сюиты здесь не гоняются. Менять сигнатуры и имена — осторожно: соседи сломаются
  молча. Коммит в библиотеку отдельный, указатель submodule обновляется сознательно.
- **Проектная логика в ветке инструментов — норма, обычная бизнес-логика — нет.** Всё,
  что лежит в ветке, становится инструментом автоматически и попадает в выбор LLM.

## 2. Требования к функции

1. **Место** — только в ветке инструментов (`<root>/tool/**`). Всё, что туда положено,
   становится инструментом автоматически; обычную бизнес-логику там держать нельзя.
2. **Асинхронная** — движок вызывает инструменты в общем цикле событий.
3. **Имя уникально глобально**, а не внутри файла или категории (см. раздел 4).
4. **Аннотации типов у всех параметров** — по ним строится схема, которую видит LLM.
   Параметр без аннотации превращается в «строку неизвестного назначения».
5. **Значения по умолчанию** у всех необязательных параметров.
6. **Возвращает `dict`** — всегда словарь, даже если результат одно значение.
7. **Не выбрасывает исключения наружу.** Ошибка — часть результата:
   ```python
   return {"success": False, "error": "понятное описание"}
   ```
   Причина: исключение обрывает выполнение сценария, а LLM должна иметь возможность
   прочитать ошибку и попробовать иначе.
8. **Идемпотентность там, где возможно.** LLM повторяет вызовы: при таймауте, при
   непонятном ответе, просто «на всякий случай».
9. **Никаких побочных эффектов, не описанных в докстринге.** Если функция что-то удаляет
   или отправляет наружу — это первая строка описания.

## 3. Докстринг — контракт

Докстринг попадает в промпт. Он одновременно документация и спецификация:

```python
async def <domain>_<action>(target: str, limit: int = 10) -> dict:
    """
    Одна строка: что инструмент делает и когда его выбирать.

    Args:
        target: что обрабатываем — в терминах, понятных без чтения кода
        limit: сколько элементов вернуть максимум (по умолчанию 10)

    Returns:
        success: удалось ли выполнить
        items: найденные элементы
        error: описание ошибки, если success = false
    """
```

- **Первая строка — критерий выбора.** LLM выбирает инструмент по ней. «Обрабатывает
  данные» не помогает выбрать; «Ищет пользователя по email» помогает.
- **`Args:` — не пересказ имени параметра**, а смысл и допустимые значения.
- **`Returns:` разбирается в перечень выходных ключей** — то, что там перечислено,
  становится доступным дальше в сценарии. Ключ, которого нет в докстринге, невидим,
  даже если функция его возвращает.
- Описывать **ограничения**: лимиты, форматы, что будет при отсутствии данных.

## 4. Автообнаружение

Типичный механизм: обход файлов ветки инструментов, разбор синтаксического дерева
(без импорта — импорт исполняет код и требует всех зависимостей), извлечение публичных
функций, их сигнатур и докстрингов, синхронизация в реестр (таблицу БД).

Практические следствия:

- реестр — **производная от кода**, его не правят руками (правки затрутся)
- реестр в seed не попадает (см. `backup_rules.md`)
- удалённая из кода функция должна **исчезать или помечаться неактивной** при синхронизации,
  иначе LLM продолжает вызывать несуществующее
- синхронизация запускается при старте и/или вручную; после правки инструмента её надо
  выполнить, иначе изменения не видны движку

## 5. Уникальность имени

> ⚠️ Если имя инструмента хранится в колонке с уникальным индексом и ограничением длины,
> **два инструмента с совпадающим префиксом схлопнутся** — и синхронизация может
> обрезать/перезаписать записи. Симптом непропорционально страшный: часть реестра
> исчезает.

Правило: имена короче лимита колонки и различаются в начале, а не в конце.
Правило префикса из `code_rules.md` работает и здесь — оно же и даёт различимость.

## 6. Приведение типов

Параметры приходят из LLM и из определения сценария **строками**. Движок приводит их к
аннотированным типам. Отсюда:

- `bool` из строки — сравнение с набором истинных значений, а не `bool("false")`
  (непустая строка всегда истинна)
- пустая строка для числа — это «не задано», а не `0`
- **проверка «значение задано» через «истинность» ломается на `0`, `""`, `False`, `[]`.**
  Различать «не передано» и «передано пустым» нужно явно (`is None`)
- сложные структуры передавать как JSON-строку с явным разбором внутри функции

## 7. Чек-лист нового инструмента

1. **Слой выбран осознанно** (§1): универсальная часть — в общую библиотеку, проектная —
   в ветку инструментов. Смешанное разделено.
2. Файл — в ветке инструментов, имя по правилу префикса.
3. Функция асинхронная, все параметры аннотированы, необязательные — с дефолтами.
4. Докстринг: первая строка = критерий выбора; `Args:` со смыслом; `Returns:` со всеми
   ключами, которые нужны дальше.
5. Возврат — `dict`; ошибки — `{"success": False, "error": ...}` без исключений.
6. Проведена синхронизация реестра; инструмент появился и параметры разобраны верно.
7. Вызов проверен вручную с валидным и с заведомо плохим входом.
8. Опасные действия (удаление, отправка наружу, трата денег) — явно названы в докстринге
   и по возможности требуют подтверждения.

## Грабли

1. **Бизнес-логика в ветке инструментов** — становится инструментом и предлагается LLM
2. **Ключ не описан в `Returns:`** — недоступен в сценарии, «инструмент ничего не вернул»
3. **Исключение вместо `{"success": False}`** — обрыв сценария вместо обработки
4. **Забыта синхронизация** — правка не видна движку
5. **Коллизия имён** — часть реестра пропадает
6. **Проверка «задано» через истинность** — `0` и `""` считаются отсутствующими
7. **Размытая первая строка докстринга** — LLM выбирает не тот инструмент
8. **Универсальный код осел в ветке инструментов** — соседний проект пишет его заново
9. **Функция положена в общую библиотеку в расчёте на LLM** — в реестр не попадёт, её
   там никто не ищет
10. **Проектная подробность просочилась в общую библиотеку** — та перестала быть
    переносимой, и узнают об этом другие проекты
11. **Самописный аналог функции, которая уже есть в общем слое** — одно и то же лежит
    в двух местах и живёт своей жизнью в обоих; перед правкой — `ls` пакетов и докстринги

## Переименование инструмента задевает базу

Имя функции инструмента — ключ в реестре (`tool` в БД) и в шагах workflow, которые
зовут его по имени. Переименовал функцию — сменился `tool_name`, и всё, что звало
старое имя, перестанет работать.

Правка кода при этом обратима, правка базы — нет, а база у всех выкладок общая.
Поэтому: SQL кладём **миграцией** и не применяем его по ходу работы — он приедет
вместе с веткой и применится при старте. Подробности — `database_rules.md`, раздел
«Изменение данных из задачи».
