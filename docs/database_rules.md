# Database Rules — схема, миграции, безопасность прода

> Схема живёт в **одном** DDL-файле — он единственный источник истины. Данные в него не
> попадают никогда. Прод трогается только руками и только адресными `ALTER`.

## 1. Единственный источник схемы

Все `CREATE TABLE` / `ALTER TABLE` / `CREATE INDEX` — **в одном файле миграции**.
Второго файла со схемой не существует, «временных» миграций рядом тоже.

Причина: как только DDL размазан по десятку файлов, ответ на вопрос «какая сейчас схема»
требует их мысленного проигрывания в правильном порядке. Один файл читается глазами.

Порядок применения при старте приложения:

```
миграции (DDL)  →  seed (данные)
```

### Идемпотентность

Файл должен применяться к любой базе — и пустой, и заполненной:

```sql
SET FOREIGN_KEY_CHECKS = 0;
DROP TABLE IF EXISTS `<table>`;
-- ... все DROP сверху файла
SET FOREIGN_KEY_CHECKS = 1;

CREATE TABLE `<table>` ( ... );
```

`DROP` собираются в начале файла, `CREATE` — после, чтобы порядок FK не мешал сносу.

### Порядок создания таблиц

Таблицы создаются **в порядке FK-зависимостей**: сначала те, на которые ссылаются,
потом ссылающиеся. Практически это уровни:

1. независимые справочники (пользователи, ноды, роли, модели)
2. связки M:N между ними
3. сущности, ссылающиеся на справочники
4. дочерние сущности (шаги, переменные, вложения)
5. runtime/журнальные таблицы (сессии, трейсы, запросы, логи)

Держите этот порядок и в файле миграции, и в порядке инициализации репозиториев.

### Конвенции DDL

- `UNIQUE INDEX` — для ограничения целостности, обычный `INDEX` — для ускорения поиска
- комментарий колонки (`COMMENT`) — на всё, что не очевидно из имени
- `ON DELETE CASCADE` — для дочерних записей, `ON DELETE SET NULL` — для ссылок на
  справочник, который может исчезнуть, не унося за собой историю
- явная кодировка/коллация на уровне БД, чтобы не зависеть от дефолта сервера

## 2. Данные — никогда в миграции

Миграция описывает **форму**, а не содержимое. Всё, что кто-то может отредактировать в
UI, в DDL-файле не появляется.

| Тип данных | Где живёт |
|-----------|-----------|
| Схема | DDL-файл миграции |
| Архитектурные данные (роли, ноды, конфигурации агентов) | seed-файл, генерируется из живой БД |
| Пользовательский контент | только БД |
| Автогенерируемое (реестр инструментов, сессии, трейсы) | не экспортируется вообще |

Подробнее про seed и бэкапы — `backup_rules.md`.

## 3. Добавление таблицы: чек-лист

1. `DROP TABLE IF EXISTS` в блок сносов **в правильном месте по FK**
2. `CREATE TABLE` после таблиц, на которые он ссылается
3. Репозиторий/аксессор — по правилам `code_rules.md` (префикс = namespace)
4. Если таблица содержит ручные данные — добавить её в список seed-таблиц
5. Сброс локальной БД и полный прогон с нуля — проверка, что порядок FK не сломан

## 4. Сброс локальной базы

Стандартная процедура: снести том/базу → поднять сервис БД → приложение при старте
применит миграцию и seed само.

Проверять руками, что после сброса приложение стартует **без ошибок FK** — это
единственный надёжный тест порядка таблиц.

## 5. Прод: что можно и чего нельзя

> ⚠️ **Никогда не применять DDL-файл целиком на проде.** Файл содержит `DROP TABLE` и
> обычно сам выбирает базу (`USE <db>`) — так что и «безопасный» пайп в другой хост,
> и попытка «прогнать в тестовую базу» сносят рабочие данные.

Если нужно прогнать файл в песочнице — сначала **срезать строки, выбирающие базу**
(`sed '1,2d'` или аналог), и только потом подавать на вход клиенту с явно указанной
тестовой базой.

Правила работы с прод-базой:

1. **Изменения схемы на проде — только адресные `ALTER` / `RENAME` / `CREATE`**,
   написанные руками, и **сразу же отражённые обратно в DDL-файл**. Иначе прод и файл
   разъезжаются молча.
2. **Не гонять ad-hoc скрипты с пулом соединений** без гарантированного закрытия пула в
   `finally` — утёкшие соединения выедают лимит и роняют приложение.
3. **Кодировку клиента задавать явно** при каждом подключении из консоли, иначе
   не-ASCII данные выглядят как `??????` — и это косметика, легко перепутать с порчей
   данных.
4. **Пароль никогда не появляется в тексте**: ни в документации, ни в коммите, ни в
   истории shell. Он читается из файла окружения в момент вызова.
5. **Перед любой правкой данных — бэкап.** Восстановление из бэкапа дешевле, чем
   восстановление из памяти.

## Грабли

1. **DDL-файл сам выбирает базу** — запуск «куда-то ещё» на самом деле идёт в рабочую
2. **Новая таблица вставлена не по порядку FK** — падает только на чистой БД, локально
   с заполненной базой ошибка не видна
3. **Данные попали в миграцию** — при следующем сбросе они «воскресают» и конфликтуют с
   тем, что человек уже поправил в UI
4. **`UNIQUE` не ловит дубли, если в колонке `NULL`** — SQL считает `NULL` не равным
   `NULL`; для scoped-записей нужен ручной upsert (см. `env_config_rules.md`)
5. **Кодировка клиента по умолчанию** — «испорченные» данные, которые на самом деле целы

## Изменение данных из задачи: SQL кладём, но не применяем

Рабочий каталог подзадачи изолирует **код**, но не базу: `.env` у всех выкладок
общий, база одна на весь стенд. Отсюда правило, которое иначе неочевидно.

**Подзадача, которой нужно изменить данные, кладёт SQL миграцией и не применяет
его.** Ни `UPDATE` по таблицам, ни `POST /tool/sync`, ни правку шагов workflow —
ничего, что видно за пределами её ветки. Миграция едет вместе с кодом, который её
требует, и применяется при старте: человек, сливающий ветку, видит обе половины
работы на одном экране.

Причина не в осторожности, а в необратимости. Ветку откатывают одной командой,
базу — нет. Изменение, сделанное посреди работы, немедленно видят соседние
подзадачи, живой конвейер и роли, которые в этот момент работают, — включая тот
прогон, который это изменение и делает.

Типичный случай — переименование функции инструмента. В коде это правка одной
строки, а в базе — `tool_name` в реестре и в шагах workflow, которые зовут
инструмент по имени. Синхронизация реестра на живом стенде ломает всё, что звало
старое имя, и делает это сразу.

Применяют такой файл **после слияния ветки**, с той же страницы, где смотрят
diff: `/admin/task/diff?task=<id>`, вкладка «Миграции». Там же сухой прогон —
выполнить в транзакции и откатить, показав, сколько строк затронет. Для файла с
DDL сухого прогона нет: MySQL коммитит `ALTER TABLE` неявно, и «проверка» стала
бы настоящим применением.

Что попадает в такой файл и как он устроен — `.claude/docs/migration.md`, раздел
«Ручная миграция данных». Журнал применённого — таблица `migration_manual_log`:
по ней видно, что уже прогнано, куда и чем кончилось.

## Миграции: имя — метка времени, применяет yoyo

`YYYYMMDDHHMMSS_<что делаем>.sql` в `migrations/`. Например
`20260101000000_initial_schema.sql` — начальная схема, `20260826090000_project_task_metric.sql`
— таблица замеров.

Метку берут командой `date +%Y%m%d%H%M%S`, а не сочиняют. **Секунды обязательны:**
округлив до минуты, две работы одного часа берут один номер, и вся уникальность
метки пропадает — при слиянии веток это конфликт, то есть ровно то, от чего метку
времени и завели.

Почему не `0001`, `0002`. Миграции пишутся в ветках подзадач параллельно, и
номерами они столкнулись бы: две ветки завели бы `0002.sql` с разным содержимым, и
слияние молча оставило бы одну. Метка времени уникальна сама по себе, а
алфавитный порядок файлов совпадает с хронологическим — в нём yoyo их и применяет.

**Начальная схема заморожена.** Новые таблицы и `ALTER TABLE` идут отдельным
файлом, а не дописываются в неё. Дописать — значит изменить уже применённый файл:
yoyo его больше не тронет (он в журнале), и на живой базе изменение не появится,
а на новой установке появится. Две базы разъедутся молча.

**Применяет только yoyo**, при старте приложения (`mysql_migration_up`). Руками
файл прогонять не нужно и вредно: журнал `_yoyo_migration` не обновится, и yoyo
применит его ещё раз.

> ⚠️ **Переименовать применённую миграцию — значит применить её заново.** yoyo
> помнит применённое по имени файла. Хеш в журнале — sha256 **от имени**, не от
> содержимого, поэтому фиксация переименования считается точно:
> `hashlib.sha256(name.encode()).hexdigest()`.

**Имени базы в файле нет.** Ни `USE`, ни `CREATE DATABASE`: базу задаёт
подключение, yoyo создаёт её сам. Раньше в схеме стоял `USE \`project\``, и любой
прогон «в песочницу» молча сносил рабочую базу.

**Порядок таблиц — по зависимостям.** Создание идёт с включённой проверкой
внешних ключей, поэтому таблица-цель обязана стоять раньше ссылающейся. Проверка:

```bash
python3 - <<'EOF'
import re
s = open('migrations/20260101000000_initial_schema.sql').read()
creates = [(m.start(), m.group(1)) for m in re.finditer(r'CREATE TABLE `(\w+)`', s)]
pos = {n: i for i, (_, n) in enumerate(creates, 1)}
for i, (start, name) in enumerate(creates, 1):
    end = s.find('CREATE TABLE', start + 10)
    for ref in re.findall(r'REFERENCES `(\w+)`', s[start:end if end > 0 else len(s)]):
        if ref != name and pos.get(ref, 10**6) > i:
            print(f'{name} ссылается на {ref}, который создаётся позже')
EOF
```

## Проверять — в песочнице, а не на рабочей базе

`migration_sandbox_create()` заводит одноразовую базу `<рабочая>_sandbox_<метка>`,
накатывает в неё всю папку миграций по порядку и отдаёт имя. Там проверяют новую
миграцию и новый код; потом базу сносят целиком.

Данных в песочнице нет: она проверяет схему, а не поведение на живых данных.
Копировать рабочие данные — значит носить в проверку и персональные записи, и
мусор. Нужны данные — их наливает seed, тем же путём, что и в пустую рабочую базу.

Права выданы узко: `developer` может создавать и сносить только базы с префиксом
`project_sandbox_`. Снос чужой базы модуль отклоняет сам — имя базы подставляется
в запрос текстом, и ошибка вызывающего иначе означала бы `DROP DATABASE` по рабочей.
