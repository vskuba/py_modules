# Datetime Rules — время и часовые пояса

> Одно правило на всё: **любая метка времени, которую видит человек, показывается в
> часовом поясе из настройки `timezone`.** Человек сверяет её с часами на стене, а не
> с часами контейнера.

## 1. Три пояса, которые разъезжаются

Контейнеры живут по UTC — и приложение, и база. Пользователь живёт в своём поясе.
Настройка `timezone` в таблице настроек (`'+3'`, `'UTC-2'`) говорит, в каком именно.

Отсюда три источника времени, и они не совпадают:

| Источник | Что даёт |
|----------|----------|
| `datetime.now()` в контейнере | пояс образа — UTC по совпадению настроек, а не по замыслу |
| `NOW()` / `CURRENT_TIMESTAMP` в базе | пояс базы — тоже UTC |
| настройка `timezone` | пояс, в котором человек читает |

Правило простое: **хранение — в UTC, показ — в поясе настройки.**

## 2. Что делать при показе

Время, прочитанное из базы, перед показом сдвигается. Никаких «и так сойдётся»:
разница в три часа выглядит как метка из будущего или из прошлого, и человек
начинает искать несуществующий сбой.

```python
offset = await setting_get('timezone', '+0')
shown = datetime_offset_apply(row['created_at'], offset)
```

**Настройку читать один раз на пачку.** Меток в списке десятки; запрос на каждую —
запрос на пустом месте. Разовый показ обходится готовым `datetime_local(value)`,
который смещение возьмёт сам.

Наступали дважды. Первый раз — журнал работы агентов показывал шаги на три часа
раньше, чем они случились, и «47 минут без записей» приходилось пересчитывать
руками. Второй — страница с чужими метками, где часть значений шла из базы, часть
из приложения, и они расходились между собой в одной таблице.

## 3. Что делать при сравнении

Сравнивать можно только величины **из одного источника**. Классическая ловушка:
метка записана приложением в поясе настройки, а свежесть её проверяют через `NOW()`
базы. При расхождении поясов запись либо вечно «свежая», либо мгновенно «протухшая»
— и то, и другое выглядит как случайный сбой, а не как ошибка в поясах.

```python
# Так: обе стороны из одного источника
stale_before = await datetime_now() - timedelta(seconds=60)
"... WHERE last_seen_at >= %s", (stale_before,)

# Не так: метку писало приложение, порог считает база
"... WHERE last_seen_at >= NOW() - INTERVAL 60 SECOND"
```

Это же относится к ручным проверкам: `TIMESTAMPDIFF(SECOND, <метка>, NOW())` над
колонкой, которую пишет приложение, даст разницу поясов, а не возраст записи.

## 4. Колонки, которые читает фронтенд сам

Отдельный случай: значение уходит в браузер, и он переводит его сам —
`new Date(str + 'Z')`. Такие колонки пишутся **строго в UTC** и на сервере не
сдвигаются: иначе сдвиг применится дважды.

Признак у колонки один на всю жизнь. Если её пишут в UTC для фронтенда, значит
никакой серверный показ её сдвигать не должен, и наоборот. Смешение двух
соглашений в одной таблице — источник расхождений, которые ловятся глазами и
никогда автотестами.

## 5. Чек-лист

- [ ] Новая метка времени: решено, кто её читает — сервер или браузер;
- [ ] показ человеку идёт через смещение из настройки;
- [ ] настройка прочитана один раз на список, а не на строку;
- [ ] сравнение свежести берёт обе стороны из одного источника;
- [ ] в ручных запросах к базе `NOW()` не сравнивается с меткой приложения.
