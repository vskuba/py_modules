# Сверка списков колонок в коде (sql_align)

> `INSERT` и `SELECT` одной таблицы в одном файле должны перечислять колонки
> одним голосом: этот инструмент сверяет списки текстом, не дожидаясь падения
> теста, читающего кортеж по индексу.

## 1. Зачем

Добавление колонки в таблицу-снимок — три ручных правки: список `INSERT` в
сохранителе, список `SELECT` в читателе и порядок `VALUES`. Забыл одну — и
`row[17]` в тесте вдруг читает соседнюю колонку: провал выглядит как враньё
данных, а не как сдвиг. Порядок `%s` против длины списка расходится — запрос
падает уже на живой базе.

## 2. Что сверяется

- **списки равной длины** одной таблицы в одном файле: множества (пропала/
  лишняя) и порядок (переставили);
- длина списка `INSERT` против числа **значений** в `VALUES` — литералы вроде
  `1, NULL` считаются, функции с запятыми внутри — нет (снять ложный счёт).

Разная длина — штатное чтение подзадачей: `SELECT at, price` из таблицы, куда
сохранитель пишет пять колонок, — не расхождение.

## 3. Чего здесь нет

- **Схемы базы.** `mysql_schema` сверяет таблицы с миграциями; этот модуль
  не соединяется никуда и работает даже с пустой базой.
- **Межфайльных пар**: пишет один файл, читает другой — это чужой договор.
- **Подзапросов и f-строк** со сборкой колонок строкой — список не разобрать,
  молчание, не находка.

## 4. CLI

```bash
python -m sql_.sql_align [root] [--table имя]     # выход 1 — есть расхождения
```

## Грабли

1. **SQL живёт в склеенных литералах** — `'INSERT INTO t (a, ' 'b) VALUES …'`;
   перед разбором текст сшивается (`_joined`), иначе список дробится на огрызки.
2. **Первый `from` не всегда нужный** — между `SELECT` и `from` не должно
   попадаться чужих `select`/`from`/`join`, такой захват выбрасывается;
   жадность к первому `from` иначе ловит подзапросы как список колонок.
3. **Порядок — не приговор сам по себе**: именованный курсор переживает
   разнобой, но чтение по индексу — нет; находка говорит «набор тот же,
   порядок разный», решает читающая сторона.
