# Mysql remote — разовый запрос к базе прода

> `mysql_/mysql_remote.py`: SQL доезжает на прод через stdin, учётки читаются
> на той машине из её `.env`, ответ приходит таблицей без клиентского шума.
> Разведка схемы (`tables`/`columns`/`find`) — те же три вопроса, что у
> `mysql_schema`, только заданные живому проду.

    PYTHONPATH=py_modules python3 mysql_/mysql_remote.py 'SELECT NOW()' \
        --target rhapsody-prod --container dating_mysql --env .env.prod --dir datingai
    PYTHONPATH=py_modules python3 -c "from mysql_.mysql_remote import mysql_remote_find; \
        print(mysql_remote_find('rhapsody-prod', 'first', container='dating_mysql', \
        env_file='.env.prod', app_dir='datingai'))"

## 1. Зачем

Привычка «посмотреть на проде» писалась каждый раз заново и каждый раз с
ошибкой:

```bash
cat probe.sql | ssh хост 'cd ~/app && set -a && . ./.env.prod && set +a && \
    docker exec -i -e MYSQL_PWD="$MYSQL_PASSWORD" контейнер mysql -t \
    --default-character-set=utf8mb4 -u"$MYSQL_USER" база' 2>/dev/null | grep -v 'bind \['
```

В этой строке пять мест для промаха, и все пять уже стоили круга: без
`--default-character-set` Cyrillic в JSON-колонке отвечает «Invalid JSON path
expression», без `-t` ответ едет нечитаемыми табами, `.env` без `set -a` не
экспортирует переменные, а `2>/dev/null` заглушает и настоящую ошибку базы.
Один раз вместо `first_at` написали `created_at` — и скрипт умолк на середине,
потому что mysql бросает файл на первой ошибке, а stderr был заглушён.

Локальные двойники к проду не доезжают: `mysql_query` стучится `pymysql` в
свою базу по адресу из локального `.env`, `compose_x` ходит в compose своей
машины. До продной базы есть одна дорога — ssh, и она здесь одна на все
запросы и разведки.

## 2. Устройство

Три слоя, каждый со своей работой:

| Слой | Кто | Что делает |
|------|-----|-----------|
| дорога | `ssh_.ssh_x` | скрипт уходит через stdin — кавычки не съедаются, значений нет в `ps` |
| учётки | `set -a && . ./.env*` на самой машине | секрет не покидает прод и не подставляется с локальной стороны |
| клиент | `docker exec -i … mysql` внутри скрипта | кодировка включена, `-t`/`-N -B` на выбор, шум гасится `quiet` |

SQL доезжает переменной `DSH_SQL` и `printf` — через аргументы командной
строки он не проходит вовсе, только окружением.

Разведка — тот же ход, только `-N -B` ради разбора. `find` отвечает на
«в какой из сорока таблиц лежит время» одним `information_schema` запросом
вместо перебора `DESCRIBE`; это ровно та разведка, что спасает от `Unknown
column` до правки запроса, а не после второго промаха.

## Грабли

⚠ **Голое имя файла для `.` POSIX ищет по PATH, а не в каталоге.** От
`cd app_dir` до sourcing доходит путь, и `. .env.prod` без `./` отвечает
`not found` именно на проде с dash. Относительность судится по отсутствию
`/` в имени: файл `.env.prod` сам начинается с точки — по первой букве его
первая версия принимала за уже относительный путь.

⚠ **Правка продной базы — только явно.** Без `write=True` уходят лишь
читающие первые слова; код возврата `-2` и слово в `error`, а не исключение:
осмотр не должен иметь возможности случайно поправить живых людей.

⚠ **`--dir` разбирает `~/` только в начале**, остальное кавычится как есть:
`shlex.quote` тильду не раскрывает.

⚠ **Шум гасится списком `MYSQL_REMOTE_QUIET`** (сессия ssh, `[Warning]`
клиента, строки `bind [`). `--no-quiet` на них не распространяется; если
клиент начал печатать новый — не убирайте старый маркер, допишите новый.

⚠ **Маска `LIKE` фильтруется символами `[_%a-z0-9]`** — в `find` и `tables`.
Регистронезависимый поиск идёт `LOWER()` по обе стороны; кириллица в
разведке имён таблиц не работает намеренно: метки схем — латиница.
