# Docs Rules — формат документации

> Документация пишется для того, кто открывает файл, чтобы **сделать задачу**, а не чтобы
> восхититься архитектурой. Правило попадает в файл после того, как на грабли наступили —
> и вместе с объяснением, почему они грабли.

## 1. Разделение папок

| Папка | Содержимое | Признак |
|-------|-----------|---------|
| `docs-common/` | универсальные правила | копируется в новый проект без правок |
| `docs/` | устройство конкретного проекта | содержит имена таблиц, портов, файлов |

**Тест на переносимость:** если из файла нельзя убрать проектные специфики, не потеряв
смысл, — файл проектный. В общих правилах пишут не «`migrations/20260101000000_initial_schema.sql`», а «единственный
DDL-файл»; не имя контейнера, а «контейнер приложения».

Обратное тоже верно: общее правило не дублируется в проектной документации. Проектный файл
**ссылается** на общий и описывает только то, чем проект от правила отличается.

## 2. Структура файла

```markdown
# <Название> — <подзаголовок одной строкой>

> Суть в одном-двух предложениях. Читается вместо всего файла, когда некогда.

## 1. <Раздел>
...

## Грабли
1. **<Симптом>** — <причина/последствие>
```

Обязательные элементы:

- **H1 с подзаголовком** — чтобы из оглавления было понятно, о чём файл
- **блокквот-выжимка** сразу после H1 — главное правило файла
- **нумерованные разделы** — на них удобно ссылаться в обсуждении
- **раздел «Грабли»** — то, из-за чего файл вообще написан
- **чек-лист** там, где есть повторяющаяся процедура
- **команды проверки**, если правило можно проверить машинно

## 3. Тон

1. **Правило + причина.** Правило без причины нарушают при первом неудобстве. Одна фраза
   «иначе будет X» удерживает лучше слова «обязательно».
2. **Утвердительно, в настоящем времени.** «Схема живёт в одном файле», не «схему следует
   размещать».
3. **Показывать ❌ и ✅ парой.** Неправильный пример рядом с правильным читается быстрее
   абзаца объяснений.
4. **Таблица вместо перечисления однородного.** Файлы, поля, статусы, соответствия — в
   таблицу.
5. **Честно про пробелы.** Не реализовано, не проверено, известная проблема — пишется
   прямо. Замолчанный пробел находят в аварии.
6. **Без воды.** «Важно отметить», «как известно», «в современной разработке» — удалить.

## 4. Чего в документации нет

- **Секретов**: паролей, токенов, ключей — даже «примерных», даже устаревших
- **Доменов, IP, внутренних адресов** — в общих правилах вообще, в проектных — только если
  без них нельзя
- **Персональных данных** и реальных данных пользователей в примерах
- **Пересказа кода**: перечисление всех функций модуля устаревает через неделю; описывается
  назначение, контракт и неочевидное
- **Дублирования**: одно правило живёт в одном месте, остальные ссылаются
- **Истории изменений** — она в git

## 5. Именование файлов

Проверять существующий шаблон в целевой папке **до** создания файла (это же правило —
первое в `code_rules.md`). Внутри одной папки имена однородны: либо все с суффиксом, либо
все без.

- нижний регистр, `snake_case`, расширение `.md`
- **имя tool-дока — полный неймспейс модуля**: `setting_/setting_state.py` →
  `setting_state.md`, `image_/body_/body_.py` → `image_body.md`; неймспейсы — только
  существующие папки, ничего не выдумывать
- один файл — одна тема; ориентир ~200 строк, превышение — сигнал разделить
- индексный файл (`readme.md`) со таблицей состава — чтобы папка читалась без `ls`

## 6. Поддержание в актуальности

0. **Перед коммитом прозу проверяют инструментом.** Секунда работы; вывод обязан быть
   чистым:

   ```bash
   PYTHONPATH=. python -m tool_.tool_typo
   ```

   Ловятся следы неудачной правки — подмена буквы из другого алфавита (`косинуc` с
   латинской `c` глазами не видна), слипшиеся при вставке слова (`вcwd`, `иTokenizer`),
   повтор слова подряд. ⚠ **Чистый вывод означает «механических следов нет», а не
   «текст без ошибок»**: орфографию и согласование это не проверяет — за ними
   `--prose` и живой читатель. Подробности и границы — `tool_typo.md`.

1. **Правка поведения и правка документации — один коммит.** Разнесённые по времени, они
   не встречаются никогда.
2. **Устаревший файл хуже отсутствующего**: отсутствующий заставляет читать код,
   устаревший заставляет верить в неправду.
3. Файл, потерявший актуальность, **удаляется**, а не оставляется «на всякий случай».
4. В индексе — только существующие файлы. Строка в индексе на несозданный файл допустима
   лишь как явно помеченный план.
5. Раздел «Грабли» пополняется по факту: наступили дважды — записали.

## 7. Новый инструмент приносит свою страницу

Инструмент без страницы находят только чтением кода — а чтение кода и есть то, ради чего
документация существует. Поэтому **новый namespace или инструмент выходит комплектом**, и
комплект едет одним коммитом:

| Что | Куда | Зачем |
|-----|------|-------|
| докстринги публичных функций | рядом с кодом | контракт вызова; формат — `code_rules.md`, §7 |
| страница `docs/<namespace>.md` | `docs/` | устройство модуля, порядок работы, грабли |
| строка в `docs/readme.md` | индекс | без неё страницу не найдут |
| строка в таблице корневого `CLAUDE.md` | корень репозитория | что прочесть перед правкой namespace |

Разнесённые по коммитам, код и документация не встречаются никогда (§6.1).

**Страница обязательна у того, что зовут руками**: есть CLI, есть режимы, есть порядок
вызовов. Обёртка из трёх функций без граблей обходится докстрингами — заводить ей файл
значит плодить индекс, который нечем наполнить.

### 7.1 Граница между докстрингом и страницей

Они отвечают на разные вопросы — это разделение труда, а не дублирование:

- **докстринг** — контракт одной функции: что примет, что вернёт, обо что споткнёшься;
- **страница** — устройство модуля: из чего собран, в каком порядке звать, почему так.

Поэтому пересказ списка функций на странице остаётся запрещённым (§4): он устаревает
через неделю, а докстринг живёт рядом с кодом и правится вместе с ним.

```text
❌ «Функция image_tone_rows(path, rect, chan) возвращает список кортежей (y, медиана)»
✅ «Оттенок меряется по строкам, а не по площади: полоса выдаёт себя скачком медианы
   g-b, и порог этого скачка — единственное, что здесь настраивают»
```

## Грабли

1. **Проектные специфики в общих правилах** — файл нельзя перенести, правило умирает
2. **Правило без причины** — нарушается при первом неудобстве
3. **Документация отдельным коммитом «потом»** — «потом» не наступает
4. **Пересказ кода** — устаревает быстрее, чем дописывается
5. **Одно правило в трёх файлах** — три версии правила, две неверные
6. **Секрет «для примера»** — навсегда в истории git
7. **Замолчанный пробел** — обнаруживается аварией, а не чтением
8. **Подмена буквы из другого алфавита** — глазами не ловится никогда, только машиной
   (`tool_typo.md`); в докстринге живёт годами и портит корпус поиска
