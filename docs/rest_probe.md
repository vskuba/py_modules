# Разведка чужого API (`http_rest`, `http_watch`, `mcp_client`)

> Один цикл на все проекты: вызвать ручку с угаданным заголовком ключа, прочесть
> схему из zod-ошибки, сторожить поле JSON-эндпоинта, вызвать инструмент MCP.
> Знание о конкретном API (какие поля, какие ручки) в модули не въезжает —
> только механика «ткнуть и прочесть».

## Как устроено

- `http_rest_call` — один вызов; заголовок ключа подбирается из
  `x-api-key`/`Authorization: Bearer` и запоминается на хост (модульный dict
  — живёт до конца процесса); 400 с zod-`issues` превращается в
  `{'message', 'missing': {путь: ожидание}}` — скелет тела для повторного
  вызова собирается из `missing`.
- `http_rest_schema` — обход кандидатов openapi (`/api/openapi.json`, …):
  нашёлся — отдаёт список `routes`, нет — честно `found: None`.
- `http_watch` — близнец `state_watch` для API: `{value_of, probe}`; проба —
  готовая команда сторожа, как у базы.
- `mcp_client_tools` / `mcp_client_call` — streamable-HTTP: `initialize` →
  `Mcp-Session-Id` → `notifications/initialized` → `tools/*`, разбор SSE
  `data:`-строк, ошибка инструмента — `{'error': …}` без исключения.

## Грабли

- MCP-сервер обязан принимать ключ **своим** заголовком и не обязан пробрасывать
  его в апстрим: «Missing API key» из результата — про сервер, честный REST
  ближе.
- `x-api-key` в догме не живёт: у чужих API он то с префиксом, то без, то
  вообще Bearer — отсюда угадывание по кандидатам.
- `_http_rest_tried` — модульный синглтон; длинный импорт удвоит кэш.
