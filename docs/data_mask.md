# data_mask — секреты из дампа до того, как дамп уйдёт наружу

> Дамп запроса, лога или сети браузера перед публикацией (тикет, чат, LLM, файл
> отчёта) прогоняется через маску: номера карт, CVV, токены и пароли режутся по
> значению, имена ключей остаются — по ним дамп и читают.

## 1. Вызовы

| Вызов | Для чего |
|-------|----------|
| `data_mask_text(text)` | текст или байты (`curl -v`, лог): PAN, CVV, Bearer/Slack/JWT-токены по шаблону |
| `data_mask_json(obj)` | разобранный JSON: ключи из `DATA_MASK_SECRET_KEYS` → `***`, строки — через `data_mask_text` |
| `data_mask_find(text)` | что нашлось и где — значения обрезаны до 10 символов, сами секреты наружу не идут |

Все три отдают `(результат, None)` или `(None, 'ошибка')`; исходник не меняется.

```python
masked, err = data_mask_json(json.loads(row['answer']))
```

## 2. Что считается секретом в JSON

Ключи `DATA_MASK_SECRET_KEYS`, **без учёта регистра**: карта (`cvv`, `cvc`,
`cardExpireDate`), заголовки (`authorization`, `x-api-key`, `x-signature`),
OAuth (`accessToken`/`access_token`, `refreshToken`/`refresh_token`, `id_token`,
`client_secret`), `password`, `secret`. Числа и пустые строки не трогаются.

## Грабли

1. **camelCase-ключ из списка не маскировался** — сравнивали `key.lower()` с
   ключами как есть, и `cardExpireDate` не совпадал никогда. Сравнение теперь по
   списку в нижнем регистре; новый ключ добавлять в любом регистре.
2. **Тело ответа токен-эндпоинта — тоже дамп.** Перехват сети браузера
   (`browser_scenario_net`) пишет ответы целиком, а OAuth-ответ несёт
   `accessToken`/`refreshToken` голым hex, который шаблоны `data_mask_text` не
   узнают. Без ключей в списке токены уезжали в отчёт открытым текстом.
3. **Ключ вне списка не маскируется.** Свой секретный ключ (`merchantSecret`,
   `privateKey`) — либо в `DATA_MASK_SECRET_KEYS`, либо маскировать перед вызовом;
   проверять результат глазами перед публикацией.

Тесты — `data_/data_mask_test.py`.
