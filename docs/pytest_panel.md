# Обвязка сюиты панели (`pytest_/`)

> Сюита ходит по HTTP в **работающую** панель. Всё, что для этого нужно одинаково
> у всех — вход, клиенты, сторож сети, адрес базы, уборка после теста.

## 0. Почему сюита против живого приложения, а не против объекта `app`

Половина того, что стоит проверять, живёт не в коде: сессия в куке, срез
префикса прокси, права на странице, порядок роутов. Тест против `app` их не
увидит — он проверит функции, а сломается развёртывание.

Отсюда и обвязка: поднять панель, войти, раздать клиентов. Она у всех
одинаковая, и до переноса лежала в каждом проекте своей копией: замер показал,
что **91% строк фикстур** одного проекта дословно совпадают с другим, а клиент с
сессией был скопирован вместе с ⚠-пояснениями.

| Файл | Что |
|------|-----|
| `pytest_panel.py` | вход, кэш сессий на прогон, клиенты |
| `pytest_net.py` | сторож сети: наружу установки не ходить |
| `pytest_db.py` | адрес базы с хоста, `.env`, уборка после теста |
| `pytest_guard.py` | сторож приёма: исходник без собственных объяснений |
| `pytest_order.py` | отчёт о порядке прогона |

## 1. Клиенты и вход

```python
@pytest.fixture
async def client():
    """Без входа — им проверяется, что закрытое закрыто."""
    async with pytest_panel_client() as http:
        yield http

@pytest.fixture
async def auth_client():
    async with await pytest_panel_as(ADMIN_USERNAME, ADMIN_PASSWORD) as http:
        yield http
```

⚠⚠ **Клиент свой у каждого теста, а сессия общая на прогон.** Свой клиент нужен:
у него свой пул соединений, и один на все тесты держал бы его открытым между
ними. А входить заново незачем — `bcrypt` считает хеш десятки миллисекунд, и на
сотне тестов это складывается.

⚠ **Живость куки проверяется, а не предполагается.** Кука живёт час-другой, и
длинный прогон её переживает. Без проверки сюита падает 401-ми **на последних
файлах**, и причину ищут в правках, которые к делу не относятся. Проба —
`/auth/me`; проект, у которого она зовётся иначе, передаёт свою.

⚠ `follow_redirects=False` намеренно: панель отвечает отказом переходом на вход,
и клиент, идущий по нему, превращает 401 в 200 со страницей входа — тест
зеленеет, ничего не проверив.

⚠ Вход не вышел — падаем **сразу**, а не в середине проверки: «оператор не может
открыть бэкапы» одинаково выглядит и когда права работают, и когда учётки просто
нет.

## 2. ⚠⚠ Сторож сети: два сторожа, и оба обязательны

```python
@pytest.fixture(autouse=True)
def no_outside_calls(monkeypatch, request):
    pytest_net_guard(monkeypatch, request.node.name,
                     ports=(3313,),                       # порт базы наружу
                     pairs=[(h, 8021) for h in PYTEST_NET_LOOPBACK],
                     hint='Внешнее — только через заглушку: `rhapsody_fake.py`.')
```

| | что видит | чего не видит |
|---|---|---|
| сокетный (`pytest_net`) | **любое** соединение | ставится на тест и снимается с ним |
| `http_/http_mock.py` | только HTTP, зато **весь прогон** | не-HTTP соединения |

Сокетный ставится `monkeypatch`'ем на каждый тест, а часть работы уходит в
**фоновые задачи**, которых тест не ждёт. Задача доживает до следующего теста или
до конца прогона, когда сторожа уже нет, и спокойно идёт наружу. Поймано
поимённо: четыре настоящих входа на живой сайт за один прогон сюиты.

⚠⚠ **`ports` и `pairs` — разные разрешения, и слить их нельзя.** «Порт на любом
хосте» для панели означал бы, что чужая машина на том же номере считается своей;
«только петля» для базы не сработало бы вовсе — у неё адрес из сети compose.
Проверено обратным: сторож с одним общим списком пропускал чужой хост на порту
панели.

## 3. ⚠⚠ База: адрес правится первой строкой `conftest.py`

```python
from pytest_.pytest_db import pytest_db_reachable
pytest_db_reachable('3313')          # до любого импорта из src/
```

Имя контейнера с хоста не резолвится, а слой читает адрес **на уровне модуля** —
то есть при первом же импорте чего угодно из проекта. Поправь позже, и поправишь
уже прочитанное.

Там же читается `.env` **поверх окружения**: контейнеру конфиг даёт compose, а
сюите на хосте его не даёт никто. Случайная `MYSQL_DATABASE` в окружении молча
увела бы тесты не в ту базу.

## 4. ⚠⚠ Уборка после теста: сперва задачи, потом пул

```python
@pytest.fixture(autouse=True)
async def db_pool():
    yield
    await pytest_db_after()
```

Пул привязан к циклу событий, а цикл у каждого теста свой: первый тест, позвавший
базу, создаёт пул на своём цикле, второй получает соединения от цикла, которого
уже нет, — и падает «Event loop is closed» на ровном месте.

А закрыть пул, не погасив фоновые задачи, нельзя: ручки заводят работу намеренно
и не ждут её — в этом весь смысл. Брошенная задача держит соединение, закрытие
пула ждёт, пока его вернут, и сюита встаёт намертво **без единого сообщения**.

⚠ Ждать после отмены задачи обязательно: отмена доходит до неё только на
следующем шаге цикла, и без ожидания она жалуется уже после того, как тест
прошёл, — то есть красит собой следующий.

## 5. Что здесь не живёт

Уборка **своих строк** из базы: какие таблицы, по какой примете, что считать
посевными данными — предметное знание установки, и в слой оно не уезжает
(`tool_rules.md`, §1). Общее у неё только одно правило, и оно записано словами:
уборка идёт **и до прогона**, потому что хвост остаётся именно от `Ctrl-C` и
упавшей фикстуры — то есть ровно тогда, когда «убрать в конце» не срабатывает.
