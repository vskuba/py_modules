# Выход для браузера: проверить и не отпустить

Модуль: `browser_/browser_proxy.py`. Отвечает на один вопрос — **откроет ли
браузер эту страницу через этот выход**, и, если надо, оставляет открытую
сессию работе.

Соседи по теме: `http_proxy.md` (дешёвая HTTP-проверка и анонимность),
`browser_control.md` (сессии контейнера).

## 1. ⚠⚠ Бесплатный выход умирает быстрее, чем длится прогон

Замерено на живом реестре в две тысячи адресов:

| Что мерили | Итог |
|------------|------|
| адресов с вердиктом `elite`/`anonymous` | 209 |
| из двадцати свежепроверенных открыли страницу товара | **1** |
| прошло между отбором выхода и первым шагом сценария | ~40 с |
| что сказал браузер на отобранном выходе | `ERR_TIMED_OUT` |

Проверка, сделанная заранее, к моменту работы успевает устареть. Это не беда
кода — это свойство бесплатных прокси, и бороться с ним надо не упорством, а
устройством.

## 2. Как устроено: проверка не отпускает сессию

```python
from browser_.browser_proxy import browser_proxy_pick
from browser_.browser_session import browser_session_close

got = await browser_proxy_pick(candidates, product_url, keep=True)
if not got['proxy']:
    raise ValueError('ни один выход не открыл страницу')

try:
    ...  # сценарий идёт В ЭТОЙ ЖЕ сессии: got['session_id']
finally:
    await browser_session_close(got['session_id'])
```

⚠⚠ `keep=True` — главное здесь. Сессия, открытая проверкой, это **и есть**
доказательство, что выход жив: между «адрес работает» и «работаем адресом» не
остаётся промежутка, в который он успел бы умереть. Закрыв её, мы через
полминуты снова ничего не знаем.

⚠⚠ Взял номер — обязан закрыть. Брошенная сессия это вкладка Chromium до
перезапуска контейнера; через сотню проверок браузер станет медленным, и
причину будут искать где угодно, только не здесь.

## 3. ⚠ Две ступени: сперва дёшево, потом по-настоящему

Браузерная проверка дороже HTTP во много раз — контейнер заводит контекст,
Chromium тянет страницу целиком. Поэтому по реестру её не гоняют:

1. `http_proxy_reach` пачкой — отсекает заведомо мёртвых (их большинство:
   замер дал одного живого из двадцати);
2. `browser_proxy_pick` по выжившим — отвечает на настоящий вопрос и оставляет
   сессию победителя.

⚠ Проверки второй ступени идут пачками по `BROWSER_PROXY_PARALLEL` (четыре):
каждая — живая вкладка в контейнере, а контейнер бывает общим с соседями.

## 4. ⚠⚠ Проверять надо ТОЙ ЖЕ ссылкой, по которой пойдёшь

Главная сайта легче внутренней страницы. Адрес, справившийся с главной, на
карточке товара падал по таймауту — поймано живьём. В `target` кладут ровно
тот URL, который откроет первый шаг сценария.

⚠ Схема обязательна. Адрес площадки обычно хранится так, как его ввёл
человек, — голым доменом; на такой строке httpx падает `UnsupportedProtocol`, и
перебор честно отвергает два десятка живых адресов подряд, виня в этом прокси.

## 5. Почему не хватает HTTP-проверки

Браузер делает не то, что HTTP-клиент: держит CONNECT-туннель, тянет страницу и
следом десятки её ресурсов параллельными соединениями через тот же прокси.
Выход, справляющийся с одним запросом, на двадцати умирает.

⚠ При этом замер показал и обратное: когда адрес **правда** жив, проходят оба
(HTTP 200 за 6 с, браузер — за 4.4 с). То есть HTTP-проверка не врёт — она
просто отвечает на более лёгкий вопрос и устаревает.

## 6. Договор отказов

Ни `browser_proxy_reach`, ни `browser_proxy_pick` ничего не бросают: их зовут
по списку, и одна мёртвая строка не должна ронять остальные. Отказ приходит
теми же ключами, что и удача (`ok: False`, `error` словами) — тот же договор,
что у `http_proxy_check`.

⚠ Текст ошибки режется до первой строки: `Page.goto` приносит call log на
двадцать строк, а в журнале и в ответе человеку нужна суть.

## 7. Что проверять после правки

```bash
PYTHONPATH=. python -m tool_.tool_find "проверить прокси браузером"
```

Живьём — только при поднятом контейнере браузера: модуль ходит в него по HTTP
(`browser_upstream_request`), и без него всякая проверка честно скажет «не
дошли».
