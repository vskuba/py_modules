# Tool Find — найти инструмент по намерению, а не по памяти

> Функций в общем слое больше четырёх сотен, реестра и точки входа нет. Второй вариант
> уже существующей функции пишется обычно не от лени, а оттого, что первую **не нашли**.
> Вход один: сказать словами, что нужно. Опись собирается обходом дерева за пару секунд,
> индекса на диске нет — устаревать нечему.

## 1. Когда звать

Перед тем как писать функцию, файл или namespace — и перед тем как тянуться к `grep`.

```bash
PYTHONPATH=. python -m tool_.tool_find "снять экран телефона"
PYTHONPATH=. python -m tool_.tool_find "сравнить два кадра" --limit 5
PYTHONPATH=. python -m tool_.tool_find --map          # карта: namespace и темы
```

Из кода — одной функцией:

```python
from tool_.tool_find import tool_find

for hit in tool_find('разовый запрос к базе'):
    print(hit['where'], hit['name'], hit['coverage'])
```

## 2. Что лежит в описи

Две половины, потому что ищут одно, а зовут другое.

| Половина | Откуда | Отвечает на |
|----------|--------|-------------|
| функции | докстринги публичных функций уровня модуля | «чем это делают» |
| темы | таблица «Состав» из `docs/readme.md` | «как устроено и обо что спотыкались» |

Опись строит `tool_catalog` — разбором синтаксического дерева, **без импорта**: тяжёлые
зависимости не поднимаются, код файлов не исполняется. Цена приёма — видны только функции
уровня модуля, методы классов в опись не попадают.

Отсюда прямое следствие: **качество поиска равно качеству первых строк докстрингов**.
Первая строка отвечает «зачем звать» не для красоты — она и есть корпус (`code_rules.md`,
§7.1). Функция без докстринга невидима для поиска, каким бы он ни был.

## 3. Как сводятся слова

Совпадение лексическое, но не буквальное: слова запроса и слова описи считаются роднёй по
общему куску. Три степени родства, и различать их обязательно:

| Родство | Пример | Цена |
|---------|--------|------|
| то же слово | `кадр` ↔ `кадр` | 1.0 |
| общее начало | `картинку` ↔ `картинке` | `TOOL_FIND_PREFIX` |
| кусок в середине | `логин` внутри `залогиниться` | `TOOL_FIND_FRAGMENT` |

Третья степень дешёвая намеренно: кусок в середине слова часто совпадает случайно, и
выдача, собранная только из таких находок, обязана признаться, что она слабая.

Ранг — **вес, умноженный на покрытие**, а не сумма. Иначе одно слово, попавшее в имя
функции, перевешивает три слова, попавшие в описание темы: на запросе «разовый запрос к
базе» так и случилось — тема `project_runtime.md` с покрытием 95% уехала под функции с 33%.

## 4. Когда поиск не справился — карта

`coverage` считается по качеству совпадений, а не по их числу. Ниже `TOOL_FIND_WEAK`
выдача признаётся слабой, и вместо неё печатается карта: namespace со счётчиком функций и
темы документации одной строкой.

Это не заглушка, а рабочий путь. «Хочу залогиниться» не находит панель, потому что слова
`логин` нет нигде рядом с ней — зато по карте видно `uvicorn_panel`, и второй запрос уже
попадает. **Честное «не нашлось, вот карта» дешевле уверенно неверного ответа.**

## 5. Границы

- **Синонимы без общего корня не встретятся.** «Залогиниться» и «вошедший клиент» — разные
  слова; никакой лексический поиск их не свяжет. Для этого и существует §4.
- **Опись строится каждый раз** (~2 с на 500 записей). Кеша нет сознательно: устаревший
  индекс отвечает уверенно и неправильно, а это хуже, чем не ответить.
- **Себя инструмент из выдачи убирает.** Иначе слова примеров из его же докстрингов
  становятся корпусом и ловят чужие запросы — на «залогиниться» он находил сам себя.

## Грабли

1. **Функция без докстринга не находится ничем** — ни этим поиском, ни `grep` по смыслу.
   Пустой докстринг публичной функции ловится автопроверкой из `code_rules.md`.
2. **Первая строка вида «Возвращает X»** — слова, которыми не ищут. Функция формально
   описана и практически невидима.
3. **`tool_` — это не ветка инструментов проекта.** `<root>/tool/**` из `tool_rules.md` —
   автообнаруживаемые инструменты, которые видит LLM и которые знают таблицы проекта.
   Здесь же обычный namespace общего слоя, и про проект он не знает ничего.
4. **Слова примеров в докстрингах — тоже корпус.** Пример запроса, вписанный в докстринг
   функции, начинает ловить этот запрос. Себя `tool_find` отфильтровывает, но соседям
   примеры лучше писать теми словами, которыми модуль и так описан.
5. **Высокий `score` при низком `coverage` — мусор.** Совпало одно слово в имени, и вес
   набежал весом поля. Смотреть надо на `coverage`.

## Проверка

```bash
PYTHONPATH=. python -m tool_.tool_find "снять экран телефона" --limit 3
PYTHONPATH=. python -m tool_.tool_find "хочу залогиниться"      # обязан признать слабость
PYTHONPATH=. python -c "from tool_.tool_catalog import tool_catalog; print(len(tool_catalog()))"
```
