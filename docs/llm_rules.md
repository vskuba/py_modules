# LLM Rules — маршрутизация, фоллбэк, параллельность

> Провайдер выбирается по имени модели, порядок — по приоритету с понижением сбойных.
> Каждый вызов пишется в журнал: без журнала ни стоимость, ни причина сбоя не восстановимы.

## 1. Выбор провайдера по имени модели

Имя модели несёт префикс провайдера (`<provider>/<model>`), и клиент выбирается сравнением
префикса. Это даёт одно место, куда добавляется новый провайдер, и отсутствие ветвлений
по всему коду.

```python
name = model_name.lower()
for provider, factory in LLM_PROVIDERS.items():
    if name.startswith(provider + '/'):
        return factory(model_name)
raise ValueError(f"Неизвестный провайдер для модели: {model_name}")
```

Провайдеры, не следующие общей схеме (свой SDK, свой формат авторизации), заводятся
отдельным фабричным методом — но точка входа остаётся одна.

## 2. Приоритет и фоллбэк

У агента — упорядоченный список моделей. Порядок задаётся полем позиции, а не порядком
вставки.

### Понижение сбойной модели

Модель, ответившая ошибкой лимита, помечается временной меткой, и сортировка ставит её
в конец:

```sql
ORDER BY rate_limit_at ASC, position ASC
```

Смысл: пока метка пуста (`NULL` первыми) — работает приоритет; как только модель
выстрелила лимитом, она уходит вниз и возвращается сама, когда остальные тоже отметятся
или метка сбросится.

### Когда переключаться

Переключаться на следующую модель стоит на ошибках, которые **не про содержимое запроса**:
исчерпан лимит, отказ авторизации, проблема оплаты, слишком большой ввод, внутренняя
ошибка провайдера, недоступность сервиса.

**Не переключаться** на ошибках, которые повторятся у любого провайдера: невалидный
формат запроса, сработавшая модерация из-за содержимого, логическая ошибка в коде.
Иначе один плохой запрос перебирает и «сжигает» все модели по очереди.

Список моделей исчерпан — это честная ошибка наверх, а не тихий `None`.

## 3. Таймауты

- **таймаут на соединение** — короткий (единицы секунд): недоступный хост должен
  обнаруживаться быстро
- **таймаут на ответ** — десятки секунд и больше: генерация долгая по своей природе
- таймаут обязателен всегда. Вызов без таймаута однажды подвесит воркер навсегда

## 4. Параллельность

Когда несколько агентов работают одновременно, нужен механизм распределения:

- **слоты**: фиксированное число одновременных исполнителей
- параллельные слоты стоит разводить **на разные модели** — иначе все упираются в лимит
  одного провайдера и параллельность превращается в очередь
- занятый слот помечается в БД с временем захвата; **просроченный захват освобождается по
  TTL** — иначе упавший процесс держит слот вечно
- TTL — единственная защита от «зависших» задач; выбирается больше самого долгого
  ожидаемого вызова

## 5. Журнал запросов

Каждый вызов пишется: агент, модель, время, токены ввода/вывода, длительность, статус,
ошибка. Без этого не отвечаются базовые вопросы: сколько стоит, что тормозит, почему
переключился провайдер.

- **у журнала обязателен TTL** и чистка: он растёт быстрее всех остальных таблиц
- **производные метрики кэшируются** (пропускная способность, средняя длительность):
  считать их на каждый запрос по всей таблице — самому себе устроить деградацию
- у метрики должно быть **значение по умолчанию** на случай пустого журнала: свежая
  инсталляция не должна делить на ноль
- **запись в журнал не должна ронять вызов** — обёртка в `try/except`
  (тот же принцип, что в `observability_rules.md`)

## 6. Промпты и данные

1. Промпты хранятся так, чтобы их правил человек без деплоя (БД/конфиг), а не строками
   в коде.
2. **Пользовательский ввод — данные, а не инструкции.** Отделять его в промпте явно и не
   допускать, чтобы он мог переопределять роль модели.
3. **Ответ модели — недоверенный ввод.** Валидировать перед использованием: разбор JSON
   в `try`, проверка обязательных полей, ограничение диапазонов. «Модель обещала JSON» —
   не гарантия.
4. **Секреты и персональные данные не уходят в промпт** без явной необходимости: они
   попадают в журналы и логи провайдера.
5. Ключи провайдеров — в окружении (см. `env_config_rules.md`), никогда в БД в открытом
   виде и никогда в трейсе.

## Грабли

1. **Фоллбэк на ошибке содержимого** — перебирает и «сжигает» все модели
2. **Нет таймаута** — воркер висит бесконечно
3. **Параллельные слоты на одной модели** — общий лимит, параллельности нет
4. **Захват слота без TTL** — упавший процесс держит слот навсегда
5. **Журнал без чистки** — самая большая таблица в базе
6. **Метрика считается по всей таблице на каждый запрос** — растущая задержка
7. **Ответ модели использован без валидации** — падение на неожидаемом формате
