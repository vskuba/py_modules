# py_modules — общий слой библиотек для всех проектов

> Отдельный репозиторий, подключённый submodule во все проекты сразу. Внутри — то, что
> нужно каждому: доступ к базе, журналы, конфиг, время, очереди, база AI-фреймворка.
> **Про конкретный проект он не знает ничего** и знать не должен: правка приезжает во все
> проекты, которые его подключают.
>
> Куда писать новый код — в библиотеку или в инструменты проекта — решает `tool_rules.md`,
> §1. Здесь: что уже есть, как этим пользоваться и на чём спотыкаются.

## 1. Зачем он нужен

Проектов несколько, и каждому нужен доступ к MySQL, журнал с трассировкой, чтение `.env`,
работа со временем в поясе настройки. Написанное заново в каждом проекте расходится через
месяц: где-то пул закрывается, где-то нет; где-то время в UTC, где-то местное.

Поэтому такой код живёт один раз и подключается как внешняя зависимость. Признак, по
которому код попадает сюда: **он объясним без контекста проекта.** «Клиент Qdrant» —
сюда; «поиск фактов анкеты» — в проект.

Обратная сторона у этого решения одна, и она серьёзная: **изменение библиотеки — это
изменение всех проектов сразу**, а их сюиты в текущем проекте не гоняются. Отсюда
осторожность с сигнатурами и именами (§5).

## 2. Как подключается

Submodule в корне проекта плюс каталог в путях импорта:

```bash
git submodule update --init --recursive     # первая выкачка
```

| Где | Как задаётся |
|-----|--------------|
| контейнер приложения | `PYTHONPATH=/app:/app/py_modules` |
| тесты | `pythonpath = [".", "py_modules"]` в `pyproject.toml` |

Оба пути в `PYTHONPATH` неспроста: корень нужен для кода проекта, `py_modules` — чтобы
модули импортировались коротко, `from mysql_.mysql_ import …`, без префикса пакета.

### ⚠️ Импортировать одним способом

Из-за двух корней в путях **один и тот же модуль виден под двумя именами** и может быть
загружен дважды:

```python
from mysql_.mysql_ import mysql_get_db_async              # так — везде
from py_modules.mysql_.mysql_ import mysql_get_db_async   # так — не надо
```

Это не стилистика. Python считает их **разными модулями**: получаются два объекта, два
набора модульных переменных, два синглтона. У `mysql_` на уровне модуля лежит `pool` —
значит два независимых пула соединений вместо одного, и лимит соединений базы
расходуется вдвое. Проверяется одной строкой:

```python
import mysql_.mysql_ as a, py_modules.mysql_.mysql_ as b
assert a is b, 'модуль загружен дважды — разное состояние'
```

**Принятая форма — короткая, без префикса `py_modules.`** Она же преобладает в коде.

## 3. Что внутри

### Хранилища и данные

| Модуль | Что даёт |
|--------|----------|
| `mysql_` | `mysql_get_db_async` (контекст-менеджер соединения), пул (`mysql_pool_get`/`mysql_pool_close`), `AbstractRepository` — база для репозиториев проекта, дамп и восстановление (`backup_engine`), выгрузка таблиц в SQL (`sql_export`), прогон миграций (`mysql_migration_up`) |
| `qdrant_` | векторное хранилище: `qdrant_save`, `qdrant_search`, `qdrant_remove_by` |
| `redis_`, `redis_queue` | соединение с Redis и очередь поверх него |
| `sqllite3` | локальная короткая память LLM: `sqllite3_llm_short_memory_*` |
| `queue_` | очередь в памяти процесса |
| `state` | `state_get` / `state_set` — общее состояние процесса |

### AI-фреймворк

| Модуль | Что даёт |
|--------|----------|
| `ai/framework` | абстракции движка: `AbstractAiFramework`, `AbstractAiFrameworkManager`, `AiFrameworkModel`, `AiFrameworkResult` |
| `ai/provider` | клиенты провайдеров: Claude, Gemini, OpenAI, OpenRouter, Groq, Cerebras, Huggingface, Gx10 — и реестр `ai_provider_registry_get` |
| `ai/ai_thread` | `ai_thread_framework_run` — запуск прогона |
| `ai/ai_vision` | зрение: `ai_vision_describe` (async) и `ai_vision_describe_wait` — «что на картинке» любой моделью из реестра; `ai_vision_normalize` — JPEG без альфы, без него локальные mtmd-серверы отвергают RGBA/WebP-снимки с `400 Failed to load image or audio file` |
| `mcp_` | конфигурация MCP-серверов: `mcp_config_get`, `mcp_config_save`, `mcp_config_tools_json_get` |

Здесь лежит **основа**, а конкретный движок сценариев — в проекте: он знает его таблицы,
шаги и переменные. Граница проходит по этому же признаку.

### Документация

`py_modules/docs/` — те самые универсальные правила, что вы сейчас читаете. Здесь они
живут **в единственном экземпляре**, а в проект попадают симлинком:

```bash
ln -s ../py_modules/docs .claude/docs-common
```

Почему здесь, а не копией в каждом проекте: копии расходятся. Живьём `code_rules.md`
разъехался между двумя проектами на 67 строк — правку внесли в одном и не перенесли.
Общий submodule решает это тем же способом, что и для кода: один источник, обновление
указателя.

Актуальный список — всегда `ls py_modules/`. Таблицы выше называют назначение, а не
перечисляют всё до последней функции: сигнатуры смотрят в коде.

## 4. Именование

То же правило, что во всём коде (`code_rules.md`, §1): **имя публичной функции начинается
с namespace своего файла**.

```
py_modules/mysql_/mysql_.py       ->  mysql_get_db_async()
py_modules/datetime_/datetime_.py ->  datetime_utc_now()
py_modules/qdrant_/qdrant_.py     ->  qdrant_search()
```

Хвостовое подчёркивание в имени файла в префикс не входит — оно ставится, только чтобы не
конфликтовать со встроенным модулем или пакетом (`json_`, `datetime_`, `logging_`).

**Исторические исключения не «чинят».** В нескольких модулях префикс не совпадает с
файлом: `logger_info` (а не `logging_info`), `translate_text`, `add_text_to_image`.
Переименование здесь ломает все проекты, которые их зовут, — цена выше пользы. Новый код
пишется по правилу.

## 5. Правка библиотеки — правка чужого репозитория

Порядок работы:

1. Правка внутри `py_modules/` — **коммит в его собственный репозиторий**, не в проект.
   Это касается и кода, и `docs/`: файл, открытый через симлинк `.claude/docs-common`,
   физически лежит здесь.
2. В проекте после этого меняется указатель submodule — отдельным осознанным коммитом.
3. `M py_modules` в `git status` проекта означает **сдвинутый указатель**, а не правки
   файлов. Это не «изменённый файл, надо закоммитить заодно».

Чего требует осторожности:

- **Сигнатуры и имена.** Соседние проекты зовут их по-старому и сломаются молча — их
  тесты в этом проекте не гоняются. Расширять параметрами с умолчанием безопасно, менять
  порядок и удалять — нет.
- **Умолчания поведения.** Изменил формат времени или уровень журнала — изменил его
  везде.
- **Знание о проекте.** Одна проектная подробность — и модуль перестал быть переносимым
  для всех остальных. Нужно и общее, и частное: общая часть остаётся здесь, частное
  уходит в проект и импортирует её.

## Грабли

1. **Двойной импорт** (`mysql_.mysql_` и `py_modules.mysql_.mysql_` в одном процессе) —
   два объекта модуля, два пула соединений, синглтоны не работают
2. **Коммит правки библиотеки в репозиторий проекта** — правка не уедет к соседям, а
   указатель submodule разъедется с содержимым
3. **Проектная логика в библиотеке** — она непереносима, и узнают об этом другие проекты
4. **Переименование публичной функции** — ломает соседей молча
5. **`M py_modules` принят за правку файлов** — коммитится сдвинутый указатель, о котором
   никто не просил
6. **Ожидание, что функция библиотеки станет инструментом LLM** — автообнаружение сюда не
   смотрит, см. `tool_rules.md`, §1
