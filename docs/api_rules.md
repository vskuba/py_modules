# API Rules — контракт эндпоинтов

> Формат ответа и формат ошибки одинаковы во всём API. Роутеры дробятся по сущности.
> Всё, что пришло из запроса, считается враждебным до валидации.

## 1. Формат ответа

Выбирается **один** стиль и держится по всему API:

```json
// поимённые ключи — предпочтительно: ответ самодокументирован
{"task": {...}}
{"tasks": [...], "total": 42}

// обобщённый ключ — допустимо, но менее читаемо
{"result": {...}}
```

Если в проекте исторически есть оба поколения — **новые эндпоинты пишутся в новом стиле**,
а старые не переписываются без нужды. Но факт двух стилей должен быть задокументирован в
проектной документации, иначе фронтенд каждый раз угадывает.

Список всегда отдаёт объект, не голый массив: массив некуда расширить (`total`, `cursor`)
без ломающего изменения.

## 2. Формат ошибки

Один формат на все ошибки:

```json
{"detail": "Понятное человеку сообщение"}
```

- **код статуса несёт смысл**: 400 — плохой ввод, 401 — не аутентифицирован,
  403 — нет прав, 404 — нет объекта, 409 — конфликт состояния, 5xx — наша вина
- 200 с `{"success": false}` — **не ошибка API**, а результат операции; так отвечают
  только там, где вызывающий обязан продолжить работу (см. `tool_rules.md`)
- текст ошибки — для человека; **не отдавать наружу трейсбеки, SQL и пути файлов**
- в лог пишется полная диагностика, в ответ — краткая формулировка

## 3. Разделение роутеров

Один файл — одна ответственность, как и в остальном коде:

| Файл | Содержимое |
|------|-----------|
| `<entity>.py` | CRUD сущности |
| `<entity>_<operation>.py` | операции/конвейеры над ней |

Роуты, отдающие **HTML-страницы**, живут отдельно от роутов, отдающих **JSON** — у них
разная аудитория, разная авторизация и разные форматы ошибок.

Имена функций-хендлеров — по правилу префикса из `code_rules.md`.

## 4. Валидация входа

1. **Типы и обязательность** — схемой, а не `if` в теле хендлера.
2. **Всё, что попадёт в SQL** — только через параметры запроса; конкатенации нет.
3. **Всё, что попадёт в путь файла** — проверить на `/` и `..`, разрешить только
   ожидаемое расширение.
4. **Всё, что попадёт в shell** — список аргументов, не строка.
5. **Поля, которые роль не имеет права писать** — отрезать до `UPDATE`
   (см. `auth_rules.md`).
6. **Идентификаторы из запроса** — проверить принадлежность текущему пользователю, а не
   только существование.

## 5. Чек-лист нового эндпоинта

1. Метод и статусы соответствуют семантике (создание → 201, удаление → 204 или 200).
2. Проверка прав — в объявлении роута.
3. Схема входа описана; проверены границы (пустая строка, ноль, отрицательное, огромное).
4. Ответ в общем формате; ошибка — `{"detail": ...}`.
5. Изменяющие операции идемпотентны там, где это возможно (повторный вызов не дублирует).
6. Долгая операция не держит HTTP-соединение: постановка в очередь + отдельный статус.
7. Обновлена проектная документация с описанием контракта.

## Грабли

1. **Смешение двух форматов ответа** в одном API — фронтенд обрастает ветвлениями
2. **Список отдан голым массивом** — добавление пагинации становится ломающим изменением
3. **Трейсбек в `detail`** — утечка внутренностей наружу
4. **200 на ошибку** — клиент не отличает успех от провала
5. **Проверка `id` на существование без проверки владельца** — чужие данные по прямой ссылке
6. **Долгая операция синхронно** — таймаут прокси, повторные запросы, дубли работы
